# Api: an operation type and its transports

An Api is an operation type with its laws, in its domain package ([domain.md](../domain.md) rule 5). `ergo gen api` writes its hub, the operation type as data with the one dispatch (below); each transport is a generator written over the hub: `ergo gen rpc` (Effect RPC over HTTP), `ergo gen cli` (a command line), `ergo gen mcp` (Model Context Protocol tools) and `ergo gen llm` (a language model's tools). `ergo gen schema` writes a single type's JSON schema, with no hub. One call has one type, `Request`, and one dispatch, the hub's `Call`, on every transport. (This page was `rpc.md`.)

## ergo gen api

`ergo gen api [--check] DIR.OPTYPE` reads the checked package in `DIR` and writes the hub, one file `DIR/<pkg>api/api.ergo`, headed `// Code generated by ergo gen api; DO NOT EDIT.` and the contract line with its digest (the one every generated file of the contract carries). It admits the contracts `ergo gen rpc` admits (below). For `type Pipeline { Submit(c SubmitRun) Receipt fails run.Closed | NoSuchRun, Board() board.View, … }`:

- `Request = SubmitRequest{C pipeline.SubmitRun} | BoardRequest{} | …`: one call as data, a variant per operation whose fields are its parameters. It is the request every transport carries: `ergo gen rpc` sends it as it is.
- `Op = SubmitOp{} | BoardOp{} | …`: the operation alone, what a policy matches on. (`<Op>Op`, since `Client`'s functions are named like the operations, and a package cannot declare a type and a function of one name.)
- `Reply = SubmitReply{Value pipeline.Receipt} | BoardReply{Value board.View} | …`, a unit operation's variant with no field.
- `Failure = Closed{E run.Closed} | NoSuchRun{E pipeline.NoSuchRun} | …`: each failure type of any row, once, named like the type, which is its JSON tag. Two failure types of one name (`run.Closed`, `board.Closed`) are refused, naming both: their variants and their tags would be one. A failure named like a declaration of the hub or a name it derives from an operation (`Rejected`, `SubmitReply`) is the variant `<Name>Failure`; its tag stays its name. A contract with no failure has the one variant `NoFailure{}`, which no call answers.
- `Outcome = Done{Reply Reply} | Rejected{Failure Failure}`: what one call ends in.
- `OpOf(r) Op`; `Name(op) string`, the operation's name in kebab case (`RunOf` is `run-of`), the command and tool name of every transport; `Doc(op) string`, its doc comment, or its signature when it has none; `Schema(op) json.Value`, the JSON schema of its arguments (`ergo gen mcp` and `ergo gen llm`, below, list it).
- `Call(r Request) Outcome needs <pkg>.<OpType>`: the one dispatch. It calls r's operation on the bound provider and answers its value as its `Reply` or its typed failure as its `Failure`; its own row is empty.
- `Client`, `NewClient(send own func(r Request) Outcome) Client`: a provider of the operation type over any way to carry a `Request` to a `Call` and its `Outcome` back. An `Outcome` that is not the operation's (another operation's value, a failure outside its row) is a defect.
- `Values` holds a value of each operation's value type; `Given { Values, Failure, Failing }` is what a provider answers, and `OutcomeOf(r, g) Outcome` is r's own outcome under it: g's failure when `Failing` and the failure is in r's row, else r's value from `Values`. Every outcome a call can have is an `OutcomeOf` some `Given`, so a law drawn over `(r, g)` sees no case `Call` cannot answer.
- The laws, which run at check time with no provider of the contract: a `Client` whose send keeps each `Request` and answers `OutcomeOf(r, g)` stands in for one.
  - `CallIsTheOperation(r, g)`: `Call(r)` calls r's operation once, with r's arguments, and answers `OutcomeOf(r, g)`.
  - `ClientIsCall(r, g)`: a `Client` whose send is `Call` answers each call as the provider `Call` is bound to does.

`ergo gen rpc`, `cli`, `mcp` and `llm` are written over the hub, and each writes the hub too, beside its own package; `--check` checks both. So no order of gen commands (a gate's replay, a fresh checkout) leaves a transport over a missing or stale hub (AF-REGISTER). The property `TestApiHubAgrees` (`internal/apigen`) generates contracts (records, a union, `Option`, slices, `Map`s, unit values, failure rows of zero to three records, and two parameters of one type), writes their hubs and runs both laws in process.

### Std api and the law Agrees

Std `api` holds what every transport shares ([stdlib](stdlib.md#api)): `Output{Out, Err, Code}`, `ExitOf`, `Exit` and `ExitAs` (an `Output` as a process ends), `Kebab`, `Shell` and `Completion` (a completion script of named commands), and the operation type `Transport[C wire, O wire] { Carry(c C, answer own func(c C) O) O }`: a way to carry a call to an answer and its outcome back. Each of `<pkg>rpc`, `<pkg>cli` and `<pkg>mcp` provides one, `Wire`, and states

```ergo
law Agrees(r Request, g <pkg>api.Given) { api.Agrees(Wire, r, <pkg>api.OutcomeOf(r, g)) }
```

`api.Agrees(t, c, o)` carries c through t to an answer that records the call it got and answers o, and holds that the answer got c, once, and that t gave back o, both compared by their JSON text. So one law admits a transport: a flag the CLI drops, a failure the MCP tools answer as a result, a rejection the server maps to another all fail it. A law of `Transport` itself cannot say it, since a law cannot carry the `wired[C]` its comparison needs and a `Request` holding a slice or a `Map` is not `comparable` (AF1's probe); `Agrees` is a function, and the law stands in each transport package. `<pkg>rpc`'s `Agrees` admits the int rule (rule 5) as its one loss: a case whose ints the wire refuses holds (`fits`). `Agrees` runs in a built test binary (`ergo test`): the rpc wire needs `rpc.Loopback` and the MCP tools module `mcp`'s server, which the check-time evaluator does not run.

Prior art: Effect's `RpcGroup` and `@alchemy.run/domain`'s Api are one contract projected to many surfaces, declared from `Schema` values; tRPC's router is one dispatch its adapters (HTTP, WebSocket) share. Gleam and ReScript have no such layer. In Ergo the contract is the operation type, and the hub is plain Ergo a user could write: a union per call, a total `match`, and laws.

## Effect RPC over HTTP

Std `rpc` serves and calls an operation type over Effect RPC's HTTP protocol, so a stock Effect `RpcClient` (TypeScript, `effect` 4.1.2) calls an Ergo server, and an Ergo program calls it, with no adapter. `ergo gen rpc` writes, from a checked operation type, the Ergo server and the Ergo client of that contract. TypeScript is a peer over HTTP, not a target: Go stays the only target, and no build starts Node, Bun or a TypeScript checker ([decision](../decisions.md#owner-direction-2026-11-10)).

1. **Answer and Serve** (Rm). RPC is an ordinary handler of the std http core ([stdlib http](stdlib.md#http)): `Answer(r, mount, handle)` answers `POST mount` and `POST mount/` (Effect's `RpcClient` posts to its URL with a trailing slash), so a program that serves a page or other routes beside RPC calls `Answer` from its own `http.Serve` handler on one listener. `Serve(l, limits, mount, handle)` is `http.Serve` with `Answer` as its only handler. Before any call starts, as Effect's server answers: another path or another method is a 404 with no body (Effect's router has one `POST` route; FD1-g2), a body over `limits.MaxBodyBytes` 413 (`http.Limits` is required; R1's fixed 16 MiB cap is gone), a failed read 400, and a body that is not Effect RPC's (`Malformed`) a 200 whose one message is the server-wide `Defect` `{name, message}` in the body's framing: `SyntaxError` for a text that is not JSON (the error `JSON.parse` throws in Effect's server), `Malformed` for JSON that is not an envelope. Each `Request` envelope runs `handle(tag, payload)` on a task of its own below the request's task, inside the caller's `needs R`, so the providers a `context` binds around `Serve` serve every call. A client that goes away stops the request's task, which stops every call left, and the request ends after their releases ran. A stop of `Serve`'s caller is `http.Serve`'s: the listener closes, every request and call stops, and each is joined.
2. **Serializations.** `Content-Type: application/json` is a body of one envelope or an array of them, answered with an array of `Exit` envelopes, each carrying its request's id (not its position), once every call ended; `application/x-ndjson` is a line per envelope, answered through `http.Stream` with one flushed `Exit` line per call as it ends, so a fast call's Exit reaches the client while another call of the batch is held (`TestRpcFramedExitFlowsWhileHeld`). The stream is http's streamed body ([stdlib http](stdlib.md#http) 9): status and header are fixed before the first line, and a failed write stops the calls left.
3. **Exit.** A value is `{"_tag":"Success","value":V}`, `null` for an operation with no value; `handle`'s `Failed{Text}` is `{"_tag":"Failure","cause":[{"_tag":"Fail","error":Text}]}`; a defect is `{"_tag":"Failure","cause":[{"_tag":"Die","defect":{"name":N,"message":M}}]}`. `requestId` is the request's id token as sent, a number or a string.
4. **Call.** `Call` posts one `Request` (`application/json`, ids counted from 0) and reads its `Exit`: a value's text, `Failed` with a `Fail`'s error text, `Unrepresentable` for a `Die` named `Unrepresentable` (rule 5), and `Transport` for a failure of the transport: a server that cannot be reached or drops the connection, a status other than 200 (a URL with no RPC mount), a `Die` named `RpcError` (the server's rpc layer could not read the call: the generated `Handle` raises it for a request that is not the contract's), an `Interrupt` cause, a server-wide `Defect` or `ClientProtocolError` message, and a body that is not Effect RPC's. Any other `Die` is the server's own defect (its provider's) and is raised again as a defect: no client row names it, as Effect's `RpcClient` dies with it. A stop of the calling task aborts the request, which stops the call on the server.
5. **The int rule** (orchestrator 2026-11-10, Q3). A JavaScript number holds an integer exactly only within ±(2^53−1), so the Effect RPC profile refuses a larger one at encode and at decode: `Exact` and `ExactUint` fail with `Unrepresentable{Path, Value}`, and `Under` prefixes its path as a walker descends. The `json` codec itself writes every int's exact digits. A field that needs the full range uses a string type. `Refuse(u)` raises the defect a server answers for an int it will not send: the `Die` `{"name":"Unrepresentable","message":…,"path":P,"value":V}`. Effect's `Schema.Defect` reads its name and message; `Call` reads all four back as `Unrepresentable{Path: P, Value: V}`.
6. **Loopback.** `Loopback(handle)` is a `Conn` to `handle` served in this process: each `Call` is an `http.Request` that `Answer`, `Serve`'s own handler, answers (its envelopes, its json answer) under `http.NewRecorder()`, in memory, with no socket and no connection, so it reaches no host and needs no `Ambient`, and `handle` runs on a task below the caller, as a call of `Serve` runs. A stop of the caller stops that task, and `Call` ends after its releases ran (`TestRPCCallsStopWithTheCaller`). The caller's wait for that task is one a test clock sees ([runtime.md](runtime.md#machines-and-actors), Machines and actors 16), so a call held on a `testing.VirtualClock` (a long poll) moves its time (`TestRPCLoopbackWaitIsSeen`). A stop wins over a call's end that is ready with it, so a stopped caller always ends with the stop, never with an answer, and its wait for the calls left parks too (`TestRPCStopWinsOverAnEnd`, explored; wf10 RPC-STOP). A generated `Client` over it runs a contract's laws through the wire: `examples/limiter/loopback` serves the provider its caller passes in, and its test file binds the generated RPC `Client` itself over a memory provider in a named context (`overMemory`), and the hub's `Client` whose send is `Call` over one (`overHub`), under which `ergo test` runs the contract's laws on each client ([types.md, Laws](types.md#laws) 10, Under a context). A row-free constructor would pick the provider outside `cmd/NAME/main.ergo`.

## ergo gen rpc

`ergo gen rpc [--check] DIR.OPTYPE` reads the checked package in `DIR` and writes, over its hub, the package `DIR/<pkg>rpc` with three files, each headed `// Code generated by ergo gen rpc; DO NOT EDIT.` and a line naming the contract by its import path (never by how the command spelled the folder) with its digest:

- `wire.ergo`: `Request`, the hub's (`type Request = <pkg>api.Request`), and each variant `<Op>Request` by its name too (`type SubmitRequest = pipelineapi.SubmitRequest`), so code that names `<pkg>rpc.SubmitRequest` still compiles. A variant per operation has the operation's parameters as fields (the field `Key` for the parameter `key`, so the JSON key is `key`, as Effect's payload struct names it). The file also holds the int walkers `exact<Type>` of every type the contract carries.
- `server.ergo`: `Handle(tag string, payload string) string fails rpc.Failed needs <pkg>.<OpType>`, which decodes the `Request`, checks its ints, answers it through the hub's `Call`, and encodes the `Reply`'s value, or the `Failure` tagged with its type's name. It is `handle(tag, payload, Call)`, whose answer is any function of a `Request`. `Wire` carries a call through `NewClient(rpc.Loopback(handle(answer)))`, so `Agrees` runs the client, the envelopes and the server together.
- `client.ergo`: `Client`, `NewClient(conn rpc.Conn) Client`, and two functions per operation (owner q90, R-chk):
  - `<Op>Checked`, the call itself, whose row is the operation's row plus the transport's failures: `rpc.Unrepresentable` when the operation carries an int (in an argument, its value or a failure), then `rpc.Transport`. For `Take(key string, cost int) Grant fails Limited | UnknownBucket | BadCost` it is `TakeChecked(client Client, key string, cost int) limits.Grant fails limits.Limited | limits.UnknownBucket | limits.BadCost | rpc.Unrepresentable | rpc.Transport`. An argument the transport cannot carry fails before it is sent; a value or a failure read back fails after; a value the server refused to send fails with the server's path and value. A failure the row does not name, a value or failure that is not the contract's, and every `Transport` of `rpc.Call` fail `rpc.Transport`. An operation that carries no int has no `Unrepresentable` in its row, and a server that refuses one anyway is a `Transport`.
  - `<Op>`, with the operation's own signature, so `Client` provides the operation type: `with context { limits.Limiter: limitsrpc.NewClient(conn) } { … }` runs the same code against a remote provider, and the operation type's laws run against it too. It is `<Op>Checked` with the two transport failures raised as defects: `rpc.Refuse(u)` (Die `Unrepresentable`) and `rpc.Lost(t)` (Die `RpcClientError`). One generated path writes the call; the provider is a catch over it.

  A defect of the server's provider is a defect in both forms: it is not a failure of the transport. A caller that must report a lost server or a refused call (a CLI, a gateway with a fallback) calls the checked form and matches its row; code written against the operation type gets the provider. `examples/limiter`'s `limiter check URL` is such a caller (`BucketsChecked`).

`--check` writes nothing and fails when a file differs from what the generator would write. On the server the int rule surfaces as a defect (`rpc.Refuse`) for a value or failure before it is answered, since `Handle` answers a contract's row; a client reads that `Die` back as `Unrepresentable` (Call, rule 4).

The TypeScript mapper and loaders (below) project codec data and operation types, not function bodies. The checked functions live in the generated `<pkg>rpc` package and are not projected. What a call sends is unchanged; only the `Die` of a refused int gains `path` and `value` members, which Effect's `Schema.Defect` does not read.

Prior art: Effect's `RpcGroup` and `RpcClient` (`effect/src/rpc`, `RpcMessage.ts` for the envelopes, `RpcSerialization.ts` for json and ndjson); Go's `net/rpc` and gRPC's generated stubs; Elixir's `:erpc` over Erlang distribution (a call is a process; a dead node is an error, not a typed failure); Gleam and ReScript generate no RPC layer: their users write JSON encoders and decoders by hand (`gleam/json`) or bind a TypeScript client (tRPC). Ergo's contract is the operation type itself, so the server and the client are derived, not declared twice.

## ergo gen cli

`ergo gen cli [--check] DIR.OPTYPE` reads the same checked contract and writes, over its hub, its command line, one file `DIR/<pkg>cli/cli.ergo` over std `flag`, headed `// Code generated by ergo gen cli; DO NOT EDIT.` and the contract line (the same digest). It admits the contracts `ergo gen rpc` admits whose parameters have a command-line form:

- `Request`: the hub's (`type Request = <pkg>api.Request`), so one call has one type on every surface.
- `Commands() []flag.Command[Request]`: a command per operation, its name the operation's in kebab case (`RunOf` is `run-of`), its usage and help the operation's doc comment (the hub's `Doc`, its signature when it has none). Each field of a record parameter is a flag named by its JSON key in kebab case (`userID` is `-user-id`); a nested record's fields are flags under `field.`; with two record parameters, each flag is under `param.`. A string, int or int64 field (or a type defined over one) is a required flag, a bool a switch, a slice of a plain string, int or bool a repeated flag, an `Option` of a plain string or int an optional flag, and a union whose variants have no fields a choice flag (`flag.Choice`) whose words are the variants' names in kebab case (`RunOnce` is `run-once`); a word outside the union is refused `flag.Invalid`. Every other parameter (a string, an int, an int64, a bool, or a type defined over one) is a positional argument, in order. Any other parameter or field (a float, a `Map`, a union with fields, a refined type) is a JSON argument, the flag `-<name>-json`, read with std `json` and its bounds (1 MiB, depth 64; over them is `flag.Invalid`) and printed with `json.Encode`. A recursive record is refused, naming the parameter or field.
- An Api of one operation is the program itself: `Parse` reads its flags and arguments with no command name, and `Print` writes none.
- With several operations, `Parse` is a `match` on the first argument that builds only the command it names and reads the rest with that command's flags, as `flag.ParseCommand` reads a named command (AF-CLI-SWITCH). The list of every command, `Commands()`, is built only for help, an unknown command or no command, which go to `flag.ParseCommand`, and for completion.
- `Parse(args []string) Request fails flag.Failure` and `Print(r Request) []string`: Print writes the command, each flag as `-name=value` (a bool too: a switch alone is true), then `--` and the positional arguments, so a negative int or a text that starts with `-` is read as an argument. `RoundTrips(r) bool` is `Parse(Print(r)) == r`, and `law ArgsRoundTrip(r Request) { RoundTrips(r) }` states it.
- `Policy { Code, Text, Confirm }` and `Defaults()`: what a binary decides of its command line, as values its `cmd/<name>/main.ergo` passes, never generator options. `Code(f <pkg>api.Failure) int` is the exit status of a typed failure (default 1); `Text(r <pkg>api.Reply) Option[string]` the text of a value without `--json` (default `None`: a basic value as its text, else its JSON); `Confirm(r Request) Option[string]` the question a call asks before it runs (default `None`: none). A binary changes one field: `Policy{..workcli.Defaults(), Code: …}`.
- `Run(args []string, p Policy) Output needs <pkg>.<OpType>`: it reads `[--json] [--yes] COMMAND ARGS...`, answers the `Request` through the hub's `Call` on the bound provider and is what to print, std api's `Output{Out, Err, Code}` (`type Output = api.Output`), so a test checks it without a console. The output is a value as p's `Text` when it gives one and there is no `--json`, else as its text when it is a basic value (or a type defined over one), else its JSON, and as its JSON with `--json` whatever `Text` says; a unit as nothing (`null` with `--json`); a typed failure as its tagged JSON (as every transport writes it), with p's `Code`, on standard error after its tag (`NoSuchRun: {"_tag":"NoSuchRun",…}`), or on standard output with `--json`; the help with status 0; a usage error (`flag.Describe`) with status 2, which no policy changes. `Run` asks nothing: a call p's `Confirm` asks a question of ends with status 2 and names `--yes` unless `--yes` is given.
- `RunOnTerminal(args, p) Output needs <pkg>.<OpType> | term.Terminal | io.Stderr`: `Run` that asks the question on the terminal with std `prompt.Confirm` when there is no `--yes`. A yes runs the call; a no or a cancel ends with status 1; a standard input that is not a terminal (`prompt.NotInteractive`) ends with status 2 as `Run` does. Two entries keep a binary with no question free of a terminal: `Run` needs only the operation type.
- `Show(o, asJSON, p)` writes an outcome as `Run` prints it, and `Read(r, out)` reads a `--json` output back as r's outcome. `Wire` prints a call, runs it as a command line with `--json` under `Defaults()`, and reads the output back.
- `Completion(shell api.Shell) string`: the shell's completion script for the commands, with each command's first doc line (std api's `Completion`).
- The laws `ArgsRoundTrip`, `Agrees`, `CodeIsThePolicy(r, g, k)` (a value exits 0 and a typed failure with the policy's `Code`) and `TextIsThePolicy(r, g, t)` (without `--json` a value prints as `Text`; with `--json` every outcome prints as under `Defaults()`).

A script on standard input is the command line's own language: std `api.Session(lines, run)` splits each line into words as a shell splits a simple command (`api.Words`; quotes group, with no expansion), runs them through `run` (the generated `Run` under the binary's policy, or a function over it), and is the steps that ran, stopping after the first whose status is not 0. A blank line and a `#` comment run nothing. `examples/pipeline/cmd/pipeline` reads its operator's script so, with no parser of its own (AF3); its policy gives a refusal status 0 so the script goes on.

A binary ends with the output: `try api.Exit(workcli.Run(process.Args(), workcli.Defaults()))`, or `api.ExitAs("work", …)`, which prefixes the program's name to the error line.

`--check` is `ergo gen rpc`'s. The property `TestCliArgsRoundTrip` (`internal/rpcgen`, beside the loopback property) generates contracts, writes their hubs and cli packages (and an rpc package for every other one), and runs `ArgsRoundTrip` and `Run` in a built test binary. Every contract also has the operation `Pick` (a choice, a nested union, a float and a `Map`), and the probe tests c0's policy: a `Code` of 12 exits 12, a usage error stays 2 under it, a choice word outside the union and a JSON argument over the size bound are refused `flag.Invalid`, `--yes` answers a question without asking, and a question on a pipe exits 2.

Prior art: `@effect/cli` derives a command from its options and args but declares them by hand; Cobra and urfave/cli bind flags to variables. Elixir's `OptionParser` and Gleam's `glint` parse into a keyword list or a record the program declares again. Ergo derives the tree from the contract, as `ergo gen rpc` derives the HTTP calls, and states the round trip as a law.

## ergo gen mcp

`ergo gen mcp [--check] DIR.OPTYPE` reads the same checked contract and writes its Model Context Protocol tools: one file, `DIR/<pkg>mcp/mcp.ergo`, over std `mcp` (moved from `modules/mcp` in wf10 MCP0, so the contract's module requires nothing for it) and std `rpc`'s JSON. The file starts with `// Code generated by ergo gen mcp; DO NOT EDIT.` and the contract line. It is written over the hub, which the command writes too.

The file declares:

- `Request`: the hub's `Request`.
- `Names`: one tool per operation, in the operation type's order. A tool's name is the operation's name in kebab case, as the CLI's command is (the hub's `Name`).
- `Description(name)`: the hub's `Doc`: the operation's doc comment, or its signature when it has none.
- `Input(name)`: the hub's `Schema`, the JSON schema of the tool's arguments.
  - An operation whose only parameter is a record takes that record's fields as its arguments. Any other operation takes its parameters by their JSON keys.
  - The schema follows the codec's JSON form ([types](types.md#codecs) 2):
    - a string, a bool, an integer type and a float type map to their JSON types;
    - a slice is `items`, a tuple `prefixItems`, a `Map` `additionalProperties`;
    - a record is an object whose keys are all required, except a `json.Optional` field's key, which may be absent;
    - a union is `anyOf` its variants, each with its `"_tag"` as a `const`;
    - `json.Nullable[T]` is `anyOf` T and null, and `json.Value` is any value;
    - a refined type is its base, and a type with a by-name pair is its `Wire` type.
  - A recursive type is refused.
- `Call(name, arguments) Request fails mcp.ToolError | mcp.UnknownTool`. Arguments that are not the tool's fail `ToolError`, with the decoder's reason. Module `mcp`'s `Handle` first checks a `tools/call`'s arguments against the tool's input schema (`mcp.Conforms`): arguments outside it are the JSON-RPC error "invalid params" and the tool does not run (`ArgumentsOutsideTheSchemaAreRefused`), so a schema that marks an optional field required fails `Agrees`.
- `Arguments(r) (string, json.Value)`: its other half.
- `Answer(r) json.Value fails mcp.ToolError needs <pkg>.<OpType>`, `Show(Call(r))`. `Show(o)` is the operation's value as JSON, or `null` when it has none; a typed failure is a `ToolError` whose message is the failure's tagged JSON, as every transport writes it. `ReadAnswer(r, called)` reads a tool's result back as r's outcome.
- `Wire`: a call sent as a `tools/call` message through module `mcp`'s `Handle`, to tools that answer with the given answer, and its result read back with `ReadAnswer`.
- `Tools() []mcp.Tool needs <pkg>.<OpType>`: each tool reads its arguments with `Call` and answers with `Answer` on the provider in force where `Tools` ran, which it holds as a context (`InForce`). The tools answer while the `with` that bound that provider runs; a tool called after that `with` ended is the held-context defect ([rows.md, Context](rows.md#context)). A `with` that names a resource lends it ([resources.md, Context ownership as built](resources.md#context-ownership-as-built) 2), so `with context { Op: m } { mcp.Serve(mcp.Server{…, Tools: Tools()}, t) }` serves m and leaves it to its owner.
- The laws `ArgumentsRoundTrip` (`Call` reads what `Arguments` writes as the same `Request`) and `ArgumentsFitTheSchema` (those arguments fit the tool's schema, by `mcp.Conforms`, which is std `jsonschema`'s).

`--check` works as `ergo gen rpc`'s does. The property `TestMcpArgumentsRoundTrip` (`internal/rpcgen`) checks the generated packages:

- It uses the contracts `TestCliArgsRoundTrip` generates, with `json.Optional` fields as well.
- It writes their hubs and mcp packages.
- In a built test binary, it runs both laws and, for each operation, `Answer` against a fixed provider.

`examples/pipeline` serves its Api this way: `cmd/pipeline-mcp` over `mcp/stdio`, and `pipelinemcp`'s `Agrees` holds the tools to the hub.

The int rule (rule 5) is not applied: MCP is not Effect RPC, and the tool's JSON writes an int's exact digits.

Prior art: the MCP SDKs (`McpServer.tool(name, schema, handler)`, with the schema from zod or pydantic) and Effect's `@effect/ai` `McpServer`, which derives tools from `Schema`, declare each tool by hand. Elixir's `hermes_mcp` declares a tool as a module with a schema. Ergo derives the tools from the contract, as it derives the HTTP calls and the CLI, and states as laws that a tool's arguments round-trip and fit the schema it lists.

## ergo gen llm

`ergo gen llm [--check] DIR.OPTYPE` (wf10 L7) reads the same checked contract and writes its tools for a language model: one file, `DIR/<pkg>llm/llm.ergo`, over std `llm`, std `jsonschema` and std `rpc`'s JSON ([stdlib.md, llm](stdlib.md#llm)). The file starts with `// Code generated by ergo gen llm; DO NOT EDIT.` and the contract line. It is written over the hub, which the command writes too. One operation type is so a program's Api, its MCP server and its model's tools, with one name, description and schema for each tool on both.

The file declares:

- `Request`: the hub's `Request`.
- `Specs() []llm.ToolSpec`: one spec per operation, in the operation type's order: the hub's `Name`, `Doc` and `Schema`, the tools `ergo gen mcp` lists. The schema is written as text, the hub's, and checked and encoded once, when the program starts (`jsonschema.Encoded`), so a provider splices its text into each request.
- `Parse(c llm.Call) Request fails llm.UnknownTool | llm.BadArguments`: the call's argument text decoded straight into the record of the tool it names, the flat parameter's record (as on MCP) or the `Request` variant, with no `json.Value` between. Empty argument text is the empty object. A name that is no tool's fails `UnknownTool`; arguments that are not the tool's fail `BadArguments` with the decoder's reason.
- `CallOf(id, r) llm.Call`: its other half, the call a model writes for r by the specs.
- `Result(c, o) llm.Message`: the `llm.Result` that answers c with the hub's `Outcome`: the value's JSON (`null` when it has none), or the failure's tagged JSON with `Failed`.
- `Answer(c) llm.Message needs <pkg>.<OpType>`: `Parse`, the hub's `Call`, then `Result`; a call `Parse` refuses is a failed `Result` that says why, so the model can call again.
- The laws `CallRoundTrips` (`Parse` reads `CallOf`'s call as the same `Request`), `CallsFitTheirSpec` (its arguments fit the spec's schema, by `jsonschema.Conforms`), `SpecsNameEveryOperation` (one spec per operation, with the hub's name, doc and schema), `UnknownNameIsTyped` (a name that is no tool's fails `UnknownTool`, never another tool's `Request`) and `ResultNamesItsCall` (the answer is a `Result` of the call's id, failed exactly when the call was rejected).

`--check` works as `ergo gen rpc`'s does. The property `TestLlmCallRoundTrip` (`internal/rpcgen`) uses the contracts `TestCliArgsRoundTrip` generates, writes their hubs and llm packages, and in a built test binary runs the five laws, `Answer` for each operation against a fixed provider, and `Parse` of arguments that are no object. `benchmarks/llmtools` counts `Parse` per call against hand Go (`encoding/json` into the typed request) and a one-pass floor.

Prior art: the Vercel AI SDK's `tool({ inputSchema, execute })`, Effect's `@effect/ai` `Toolkit` (a `Tool` per `Schema`, `toolkit.handle`) and BAML's tool unions declare each tool by hand and parse a call through a schema; OpenAI's and Anthropic's SDKs take a JSON schema and leave the parse to the caller. Ergo derives the tools from the contract, as it derives the wire, the CLI and MCP, so the tools a model calls and the ones an MCP client calls are one set, and states as laws that a call round-trips and fits the schema its spec lists.

## ergo gen schema

`ergo gen schema [--check] DIR.TYPE` (wf10 JS0) writes the JSON schema of a wire type's form, with no hub: one file, `DIR/<pkg>schema/<type>.ergo` (the type's name in lower case), over std `jsonschema` ([stdlib.md, jsonschema](stdlib.md#jsonschema)). The file starts with `// Code generated by ergo gen schema; DO NOT EDIT.` and the type's line. It declares `TYPE() jsonschema.Schema`, the schema parsed once into a package `let`, and the law `TYPEValuesFitTheSchema(v <pkg>.TYPE)`: the JSON the derived codec writes for every value fits the schema. The schema is the one `ergo gen mcp` lists for an argument of the type (the mapper above). A type with no schema here is refused with its reason: a recursive type, an operation type (`ergo gen api` writes its arguments' schemas), a generic or unexported type. `--check` works as `ergo gen rpc`'s does. `TestGenSchemaFits` (`internal/rpcgen`) generates the package for a record with a `json.Optional` field and a union, checks it in process, and evaluates its law and a probe's (a tag no variant has, a fractional count and a missing key do not fit).

Prior art: zod's `toJSONSchema`, pydantic's `model_json_schema` and Effect's `JSONSchema.make` write a type's schema at run time from a schema value; Go's `invopop/jsonschema` reflects over struct tags. Ergo writes it from the checked type, as it writes the codec, and states as a law that the codec's output fits it.

## TypeScript content mapper and loaders

`ergo tsmap` serves TypeScript 7.1.0-beta's content mapper protocol on
stdio. It reads the checked package with the editor buffer as a read-only
overlay. The mapper and `ergo tsmap --emit-js FILE.ergo` share
`internal/tsproj`: one walk of the checked types emits Effect RPC groups
and schemas, with TS declarations for checking or JS values for loading.
No Ergo function body is translated to JavaScript. No generated `.ts`
file is checked in.

The private local package [tools/ts](../../tools/ts/README.md) provides
Bun, Node and Vite loaders (and an esbuild adapter), the pinned TypeScript
and Effect versions, and setup instructions. Run `tsc --runExternalCode`;
without that explicit permission TypeScript refuses to start the mapper.
Content-mapped files are not emitted as JS by TypeScript, so a runtime
loader is required. Source diagnostics use `ergo`; positions support
UTF-8 and UTF-16. Renamed codec fields use Alias spans, not Verbatim spans.

Field keys follow [Codecs 2](types.md#codecs), including explicit literals.
Decoded TS properties keep the default projected names (`NodeID` as `nodeID`);
Effect 4's `Schema.encodeKeys` maps them to their declared encoded keys
(`"node_id"`). This is the pinned API's equivalent of Effect 3's `fromKey`.
When default names collide (`ID` and `Id`) but explicit keys distinguish them,
the colliding decoded properties keep their source spelling, so neither is
lost. Tagged variants, failure schemas and imported/instantiated records use
the same mapping. The seeded mapper/RPC property includes renamed keys,
non-ASCII and escaped keys, imported fields, and colliding default names.

Supported codec shapes are listed in the tool README. An unsupported
shape is a projection diagnostic, never an unchecked `any`. Each mapped
file exports its package's operation types and every exported codec record
and closed union, including data no operation reaches. Declarations with no codec
(machines, records with function fields or operation types as values) are
left out without a diagnostic. A codec type outside the supported TypeScript
profile still reports a projection diagnostic. Reachable imported types
use private schema names. Cross-file watch registration is not provided
yet: restart TypeScript watch after changing another Ergo file in the
package or an imported package. Runtime loads do not cache the projection.

The schemas follow std json's field and value forms: a record field of
`json.Optional[T]` uses `Schema.optionalKey(T)`, `json.Nullable[T]` uses
`Schema.NullOr(T)` in every position, and nesting composes these rules.
Optional outside a record field stays the tagged Absent/Present union.
The instantiated field type selects its form, including a generic field.
Std `json.Value` uses `Schema.Json`, its untagged JSON form; the tool
README lists what a JavaScript peer does not keep of it. A float64 uses
`Schema.Number`, whose JSON codec writes and reads the same non-finite
strings as std json; a float32 is a projection diagnostic.

Measured acceptance: `ERGO_TS_TEST=1 go test -count=1 -timeout 10m
./internal/tsproj` checks a seeded codec round trip, stock RpcClient
against an Ergo server under Bun/Node/Vite with json and ndjson, and four
signature mutations reported at TypeScript call sites. It is opt-in;
the Go-only gate starts no TypeScript tool.

Prior art: Gleam emits TypeScript declarations beside JS modules;
ReScript genType emits type adapters, with codecs supplied separately.
Ergo emits only the checked codec view: Go remains the target and the
schemas are for the peer. Elixir/Phoenix sends JSON events without a
shared static client contract. The TypeScript 7.1 mapper adds virtual
source and source spans; the loaders supply its missing runtime emit.

## Not yet

- Streams (`RpcSchema.Stream`, `Chunk` envelopes) are not served and a stream operation is not generated. Envelopes other than `Request` (`Ack`, `Ping`, `Eof`, `Interrupt`) are skipped: over HTTP a client's abort is the request's end. Request headers are not read.
