# Rows: errors, capabilities, `context` and `with`

Every function has two rows besides its result: an error row, `fails …`, and a capability row, `needs`. The checker proves that each row is an upper bound on what the body can do. Rows are checked and then erased: the lowered Go has interfaces, structs, early returns and type switches. Definitions are in the [glossary](../../GLOSSARY.md).

*Prior art:* Effect's `Effect<A, E, R>` tracks the same two rows as type parameters; Koka types effects as rows and checks that each is handled; OCaml 5 has effect handlers but does not track effects in types, so an unhandled effect is a run-time exception; Go tracks neither and threads `error` and `context.Context` by hand.

## Error rows

Status: **implemented**: checked by `internal/sketch/check` ([#196](https://github.com/cevr/ergo/issues/196)) and lowered by `internal/sketch/lower` as rule 7 states (check-v1 stage C): `try`, a fallible tail and an error value returned run under `ergo run` (`TestErgoRunFunctionTails`, `TestErgoRunWholeTry`).

```go
func pay(id string) string fails OrderNotFound | GatewayDown needs Orders | Gateway {
	let order = try Orders.Find(id)
	return Gateway.Charge(order)
}
```

1. **Spelling.** `fails A | B` lists error types ([types.md](types.md#error-types)). A union of error types names a row: `fails Fail` with `type Fail = Bad | Oops` means `fails Bad | Oops` ([types.md](types.md#error-types) 4). The row is a set: order and repetition carry no meaning. A function with an error row and no value writes `fails A` after its parameters; with a value, `T fails A`.
2. **Fallible expressions.** An expression is fallible when it can fail with a non-empty row:
   - a call to a function or capability method that declares an error row;
   - `timeout.After(d) { … }` ([runtime.md](runtime.md#timeouts));
   - `with W { … }` whose last expression is fallible;
   - an `if` or `match` in value position whose branch tail is fallible: the branch passes its failure to the expression, as a `with` block does, so an enclosing `catch` or `try` handles it and `return` passes it on (stage C round 2 review O2).

   A `try` expression is not fallible: its failures have already escaped (rule 4).
3. **Handling (S105).** A fallible expression must be tried, caught or returned. It is an error in every other position: a `let` value, an expression statement, an operand, a selector's receiver, a call argument, a struct field value, an `if` condition, a `match` subject, a `timeout.After` duration and a `catch` arm's value.
4. **Escapes.** A failure escapes to the enclosing failure target in exactly these ways:
   - `try e`, which escapes `e`'s whole row;
   - `return e` where `e` is fallible, which passes `e`'s success and its failures through;
   - `return v` where `v` is a value of an error type, or `v` as a function body's tail, unless the function's declared result is that error type (below);
   - the unhandled rest of a partial `try e catch { … }`.

   A function's declared result type is its contract. When it is an error type `E`, a tail or `return` of an `E` value is the function's success value, so `func missing(k string) Missing { Missing{Key: k} }` is a constructor and `E` is not added to its row. The same holds when the declared result is a union whose every member is an error type, written as a named union (`type Fail = Bad | Oops`): a value whose error types are all members of it (`Bad{Why: w}`, or a catch binding of `Bad | Oops`) is the success value, so `func mk(w string) Fail { Bad{Why: w} }` returns a `Fail` and its callers handle no failure (fs1). In every other function an error value at a tail or `return` is a failure, whatever produces it: a literal, a call's value (`return missing(k)`), a local (`let m = missing(k); return m`) or a catch binding (K1, owner question q27 answered as "returns a value"; `TestErrorValueRuleTable`). *Prior art:* Gleam, ReScript and Rust have no implicit failure: an error value is a value and a failure is `Error(e)` or `Err(e)`, which the declared `Result` type decides; Swift needs `throw e`. Ergo keeps the implicit failure and lets the declared result decide where it would be ambiguous.

   The failure target is the innermost enclosing function or function literal. A trailing block is a function literal ([grammar.md](grammar.md#expressions)), so the block of `timeout.After` is a failure target, as every trailing block is (README Gap 31). A `with` block is part of a construct, not a function literal, so it is not a failure target: a `try` inside it escapes to the enclosing function.
5. **Upper bound (S101).** Every error type that can escape a function must be in its declared row. A function with no row lets nothing escape. Returning a value of an error type from a function with no row is therefore S101 (fixture `error-as-value`), unless the function's declared result is that error type (rule 4).
6. **Value of `try`.** `try e` has `e`'s success value, or no value when `e` has none. `try` on an expression that cannot fail is an error (S108), and so is `try` over a catch that handles the whole row with nothing inside it that propagates ([Catch](#catch) rule 5).
7. **Lowering.** `try f()` becomes `v, err := f(…); if err != nil { return zero, err }`. Error types implement Go's `error`; the row is checked and erased. *Prior art:* Borgo's tuple path for `?`; XGo's inline `expr?`; Rust's `?`; Gleam has no operator and uses `use` with `result.try`.
8. **Row values** (owner q47, 2026-11-09). A row's **value type** is the anonymous union of its error types. It is the type of a `case err:` binding ([Catch](#catch) 7), of an error row parameter in a type position ([types.md](types.md#generics) 1: `type Job[F] { Run func() int fails F, Last F }`), and of a row written as a type argument of a type parameter (`Exit[int, NotFound | Busy]`). Two row values are one type when their rows are one set; it prints as its row, `NotFound | Busy`. It has the rules of a union over its members, and no rule of its own:
   - **Assignment.** A value of one of its error types goes in, and so does a row value whose row it holds, a narrower one; a row value goes into a declared union that lists each of its error types (ConvRow). Anything else is S108: "cannot use int as NotFound | Busy in field Last: int is not one of its error types", and, for a wider row value, "it may hold an error type that NotFound | Busy does not list".
   - **Match.** A `match` on a row value is total over its members when its row is known at the instance (S103 names a missing one: "no case handles Busy"). A member that is an error row parameter `F` has no constructors, as a type parameter's value has none: a type test against it is S108 "NotFound is not a variant of F", and only `case _` or a binding covers it, the final case an open union needs.
   - **Equality.** `==` and `!=` apply when every member is equatable, and compare as a union's variants do: the member, then its fields ([types.md](types.md#operators) 1). A row value is comparable when every member is. An error row parameter has no constraint, so a row value that holds one is not equatable: S108 "F values cannot be compared with ==". A record or a union with a row value field is equatable when that field is, as with any field. A row value has no other operator: S108 "a row value has no operator +".
   - **Generators and literals.** A property parameter whose type holds a row value draws one of its members, each equally likely (a member of least rank at the size limit), as a union draws a variant, and prints as that member's literal; a generic instance prints its row argument, `Job[NotFound | Busy]{Name: "a", Last: Busy}`. A row value whose row holds a parameter, or the empty row, which has no value, is not generatable (S108 at the parameter).
   - **Lowering.** A row value is the Go `error` that holds the member; the empty row's is an `error` that never holds one. A row parameter is erased, so `Job[F]` is a Go type with no parameter for `F`, and `Exit[T, F]` instantiates its Go parameter `F` with `error`. Assignment converts nothing, since every error type implements `error`; a match is the type switch on the error; equality is Go's `==` when every member is comparable, else the generated union equality over the error.

   *Prior art:* Zig's error sets are value types, and a set coerces to a superset; OCaml's polymorphic variants type a value by a row, and a match on an open row needs a default case; TypeScript's `Exit<A, E>` in Effect holds a union type `E`; Go lowers every failure to `error`, as Gleam and ReScript lower their `Result` error to the host's value.

## Catch

Status: **implemented**: checked and lowered (196r, check-v1 stage C; `TestErgoRunOneCatch`): type tests, record patterns, `as`, `case err:` and `case _` arms run under `ergo run`.

```go
let outcome = with Live { checkout(id) } catch {
case OrderNotFound:
	"no such order"
case GatewayDown, timeout.Expired:
	"gateway unavailable"
}

let note = try with Live { checkout(id) } catch {
case OrderNotFound:
	"no such order"
} // GatewayDown and timeout.Expired escape through try
```

1. **Arms.** `e catch { case T, U: v … }` handles failures of the fallible expression `e`. `catch` on an expression that cannot fail is an error (S108). The error is in the row, not the type: the catch expression keeps the type of rule 3, so no type depends on a row and nothing cascades from the error.
2. Each type in an arm must be in `e`'s row (S108). An arm the arms before it already cover is unreachable (S108): a type test of a type an earlier arm tested is "caught twice", and a record pattern the earlier patterns of its type cover, together or alone, is unreachable. Coverage is cumulative: the arms are judged in source order against one matrix per error type (check-v1 D-C3; review M1), so `case E{B: true}` and `case E{B: false}` together handle the whole of `E`. This rule reads the arms alone, so it holds whatever the row: a duplicate arm is reported beside a rule 1 error, beside a type that is not in the row, and when `e` itself is invalid.
3. **Value.** When the catch's value is used and `e` has a value of type `T`, each arm yields a value assignable to `T` by the tail rule of function bodies ([Totality](#totality) rule 3), through a final `if` or `match`, or leaves the function; a path of an arm without a value is S107. The catch expression has type `T`. When the value is not used, or `e` has no value, each arm's tail is discarded, as in a function with no result (D-C1). An arm's value whose own failure is not handled is S105.
4. **Total catch (S103).** A `catch` without `try` must handle every error type in `e`'s row. *Prior art:* Rust and Gleam exhaustive `match` on an error enum; Swift propagates an error that no `catch` clause matches to the enclosing scope, and a non-throwing function must handle every error; Ergo's total catch is the same obligation stated per error type.
5. **Partial catch.** `try e catch { … }` handles the named types and escapes the rest through `try`. The rest escapes to the enclosing failure target and is checked against its row (rules 4 and 5 of [Error rows](#error-rows); fixture `try … catch` in `sketch/sketch_test.go`, "partial catch under try still needs the rest declared", S101). `try` covers the whole expression to its right, the caught expression included: in `try h(g()) catch { case X: 0 }` a failure of `g()` propagates, so `h` never runs, while the catch handles `h`'s row (D-C3; review M3). A `try` over a catch that handles the whole row, with nothing inside it that propagates, has nothing to pass on: it is a redundant `try`, S108, as rule 6 of [Error rows](#error-rows) says for a `try` on an expression that cannot fail (stage C round 2 review O3).
6. **Typed failures only (README Gap 1).** A `catch` covers the typed row only. Interruption and defects are not in any row, and they always pass through a `catch`, total or partial. A total catch therefore has no default arm in source. Its lowering must still pass interruption and defects on; the prototype emits a default arm that re-panics with them.
7. **Binding and statements.** `case T as e:` binds the caught error with type `T`, and `case err:` binds the whole failure ([grammar.md](grammar.md#expressions), Expressions 1 and 6). An arm may hold statements. When the `catch` is an expression, the arm's last statement is an expression that yields its value, or the arm leaves the function. `return` in an arm leaves the enclosing function, because an arm is not a block (README Gap 11). Statements in arms are checked (#196), and so is `case T as e:` alone in its arm; an arm's binding it never reads is S110. Every pattern of an arm binds the same names, as in a match (Totality 1): each pattern's names, its `as` name and a record pattern's bindings, form one set, and a pattern that binds a name the others do not, a type test that binds none included, is S108 in either order (review M2). A name the patterns bind at several types binds at their join (Totality 1), so `case NotFound as e, Denied as e:` binds `e` as the row value of `NotFound` and `Denied`, the type `case err:` would give those two (fu8a); the whole failure is `case err:`. The arms are match arms over the failure (check-v1 D-C3): a type test of an error type in the row; a record pattern of one, `case Declined{Reason: r}:`, which handles the whole type only when it matches every value of it (the usefulness solver decides, under the budget of [Totality](#totality) rule 5), else the type stays in the rest; `T as e` around either; `case _`; and `case err:`, which stands alone in its arm and binds the **row value** of the failures the earlier arms leave. A row value's type is the anonymous union of those error types: it can be returned (a failure of those types, checked against the row as rule 5 says), matched (totality over those types), caught, or assigned to a declared union that lists every one of them (an implicit `ConvRow`); it follows [Error rows](#error-rows) 8, so `err == err` compares when every type it holds is equatable (q47; before, it was S108, review M8). Over a row parameter `E` of a generic function, the row value has the type `E`, and the same rule holds: returning it is a failure of `E`, so `case err:` then `return err` re-raises what the arm caught, as `tasks.Retry` does (batch 13, schedule; before, the checker read `E` as a value type and refused the return). A name in an arm's pattern follows [Totality](#totality) rules 1 and 6 as in a match: a lone name of a type, a constant or a capability is a test, and any other lone name is `case err:`; a name of a function, a package or a package value is S108 and binds an invalid placeholder (fuzz-17d6). A refused type test in an arm, a type outside the row (`case int:`) or a type that does not resolve, declares the placeholder a match arm's refused test declares, so a read of the name in the arm adds nothing ([Totality](#totality) 6). An arm after `case err:` or `case _`, and a `case err:` with nothing left to handle, is S108 (unreachable).
8. **Lowering.** A catch becomes a type switch on the Go error value, inline, with no closure; a catch with record patterns, `case err:` or `case _` becomes the decision tree of a match on the error ([runtime](runtime.md#host-and-lowering-notes), Match): one type switch on the error, then switches on its fields, each tested once on a path, and a default branch that passes the same error value on (under `try`) or re-panics with it (a total catch). Past the tree's size bound it is an expressionless switch whose conditions test the error's type and fields (batch-10 M1b). A row value is the Go error itself; `ConvRow` is a type assertion to the union, which the error's variant satisfies. *Prior art:* XGo lowers `expr!` and `expr?:default` through a generated closure; Ergo's catch stays inline.
9. **A named row in an arm** (L2). `case U:` and `case U as u:`, where `U` is a union that names a row ([types.md](types.md#error-types) 4), handle each variant of `U` that the caught row holds, and `u` has the type `U`, so it can be passed or matched as a `U`. At least one variant must be in the row (S108 "U has no variant in the caught row"); variants the row lacks are ignored, since the error is never one of them. A union arm whose variants the arms before it all handle is caught twice (S108), and so is an arm of a variant after the union arm. The lowering is a Go type-switch case on the union's interface, or, in a catch with record patterns, a test with the union's type assertion; the decision tree does not split an interface test, so such a catch is the expressionless switch (Lowering 8).

## Capability rows

Status: **implemented**: checked (#196), with inference (rule 6), and lowered as rule 7 states, a capability being a Go interface reached through the hidden environment (check-v1 stages C and D3b); every `ergo run` test that prints calls `Console` this way.

1. **Spelling.** `needs A | B` lists capabilities ([types.md](types.md#capabilities)). The row is a set, a union as the error row is, so both rows are spelled with `|` (196n); a comma between the names is S001 ([grammar.md](grammar.md#declarations) rule 9).
2. **Charges.** A body charges a capability when it:
   - calls a capability method, `A.m(…)`, which charges `A`;
   - calls a function whose row lists `A`;
   - calls `timeout.After`, an ordinary library function whose signature lists `needs R | Scheduler` (README Gap 31).
3. **Upper bound (S102).** Every capability a body charges must be in its `needs` clause or discharged by an enclosing `with`. A name in a `needs` clause must denote a capability (S104).
4. **Entry.** `main` takes no parameters and returns no value; an error row is allowed (S113). It cannot be called (S113). The checker does not restrict its capability row; the build refuses what the host cannot supply (README Gaps 4 and 5). The entry provides three capabilities: the prelude's `Console` and `Ambient`, the authority to choose the host ([stdlib.md](stdlib.md#host-packages)), and the predeclared `go.Foreign`, the authority to run Go code that no one reviewed (`import go`, [interop.md](interop.md); owner q33). The build provides `go.Foreign` (IG3): it has no operation, so the environment holds nothing for it. `go.Foreign` is a language protocol: no context binds it, in any package, so a `test` never holds it; an entry `go.Foreign: v` is S106 "no context binds go.Foreign: its one provider is the program entry, for a main that lists it", as for `Ambient`. Any other capability in `main`'s row is S109 at the build: "the host provides only Console and Ambient; bind it with a with block inside main". `Ambient`'s one operation is unexported, so no program type implements it and no context binds it (S106); a `test` has no entry, so it never holds `Ambient`.
5. **Names.** A written capability row binds each listed capability's bare name in the body's frame, beside the parameters; `needs http.Client` binds `Client` (with packages; when two packages export the same name, the body qualifies it). A local of that name in the same frame is S104. A local in an inner frame, or a local beside a capability the row does not list, may shadow a package or prelude capability (rows-and-constraints §7 amendment 3; fixtures `local-and-binding-one-frame`, `same-local-as-cap`). A capability name is the capability in a capability row, a context entry key, a `replace` target and as the receiver of `X.m(…)`; in a type position it is the interface type ([types.md](types.md#capabilities)).
6. **Inference.** Inside a package the checker infers each unwritten row of an unexported function with a body and of a function literal; a written row is declared. `main`, `LawX`, exported functions, methods, interface methods, bodiless declarations and the step of an exported machine type spell their rows, and an unwritten row there is empty, so a changed body never silently widens a public contract. A literal passed where a function type is expected is checked against that type's rows. Inference runs per strongly connected component of the package's reference graph, joining rows to a fixpoint, callees before callers (rows-and-constraints §7 amendment 1). The graph's edges are the plain identifiers of each body that resolve, through the body's scopes, to a package function or var: a local, a parameter or a receiver that shadows a package function is not a reference to it (round 15), and a selector's name, a label, a type, a context entry key and a struct literal's field name are not references. A composite literal's key is a field name when the literal's type is a struct and an expression otherwise (a map key, an array index), as in Go; the walk decides it from the literal's written type, through the type declarations and, for an elided type, the enclosing array, slice or map literal's element or key type, and walks a key whose literal's kind it cannot decide (a type parameter) as an expression (round 17). A struct field's value never elides its type ([types](types.md#structs) 3, round 18), so the walk looks up no field: an elided literal there is S108 and the walk only visits its elements, and the walk does linear work in the literal's size (round 18). The checker finds them by a walk of every body before any body is typed, so a type error never hides an edge and the verdict does not depend on the order of the declarations (round 16, class H). A method through a selector and a function of another package spell their rows, so they need no edge. Until its component is final, an inferred row is a row variable of the function: a type that mentions the function (`Box{f}` in a package initializer read before `f` is checked) holds the variable, and once the component is final the variable stands for the solved row, so that type equals the one written with the solved row (round 12, class F). A use of a generic function applies its type arguments to the solved row. A function used as a value inside its own recursive component (passed, stored, compared or placed in a composite literal; a call is not a value use) has the rows it writes there, and each row it does not write is empty, as for an exported function. The same holds for each row of a member that a function literal, a trailing block or a go task inside the component calls, when that literal or task is a value that would carry the row (round 15). A literal carries each row it does not write, a trailing block of a call other than `with` carries both rows, and a go expression carries the error row (its capabilities are charged at the go site). A literal called on the spot passes the rows on like a call, a `with` block passes them on to its enclosing body, and a go statement discards its task. A row the literal writes stops the member's row, and so does a row it takes from the parameter of a callee it is passed to directly whose signature was fixed before any body, when that parameter's function type has the row with no type parameter in it: the signature was resolved before any body, so the stop does not depend on typing or on order (round 17). Such a callee is a function of the package, the universe or an imported package; a local bound to a non-generic one of these (`run := each`); or a method, or a field of function type, selected from a receiver whose type is written: a parameter, the receiver, a local with a written type or bound to a composite literal, or a composite literal itself (`r.Each(…)` with `r Runner`, round 18). The receiver's type is resolved where the local is declared, so a later local that shadows the type's name does not change it; a parameter's type is the one its function's signature resolved, and a written structural type (`r struct{ Run func(…) fails E }`) or a pointer to a named type (`r *Runner`) selects its method or field like a named one (round 19). A typed local (`var r struct{ Run func(…) fails E } = input`) and a composite literal (`r := struct{ … }{…}`) fix a written struct type the same way, resolved at their declaration through the package scope; a struct type that names a type parameter, an implicit one or a name a local shadows stays conservative (round 20). A callee that is a value of inferred type, a generic function bound to a local, and a parameter row that names a type parameter keep the round-15 rule, which is conservative. A row taken from any other expected type does not stop it, because the value uses are found from the source before typing, like the edges (round 16). So the pin does not depend on a row still being inferred, call admission does not depend on the rows, and the rows grow to their least fixpoint (round 14, class G). A type that does depend on such a row leaves its frames provisional, as described next. A use inside a function literal, trailing block or `with` block counts according to typing's record of that frame. The frame is *checked* when typing checked it. The frame is *invalid-diagnosed* when typing skipped it for a reason that typing reports and that holds whatever the rows: a callee or an argument that is invalid because of a refused import, an unknown name, a refused form or an arm's own error. An invalid-diagnosed frame carries no row, so nothing in it is a use (D3; round 8 review). In the reporting pass, a frame is *refused-by-class-G* when its call reads a member that class G refuses, directly or through a local bound to it. Every other skipped frame is *provisional*. This includes a frame whose skip depends on a row that the component is still inferring, and a frame inside a skipped frame. Refused and provisional frames keep their uses. The pin reads the record of the silent pass, so it is conservative: a staged or unknown type is never evidence that a frame is unchecked (round 9 review). The decision whether to report an S108 is made with the converged rows. The S108 names only the uses whose frame the reporting pass checked or refused, and a member with no such use on a row it exceeds has no S108 for that row, because its frame already has a diagnostic of its own and a refusal never cascades (round 10 ruling). An example: a bare generic catch arm `case G as g` takes its instance from the caught row. `g`'s type is provisional only while that row holds an unsolved row variable of a member of the component. A block passed to `g.run()` then keeps the class G use of the member it calls, as with `case G[int] as g`. A row from outside the component is already final, so a wrong arm on it is an error at once, and its frame is invalid-diagnosed (round 11 review). An arm on a caught expression that is invalid reports nothing for a missing instance, because the expression's own diagnostic explains the empty row. When the row never holds the arm's instance, the arm's error is reported and the member's S108 is dropped. The member's error row then stays pinned, and its references inside its component stay invalid. A reference from a component checked after it keeps the member's written signature, so an arity or argument mistake there is reported; each pinned row its body exceeds is no evidence there, so that row is *unknown*: the checker adds `invalid`, its mark of a type it cannot know, to the row (check-v1 stage D1 round 4). Only an unknown row holds `invalid`: a written row, and an inferred row whose pinned empty row held, are evidence and stay as they are, so a member refused for its capability row keeps its written error row, and a try or catch a caller writes against that row is checked (check-v1 stage D1 round 5). A written row with an entry that does not resolve or is refused (an unknown name, a refused defined type, `Fault[DStore]`) is unknown too: that entry stands as `invalid` and the valid entries stay, as go/types keeps a parameter list with an invalid parameter type. Its known part is still evidence for callers (a caller of `func g() int needs DStore | Log` misses `Log`), and as a receiving row it accepts any row: nothing escapes or is charged against it in its own body, and a catch arm over a refused type proves nothing, so the catch gives no totality verdict (check-v1 stage D3a rewrite round 3). An unknown capability row makes the inferred capability row of the enclosing function unknown in the same way, and a written capability row is not known to miss what it holds. An unknown row on the receiving side accepts any row, as an invalid type is assignable both ways: a value assigned to a function type whose row is unknown, a branch joined with one, an argument for a type parameter bound to one, a literal or a trailing block passed where one is expected. A function type nested in a parameter or a result whose row is unknown is identical to another for some content of that row, so it gives no "the parameters or results differ"; the rest of the two types must still match. A receiver whose type is inferred (an `if` join, a type parameter's binding) keeps the known part of each row it accepts, at every depth of its results, and a literal or a trailing block infers a row its expected type leaves unknown, so a failure or a capability the sender is known to have still reaches the checks after it; a `let mut` local keeps the type it was declared with (check-v1 stage D1 round 5). `invalid` is an element like any other, so every row the reference reaches holds it too: the row of a call of it, of a local bound to it, of an instance of a generic function it binds, the rest of a catch, and the inferred row of the enclosing function, of a function literal or a trailing block that calls it, and so of a call of the literal (an immediate call, or a callee whose error row takes a row parameter the literal binds). Creating a literal runs nothing, so the call the literal is passed to keeps a definite row and its checks still report (check-v1 stage D1 round 3). A written error row is closed: `invalid` does not enter it, so a function whose error row is written has a definite row whatever its body calls. An unknown row may hold more than it lists, and the checker never prints `invalid` or records it in what it reports to clients. A check that reports *presence* reads the row's known part, because the error is really in the row: "this catch does not handle …" (Catch 4), an unhandled failure (Error rows 3), an error that a declared row does not list (S101), and a row wider than that of a function type or an interface method. So does a check on the arms alone, "T is caught twice" (Catch 2). These errors hold whatever the unknown row turns out to be, so they are independent, and they are always reported. A check that reports *absence* holds only if the row lacks something: "catch on an expression that cannot fail" (Catch 1), "T is not in the caught row" and an unreachable rest arm (Catch 2), "try on an expression that cannot fail" (Error rows 6), a bare generic arm whose row holds no instance, and a return of no value. On an unknown row such a check would be a *follow-on* of the member's S108, which already rejects the program, so it is silent there, as a type check is silent on an invalid type (round 3 ruling: drop only the follow-ons that depend on the unknown row; never hide an independent error). The mark rides on the row itself, so the rule needs no side table and no extra pass, and the work stays linear in the size of the program (`TestSelfCallWorkLinear`); an earlier attempt that silenced every absence check on a poisoned row, presence checks included, hid real errors and cost quadratic time, and was withdrawn. *Prior art for the mark:* go/types `Typ[Invalid]`, rustc `ty::Error` with `ErrorGuaranteed`, and TypeScript's `errorType` are error types that unify with anything and silence the checks that read them, once their diagnostic is reported. When the body of such a function needs more than the empty row, its declaration is S108 "f is used as a value at L:C inside its own recursive group; write its error row: func f(…) T fails …" ("through the function literal at L:C" or "through the trailing block at L:C" when one carries the use; T is the written result, absent when there is none), or "write its capability row: func f(…) T needs …", or "write its error row and capability row: func f(…) T fails … needs …", and every reference to it inside its component is invalid, so nothing follows from the empty row; the checker never chooses between fixpoints. The diagnostic is at the declaration, where the row is written, so its position does not depend on which use is first (round 16). The use it names is the first in the body whose kind and name sort first, so it moves with that body's declaration (round 17). Calls inside the component stay inferred, and a value use from outside the component reads the final row. The fixpoint is bounded by 2·(bodies + edges)·(D + 1) body checks, where D counts the distinct row elements the component has produced; an element removed and added again does not raise D, so the bound is finite. Past it the component is S108 "cannot infer the error row of f; write it". *Prior art:* Go export data; OCaml `.mli` signatures; Ergo's earlier rule for exported contracts. For class G: OCaml `let rec` is monomorphic inside its own group; Haskell needs a signature for polymorphic recursion; TypeScript reports a name "referenced directly or indirectly in its own initializer"; Go and Rust require every signature. Each refuses the circular case instead of choosing a fixpoint.
7. **Lowering.** Capabilities become Go interfaces whose methods take the task handle first. A function takes a hidden environment with one field per capability, and the task. When `context` knows the concrete provider, the call may be devirtualised.

## Footprints

Status: **implemented** (#199 stage 1): the checker records each frame's footprint in `Info.Footprints`, and the lowering reads it to place interruption points ([runtime.md, I1](runtime.md#i1-interruption-points)) and to find the pure functions, which take no hidden argument ([runtime.md, Host and lowering notes](runtime.md#host-and-lowering-notes)). No tool shows it yet: `ergo inspect` is removed, and showing footprints belongs to tooling #203.

1. A function's footprint is every capability its body exercises, including those its own `with` provides, plus each task it starts (`task.Go`). The compiler infers it and never asks for it.
2. A function is pure when its footprint is empty, not when its `needs` row is empty. `with context { Console: Stdout{} } { Console.Println("x") }` has an empty row and a non-empty footprint, and `func f() needs Probe {}` has a row and an empty footprint.
3. A function type carries requirements only (README Gap 24). A call through an unknown function value counts as impure. A call is pure only when the compiler specialises it to a known function with an empty footprint.
   - A frame is a function with a body, a function literal, the block of a call other than `with` (a `task.Go` body), a named context's builder and a package-level `let`'s initializer. A provider method is a function. A `with` block runs in its enclosing frame.
   - A `with` adds the footprint of each provider it builds, whatever the context's spelling (#199 stage 3c r2). `with W` calls W's builder, a frame whose footprint is every provider W binds. An inline context builds the entries of its acquisition fact (`With.Acquired`) in the enclosing frame: its own provider expressions count there, and so does each acquired provider of a context it embeds, so `with context { W }` counts every provider `with W` builds. An embedded provider that nothing the block needs reaches is not built and adds nothing. A `with` also adds, in every spelling, the footprint of the `Close` of each provider it acquires (`Acquisition.Close`), since the release runs in the enclosing frame when the block ends (#199 stage 3c r3). A `Close` that is an operation of the provider's type is opaque.
   - Making a function literal runs nothing: its body counts for the frames that call it, never for the frame that writes it. A literal called where it is written counts there.
   - A call of a function of the package joins the callee's footprint, and recursive functions join to the least fixpoint, so a mutually recursive pair that calls a capability is impure and a pure pair is pure. A call of an imported function joins the footprint its package recorded.
   - A call is opaque, and so impure, when the compiler cannot see its body: a function value, an operation of an operation-type value (a queue's `Push`, a `Task`'s `Wait`), a host function (its body is Go, so `xs.Append(1)` counts too; a std extern whose Go body is marked pure is the exception, [stdlib.md, Pure bodies](stdlib.md#pure-bodies)), and a for-in over a `Seq`, which calls the Seq.
   - A read of a context value (`trace.Current`, `log.Annotation`; [runtime.md, G1](runtime.md#g1-context-through-with)) has empty rows but reads the running task through a host function, so it is opaque and its frame is impure. A `with` of a context value adds its operand's footprint and the footprints of its protocol calls, which can be impure even with empty rows: opening and restoring the region add no further effect.
   - The checker also records frame-local `Footprint.EntryPoll`: an impure frame polls at entry if its call-graph component has several members or a self-edge, or if its footprint is opaque, since unknown code may re-enter it. Opaque effects propagate through known calls; entry placement itself does not. Pure recursive frames get no poll. Only frames whose bodies were walked have a `Footprints` entry; lowering treats an absent entry as a checker bug, never as purity.
4. **Capability safety.** Only providers in host packages, and calls through `import go` that charge `go.Foreign`, call Go. A call into a package of the reviewed pure list (`v1.PureImports` less `v1.PureImportsExcept`) charges nothing; any other Go function or method, and a read of a host struct's field through a `go.Ref` or a borrow, charges `go.Foreign`, which only the entry provides (Entry 4; [interop.md](interop.md)). Ordinary code reaches the operating system only through a capability, so every effect appears in some footprint ([stdlib.md](stdlib.md#host-packages)). A host provider (`fs.Host`, `os.Host`) is made only by its package's `NewHost`, which needs the prelude's `Ambient`, and only the entry provides `Ambient` (Capability rows 4). So code that makes a host provider has `Ambient` in its row, or in an inferred row that reaches `main`; code that is given one, as a parameter or a capability, needs nothing (host-authority H1). The prelude's `LiveScheduler` is not under this rule yet (H2).
5. A function value whose row names a capability bound by `with` cannot escape that `with`. *Prior art:* Scala 3 capture checking and scoped capabilities; Effekt second-class blocks. A purity-carrying function type stays a candidate for [#189](https://github.com/cevr/ergo/issues/189).

## Context

Status: **checked** (#196): provider literals, closed named contexts, inline and local contexts (rule 9; check-v1 E5), embedding, `replace` and several keys in one entry. The build lowers each of them for a context of the program's own package (#199 stages 3b and 3c; `TestRuntime199ContextBuildProperty`, `TestErgoRunE5Contexts`) and for a context of an imported package (196b U4; `TestRunImportedContext`). A qualified embedding `context { b.W }` names the exported named context `W` of the imported package `b` and means what a bare embedding of a named context means: it brings `W`'s bindings, and a `replace` of the embedding context may override them. An unexported or a missing context of `b` is S104 at the name, "b.w is not an exported context of package b", and the embedding is a use of the import, so the import is not S110. Imports are acyclic, so an imported context is on no embedding cycle; the context pass reads its summary, made by its own package's pass, as one probe of the package's context budget (196b Q9; `TestQualifiedContextEmbed`). Constructors are **designed, not yet implemented**: S109 naming [#37](https://github.com/cevr/ergo/issues/37).

```go
let Live = context {
	Orders:    MemoryOrders{},
	Gateway:   FakeGateway{AuthID: "auth-7"},
	Scheduler: time.NewManual(0),
}
```

1. **Entries.** A `context` binds capabilities to providers, one entry per capability: `Cap: provider`. An entry naming a non-capability is S104. Context names are unique (S108). A second entry for a capability in one context, other than a `replace` of an embedded entry, is an error (S111; README Gap 28): two own entries of one capability, `replace` or not, are S111 "Store has a second entry in this context, entry 2; the first is entry 1", since a with binds each capability to one provider; a capability written twice in one entry names its two keys, "Store is listed twice in entry 1, as its keys 1 and 2". One entry may list several capabilities, `Clock, Scheduler: v`: one shared value that must implement each (README Gap 34). *Prior art:* Google Context rejects two providers of one type in a provider set.
2. **Providers (S106).** A provider literal's type must implement every method of the capability: the same name, the same parameter types, the same result and the same fallibility. Each error type of a provider method must be in the capability method's row: a provider may fail less, never more. A provider method that writes a capability row is wider than the capability method, which writes none (S106; README Gap 17).
3. **Inline contexts.** `context { A: X{}, B: Y{} }` appears only as a `with` operand or after `let x =` in a body (a local context, rule 9); anywhere else it is S108 "a context literal stands only after let x = or as a with operand". Its provider expressions are evaluated in the enclosing function, before the block's discharge, so their requirements and failures charge the enclosing function. A provider expression does not see the capabilities of its own context (fixture `context-sibling`, S102); it sees those of an enclosing `with` (fixture `context-order`), and those of the operands before it in one `with` (With 7). Its names are resolved where the literal is written; its capabilities are served by the `with` that builds it. For a local context these are two places: the `let` and the `with` (rule 9).
4. **Named contexts.** A named context is built by its own function at each `with` that names it, so its provider expressions do not see the caller's locals (fixture `named-context-shadow`). A named context is closed: its providers require no capability from the caller (S102) and let no failure escape (S101). It may use a capability it binds itself. Open named contexts are #37's (README Gap 6).
5. **Cycles.** A named context whose build can reach itself is an error (S108): a provider expression that enters it with `with`, a function or method a provider calls that does, a capability method whose provider in the package does, or an embedding. Entries of one named context whose providers use each other's capabilities (Context 4) form a cycle too, since none can be built first (S108, once per cycle). The checker follows every method of the called name for a call on a value of interface type, which over-approximates. On a reported embedding cycle, what an embedding of a context on the same cycle brings is no second entry (S111), against the context's own entries or its other embeddings, because it depends on how the cycle is fixed; a `replace` may still name it. The checker computes each context's bindings once, over the strongly connected components of the embedding graph, and checks each context body once for second entries (Context 1 and 7). A component's bindings are a persistent set that shares the largest of its parts (an entry set or an embedded component's bindings) and adds the others. Each element carries the entry that provides it, and a member's own entry is put over what an embedding brings (a `replace`), so the set is also the resolved bindings: the lowering reads them from the context (`Context.Provider`), every `with` of the context and every context that embeds it shares them, and nothing copies them per `with`. A `with` records only the capabilities its block's row needs from it (With 2), with the entries its discharge test found, so its record is bounded by its block. A body's check records what each `replace` overrides once per context (`Context.Overrides`), from the same lookups and collisions; an embedded context keeps its own. The proof is bounded (D16, amended for contexts in rounds 19 to 21) in two parts, both proportional to the package's context size (its context declarations and literals, their entries and embeddings, the capability names written in context entry keys and `needs` rows, plus one). Repeatable work, which can run more often than a fixed multiple of the context source it reads, is charged before it runs against one budget per package, 128 × the context size: a step is a set node read, copied or created, an element enumerated, a probe against a summary, an override recorded, or a sort's comparison or move, and a sort charges its whole bound, n⌈log₂ n⌉ comparisons and two moves per element and level, before it starts. Single-pass work, which reads each context node a fixed number of times (entries, keys, embeddings, the steps of the embedding graph's walk, each component's members, each root), is not charged; it is at most 12 × the context size. The pass does at most 140 × the context size work. The count follows the source alone, so a package's verdict does not depend on the machine or on time. Nor does it depend on the order of the declarations (round 15's rule; round 20): the pass runs once, before any body, over the named contexts in name order and then over the inline contexts grouped by the name of their top-level declaration; sets are keyed by the capabilities' qualified names; and every union keeps the larger side, the first of equal sizes in that order. An inline context's keys resolve in its body's scope, so the pass charges the most repeatable work its entries can do (per key, lookups as deep as the embeddings' union and the cycle's summary, and one step per collision) and checks them once, at the first check of the body. Past the budget, the context whose summary or body was being checked is S111 "this context's embedding graph is too large to check for duplicate entries; split it", at its name, or at each inline context of the declarations that share the name being checked; a context whose summary was not computed binds nothing and its dependents report nothing more from it (D3), so the checker never accepts a context it has not checked. An embedding chain whose every context adds an entry, a wide fan-in, an inline fan-in, an entry of 8000 keys and a replaced diamond of 8000 contexts each charge under 25% of the budget, 8000 empty contexts 31%, and the largest context of the corpus and examples under 4% (checker tests `TestContextBudget`, `TestContextBudgetPrefixes`, `TestContextSinglePass`, `TestContextBudgetOrder`, `TestContextBudgetHeadroom`; #196 rounds 17 to 21). *Prior art:* go/types orders package initialization over its dependency graph once (initorder.go); OCaml's `Set`, Erlang maps and Gleam's dicts share structure between versions; TypeScript's instantiation limit (TS2589) and rustc's `recursion_limit` refuse past a fixed count, as Totality 5 does for switches.
6. **Constructors (designed; S109 naming #37).** An entry may name a constructor: `Orders: OpenPostgres`. A constructor is an ordinary function. Its `needs` row is satisfied from the same context graph, and its error row joins the startup errors of every `with` that builds it. A constructor that returns a resource gives the context its release ([resources.md](resources.md#context)). *Prior art:* Effect `Layer.effect` and `Layer.scoped`; Google Context's generated constructor with cleanups in reverse order.
7. **Composition.** A context may embed another context by name. `replace Cap: provider` overrides an embedded entry; a second entry for one capability without `replace` is an error (S111). Two embedded contexts that bind one capability are S111 unless a `replace` entry of the embedding context, named or inline, overrides it; a `replace` of a capability no embedded context binds is S108. A shared node is built once per build, and each `with` is a new build. *Prior art:* Effect `Layer.merge`, `Layer.provide` and `Layer.fresh` (README Gap 22).
8. **Header (parsed; S109 naming [#196](https://github.com/cevr/ergo/issues/196) stage b).** A context literal may state what it exposes and what it requires: `let App = context provides Account | Invoice needs Config { … }`. Both clauses are optional, and `provides` comes first.
   - `provides A | B` lists the capabilities a `with App` discharges. An entry the context builds and does not list stays private to its build: `Store: MemoryStore{}` can serve `Account` and `Invoice` without reaching the `with` body. Without `provides`, every entry is exposed. `binds(W)` in [Composition laws](#composition-laws) is this list.
   - `needs C | D` lists the capabilities its providers require from the `with` site. They join that site's row (`needs(W)` in [Composition laws](#composition-laws)).
   - The parser and formatter implement both; the checker refuses them with S109 naming #196 stage b, which checks them. *Prior art:* Roc, where an app `provides` entry points to a platform that `requires` them; Effect's `Layer<ROut, E, RIn>`; OSGi's `Provide-Capability` and `Require-Capability`; Dagger's `@Provides` (README Gap 33).
9. **Local contexts (D-E5).** `let w = context { … }` in a body binds `w` to a local context. A local context is a recipe, not a value: it is the inline literal at each `with` that names it.
   - **Uses.** `w` is used only as a `with` operand or as an embedding entry of another context literal, inline or local (`context { w, … }`). Any other use is S108 "a context is used only by with or embedded in a context: with w { … } or context { w, … }": an argument, a `let` value, a return or tail value, a field, an element, an operand, a call, or a capture that is one of these. `let mut w = context { … }` and an assignment to `w` are S108 "a context is bound once by let; it is not reassigned"; a written type is S108 "a context has no type to write; bind it with let x = context { … }". A package-level named context cannot embed a local one (scope).
   - **Names.** `w` follows the binder rules of every local (D-D2). It may reuse a package context's name, and then hides it in its scope.
   - **Checked once.** Its provider expressions are checked once, at the `let`, in the `let`'s scope. The duplicate, `replace` and cycle rules (rules 1, 5 and 7) hold as for any context, and its summary is charged against the package's context budget (rule 5).
   - **Charged at each with (P4).** Each `with` that builds `w`, directly or through an embedding, charges the needs and failures of its provider expressions there, as an inline context's (rule 3), with one difference for needs. A need that no enclosing `with` provides and the function's written row does not declare is S102 at that `with` operand, the place the reader fixes. A need never widens an inferred row, where an inline context's need does ([Composition laws](#composition-laws), 9). A failure escapes to the function of that `with`. So `let w = context { Box: Holder{Value: read()} }` followed by `with A { with w { … } }` runs `read()` with A's `Store`.
   - **Built at each with.** A local context named by two `with`s is built twice: each `with` evaluates its provider expressions again, in entry order, with the values its locals hold at that `with`, and acquires and releases each resource provider once ([resources.md](resources.md#context), Context ownership). The lowering writes the provider expressions in place at each `with`: the recipe has no run-time value, closure or allocation (`TestLocalContextLowersInPlace`).

   *Prior art:* Effect's `Layer` and ZIO's `ZLayer` are recipes that `Effect.provide` and `ZIO.provideLayer` build where they are provided, and whose requirements are satisfied there; Gleam and Elixir pass dependencies as values, which can escape.

## With

Status: **implemented**: checked (#196) and lowered for every operand kind: a named, an inline or a local context (Context 9), a context value (rule 9; #199 stage 4a), its protocol functions generic or not (check-v1 E6b, `TestErgoRunGenericContextKey`), and several operands (rule 7; check-v1 E5, `TestErgoRunE5Contexts`). A `with` of an imported context, `with b.W`, and of a context that embeds one are lowered too: the providers are built and released as those of a named context of the program's own package are (196b U4; `TestRunImportedContext`). Rule 6's constructor startup errors for [#37](https://github.com/cevr/ergo/issues/37). An inline context whose entries are explicit provider expressions runs (#199 stage 3c; `TestRuntime199AcquireProperty`).

```go
let value = with Live { checkout(id) }
let local = with context { Orders: MemoryOrders{} } { report(id) }
let quiet = context { Log: Discard{} }
let both = with Live, quiet { report(id) }
```

1. `with W { block }` takes a context, named, inline or local, or a context value, and a block (S108 otherwise); `with A, B { block }` takes several (rule 7). An unknown context name is S104.
2. Inside the block, every capability that `W` binds is discharged: a charge of that capability does not reach the enclosing function's row. The checker records, for the lowering, each capability the block charges that this `with` discharges and the entry that provides it (the innermost `with` that binds it, rule 3), not every capability `W` binds.
3. **Nested `with`.** A `with` inside another keeps both scopes:
   - the inner context's provider expressions are evaluated in the outer scope, so they see the outer bindings; a local context's provider expressions too, wherever its `let` stands (Context 9);
   - an inner entry shadows an outer binding of the same capability for the inner body only;
   - each outer provider that the outer `with` builds keeps its own startup errors and its own release at the end of the outer block, even when an inner entry shadows it. An outer entry that no acquired provider reaches is not built ([resources.md, Context ownership](resources.md#context-ownership-as-built) 1).

   Measured (fixture `context-order`, output `outer inner`):

   ```go
   with context { Store: Holder{Value: "outer"} } {
   	with context { Store: Holder{Value: "inner"}, Box: Holder{Value: read()} } {
   		Console.Println("\(Box.Get()) \(Store.Get())") // read() saw the outer Store
   	}
   }
   ```

   Flattening the two into one context `context { Store: Holder{"inner"}, Box: Holder{read()} }` changes the program: `read()` would need `Store` from its own context, which is S102 (fixture `context-sibling`).
4. `with context {}` binds nothing and keeps the enclosing bindings (fixture `empty-context`).
5. When the `with` is used as a value, the block's value is its last expression statement; a `with` used as a statement needs none: its block's call tails are discarded, whatever their types, and a pure value tail is S110 (Totality 3, the statement-position rule). A `return` in the block returns from the function after the `with`'s providers are released, innermost first, and before the function's exit actions; `break` and `continue` cannot leave the block (S108; [grammar.md](grammar.md#statements) rule 5). Locals declared in the block are scoped to it.
6. A `with` expression is fallible when its last expression is fallible. A failure that a `try` in the block escapes goes to the enclosing function. Designed: the startup errors of the context's constructors join the `with` expression's row.
7. **Several operands (D-E5).** `with A, B, …, Z { b }` is `with A { with B { … with Z { b } … } }`, for every operand kind in any position, with no limit but the source and the package's with budget (rule 10). So B's provider expressions see A's bindings; where A and B bind one capability, B's binding wins in the block. A's provider of that capability is built and released only when the `with` acquires it: when a provider that B builds, or another provider of A that the `with` builds, uses it ([resources.md, Context ownership](resources.md#context-ownership-as-built) 1). Otherwise it is not built and not released: `with a, b { Store.Get() }`, where `a` and `b` each bind `Store`, builds and releases only `b`'s `Store`, as the nesting does (`TestErgoRunE5Contexts`, shadowed-unbuilt). Each operand's failures, needs and acquisitions are the ones its nested `with` would have, and the checker records one fact per operand, in operand order (`With.Next`). *Prior art:* Python's `with a, b:` is `with a: with b:` (PEP 343).
8. **Lowering.** `with` copies the environment and sets the context's fields inline, with no closure. A named context is its own Go function; an inline or a local context writes its provider expressions in place. Several operands lower as their nesting, one Go block per operand.
9. **Context values (G1).** `with v { block }` also takes a context value, whose type satisfies the context-binding protocol (`contextKey(v) string` and `contextText(v) string` on the type, with empty rows): `with trace.Span("ingest"), log.Annotate("region", "eu") { … }` ([runtime.md](runtime.md#g1-context-through-with)). The operand is checked as an argument, in the frame around it (the enclosing frame, or the operands before it), so its failures and capabilities are that frame's. A context binding discharges no capability: the block's rows are the enclosing ones. An operand that is neither a context nor a context value is S108. The checker records the binding and its protocol functions for the lowering (`With.Value`).
10. **With budget (D16; #229).** Inside a body, the checker keeps one map from each capability to the innermost `with` that binds it, so a charge costs O(log n) whatever the number of `with`s around it. A `with` operand adds its context's bindings to that map. This costs O(log n) when the context's bindings and the map's differ in a few capabilities, as for a chain of contexts that each embed the one before, or two such chains in turn (`TestWithSiteWorkLinear`). It costs O(m log n) when m bindings change their `with`: `with A, B, A, B, …` of two large contexts whose capabilities interleave, or `with Z1, …, Zn` where each `Zi` embeds one large context. That work is charged against a budget per package, 16 × its source bytes + 65536 steps. Past it the checker stops computing the map: the first operand past the budget is S102 ([diagnostics.md](diagnostics.md#s102-missing-capability)), and it and every later operand whose push needs work discharge everything, so nothing cascades (D3). The checker never accepts a program whose `with` scopes it did not compute. *Prior art:* the context budget (Context 5) and the match budget (Totality 5); TypeScript's TS2589.

*Prior art:* Effect `Effect.provide` with a layer; Go `context.WithValue`; Java `ScopedValue.where(…).run(…)`; Gleam has no provision construct, and dependencies are passed as arguments.

## Totality

Status: **implemented**: checked (#196) and lowered (check-v1 stage C): every pattern form, several subjects included, runs under `ergo run` (`TestErgoRunPatterns`), and a tuple pattern matches a type defined over a tuple (check-v1 E6b, `TestErgoRunDefinedTuple`).

1. **Patterns** (check-v1 D-B3, 196p). A `match` takes a subject of any type, and its cases list patterns ([grammar.md](grammar.md#expressions), Expressions 6): `_`; a name, which binds; a literal (an integer, rune, string or `bool` constant, typed by the subject; a float or duration pattern is S108, test with `if`); a type, which tests the variant of a union subject or is the subject's own type (any other type is S108); a record pattern `T{F: p, …}` with keyed field patterns, or one positional pattern for a one-field record (an unknown field is S104, a field twice S108, and `T{}` is S108 "write case T:"); a tuple pattern `(p, q)` of the subject's arity; and `p as x`. A name that names a type or a constant is that pattern; a name that names a function, a package or a package value is S108 ("a pattern name binds"); any other name binds, and a capitalised name that binds gets a hint in its S110. A name is bound at most once in a pattern (S108), and every pattern of a case binds the same names (S108). **One rule for a name bound at several types** (fu8a; q39): when the patterns of one case, in a match or a catch, bind a name at different types, it binds at their join. Types that are each a failure of the caught row, or a variant of a matched row value, join to the row value of those failures (the type `case err:` gives them, [Catch](#catch) 7): `case NotFound as e, Denied as e:` binds `e` as the row value `NotFound | Denied`, which can be returned, matched, caught, or passed where a declared union that lists both is expected. Other types join by the branch join of rule 3: to a declared union that is one of them and lists the others, else to the one declared union that lists each (`case Circle as c, Square as c:` binds `c` as `Shape`). With no join it is S108 at the binding, naming the two types. The lowering declares the binding at the join's Go type, an interface each alternative's value satisfies, so no conversion runs. *Prior art:* OCaml and Rust require each side of an or-pattern to bind a name at one type (Rust E0308); OCaml's polymorphic variants bind `#t as x` at the union of the matched tags, and TypeScript narrows to the union of the tested members, which is the row-value case here. A row value type is not yet written in a signature (that is q47's row-field unit), so a function that takes the binding names a declared union that lists the failures. A binding its arm never reads is S110. A match on an operation-type value admits only `_` and bindings: Ergo has no type assertions (S108). A case that earlier cases cover is unreachable (S108), including `case _`. When one earlier case covers it, the message names that case's pattern. A refused pattern name binds an invalid placeholder, so later uses add no diagnostic. *Prior art:* Gleam, ReScript, OCaml and Rust patterns mirror construction; Elixir matches structs by name.
2. **Totality rule (S103; README Gap 3; check-v1 D-B4).** A `match` names every constructor or has a covering case: the constructors of a union are its variants, nested through record patterns; of `bool` its two constants; of a tuple the product of its elements'; of a non-union record its one shape. Constants of other types never cover (S103 "constant patterns never cover int; add case _"). A match that misses a case is S103 at `match`, naming one missing pattern (`no case handles Declined{Reason: CardExpired}`). *Prior art:* Gleam, Rust and Swift reject a non-exhaustive match; OCaml warns (warning 8); Go accepts one.
3. **Tail results and missing return (S107; 196r, check-v1 D-C1 and D-C2).** A body yields its last expression: a function body, an `if` or `match` arm, a `catch` arm, a `with` block and a trailing block; `return e` leaves early and means the same as a tail `e`, so a fallible tail's failures escape and a tail value of an error type is a failure. That failure is ambiguous when the function's one result is a union that has the error type as a variant beside a variant that is no error type, and the function's row does not declare the error type: S101 at the value says both spellings, `let v Signal = WrongCode` then `v` for the value, and the error type in the row for the failure, and the value is read on as the result, so no caller gets a failure that was not meant (lane MB F3; `TestAmbiguousTailFailure`). A row that declares the error type chose the failure, so it is quiet. Elsewhere (a `let`, an argument, a branch of a `let`'s value) a value of an error type is a value of the expected type. A final `if` with an `else` and a total `match` yield through their branches, in every position: `let s = if c { 1 } else { 2 }`, `1 + match p { … }`, an argument. With an expected type every branch is assigned to it; without one the branches have one type, the first branch's, and later literals take it, except that branches that are variants of one union, or that union, join to the union (K3, owner decision O6 by principle): `match s { case "open": Open case _: Closed }` is a `State`, `if c { Some{Value: n} } else { None }` is an `Option[int]` (a generic union takes its type arguments from the branches), and branches of one variant keep the variant. The union is the branch that is a union, else the one union declared in the variant's package that lists every branch; when two unions list them there is no join, and `let s State = if …` writes the one meant (`TestUnionJoinTable`). A `let mut x = None` that a later assignment gives another variant is S108 "x is typed None by its value; write let mut x Option[int] = None". *Prior art:* Rust, ReScript, Gleam and OCaml type a constructor as its enum's type, so branches always join; TypeScript joins to a union of the branch types. A branch that ends in `return`, `break` or `continue` has no value and joins any type. A body that needs a value and whose path ends in a statement (a `let`, an assignment, a `for` that can exit, an `if` without `else`) is S107 at the body's closing brace; an `if` without `else` in a value position is S108 "a value if needs an else". A body with no result discards its tail, and the tail position reaches through its final `if` and `match`, under the statement-position rule below. A `with` block whose value is used and a trailing block whose result is inferred yield a value when every path does, of the first value's type. A path of a used `with` block that has no value is S107 at the block's closing brace, as in every other body that yields a value (stage C round 2 review O1); a trailing block whose result is inferred yields no value when a path has none, and the call that uses it reports (review M4). A `with`, `try` or `catch` whose value is discarded (an expression statement, the tail of a body with no result) is a body with no result for its block or arms (review m4). **One statement-position rule** (stage C round 3 review m2), for an expression statement and for the tail of every body with no result, in every body kind: an `if` or `match` arm, a `with` block, a trailing block, a `catch` arm, a function body. A tail that is a call, a `try`, a `catch` or a `with` has its result discarded, whatever its type, so `if c { f() } else { g() }` is a statement when `f` and `g` return different types. A tail that is a pure value, decided by its top-level form (a literal, a name, an operator or a conversion: `1`, `x`, `!c`, `f() + 1`, `int8(n)`), is S110 "this value is not used". A conversion is known by the call's resolved kind, not by its spelling, so `N[int](n)`, `(T)(x)` and `pkg.T(x)` are conversions too (stage C round 4 review M1); a conversion to an error type that ends a function body is a failure (Error rows 4), not an unused value, as Go reports an expression statement that is not a call ("evaluated but not used"). A body with no work is empty: `if c { } else { f() }`, `case 0:` with no statements, `case E:` with no statements in a `catch`, `with W { }`. A `break` inside a match leaves the enclosing for and makes that loop able to exit. A nested for owns its own breaks.
4. **Total catch.** See [Catch](#catch), rule 4.
5. **Multi-subject match (README Gap 12).** `match (s, e)` with tuple cases is total over the product of the unions; `_` matches any variant. The checker decides totality by a usefulness check over the case matrix (Maranget), never by enumerating the product, and names one missing tuple (S103). The proof is bounded (D16, amended for sparse matches): the solver splits on the column that most rows need (Maranget's necessity heuristic, ties broken by the column's source position), memoizes each residual matrix, and counts its steps, and every other superlinear pass over the case matrix, against source limits shared by reachability and totality: max(200,000, 512*W) work steps and max(200,000, 1024*W) allocated cells, where W is the number of syntax nodes in the written patterns plus the number of subjects (a default contributes one node). Thus both fit max(200,000, k*W) with k=1024; the work limit is stricter. The 200,000 floor is unchanged. Unwritten fields are implicit wildcards: they create neither columns nor index entries. Only fields some pattern writes need columns. Steps count construction, prepaid sorting, specialization, candidate comparisons, residual keys and witness copies. Allocation cells count container slots and key storage, with allowances for growth and copying; every proof allocation reserves its cells before it runs. Pattern keys name immediate children by identity; they never expand every descendant into every ancestor's key. Residual keys contain interned sparse row identities and no list of remaining columns; unchanged row storage is interned once. The solver is deterministic for a given source. Reordering the subjects may change whether a switch near the budget is refused; it never changes a proved verdict. A completed totality proof is decided over the maximal case rows, so its answer does not depend on the order of the cases. A `case _` covers every remaining value, but its own reachability still needs a proof under the same budget. A default-only match costs linear work in its subjects. A case resolves to its variant by instance identity (D16 as amended in round 8): the union's variant index is a discrimination tree over the variants' types, built once per origin union and shared by every instance of it, with every edge hashed (D16 as amended in round 9): a constructor edge by its constructor, a variable edge by its declaration parameter, reached through the instance's type arguments indexed once by identity, and a row that mentions a parameter (`fails E`) by its pattern, reached through the instance's bound rows indexed once by identity. A case follows its own path, so it resolves without scanning or substituting the variants that share its origin, and resolving the cases is linear in the variants and the cases, for shared origins, variable edges, row-bearing signatures, generic unions and tuple cases alike. Every type has one identity, a hash-consed id: its constructor plus its children's ids, one hash lookup per node, so equal structures share one id. The checker compares types, caches generic instances and indexes rows and variants by that id, never by a serialized type (round 11); interned types never change, an inferred row being a variable solved beside the type (round 12), and the bound identities and rows of an instance are indexed once and shared by every switch subject of that instance (round 10). As a safety net, every operation of resolving a switch's cases, each type node it interns and each row operation included, is charged to that switch's step counter in proportion to its size, and every insertion into the index to the union's own counter, against its deterministic resolution budget; past it the switch is S103 "too many cases to prove this match total; split it or add case _", so no uncounted pass runs before the solvers. Reachability (S108, a case the cases before it cover) follows the cases' order by definition and shares the source proof budget with totality. A switch over a work, allocation or resolution budget is S103 ("too many cases to prove this match total; split it or add case _", or "… which cases of this match are reachable; split it"); the checker never accepts a switch it has not proved. Every switch of up to 6 subjects of up to 3 variants stays far below the budget. *Prior art:* rustc's `pattern_complexity_limit`, OCaml's Parmatch, GHC's `-fmax-pmcheck-models`.
6. **Irrefutable `let` and `for` patterns** (check-v1 D-B5; 196v amended rule 4). `let P = e` and `for P in xs` take a pattern that covers every value of its type: a record pattern of the value's own type, a tuple, or a name. Binders outside match and catch follow D-D2: a local may reuse a package-level name except a prelude name. Thus `let helper = 5` binds over a package function, as a parameter named `helper` does; rule 1's package-value and function-name S108 applies to match and catch arms. A bare name of a package type in a body's let or for pattern binds too, as in Go, and type positions still see the type ([types.md](types.md#scope) 1; L5, which replaced the rule that such a name tests the type); in a package-level let's pattern it still tests the type. A bare prelude name in a let or a for pattern is a binder that D-D3 refuses: `let true = false` is S108 at `true`, and `true` still binds, with the value's type, for the rest of its scope. Other refutable patterns are S103 "this let pattern does not match Pending, a value of Payment: a let pattern matches every value; use match". A refused type-test name binds an invalid placeholder. A refused binder (that placeholder, or a binder with its own diagnostic, such as D-D3's) changes no other verdict ([diagnostics.md](diagnostics.md), D3): (P1) a read of the name in a value position, in the binder's scope, adds no diagnostic; (P2) everywhere else, a type position, a later pattern, a later binder, a later type test, the name means what it would mean without the refused binder and gives the diagnostics it would give then, so a placeholder is never a binding that a later binder shadows, and a pattern never classifies a name by it; (P3) typing and the reference walk give each identifier one meaning; (P4) a type whose declaration is refused (an invalid underlying type, a union that lost every variant) adds no diagnostic where it is used, in a pattern, a literal, a binder or a read. The solver uses the same source budget as a match; a proof past it is S103 "too many cases to prove this let pattern irrefutable; split it" (or "for pattern"). A package-level `let P = e` is checked once for all its names, and lowers to one Go variable for the initializer, evaluated once, and one Go package variable per binding read from it, so Go's reference order initializes it before every binding and every binding before its readers (review M5). Stage D enforces D-D2 for single-name loop binders too. *Prior art:* Rust's `let` resolves type paths but binds over functions (E0005 for refutable patterns); Gleam requires `let assert` for a partial pattern; MoonBit's `let` takes irrefutable patterns; Elixir's `=` raises `MatchError` at run time.

## Composition laws

Status: **designed**. These laws state the algebra of the row constructs. Law tests ([types.md](types.md#laws)) will check them.

| Composition | Error row | Capability row |
| --- | --- | --- |
| `a; b` (sequence) | `rows(a) ∪ rows(b)` | `needs(a) ∪ needs(b)` |
| `try e` | escapes `rows(e)` | `needs(e)` |
| `e catch { case T: h }` (total) | `rows(h)` | `needs(e) ∪ needs(h)` |
| `try e catch { case T: h }` | `rows(e) − {T} ∪ rows(h)` | `needs(e) ∪ needs(h)` |
| `with W { b }` | `rows(b) ∪ startup(W)` | `needs(b) − binds(W) ∪ needs(W)` |
| `timeout.After(d) { b }` | `rows(b) ∪ {timeout.Expired}` | `needs(b) ∪ {Scheduler}` |

1. **Wrapping.** Moving a body into a function `f` and calling `f()` changes no row, provided `f` declares the body's rows. Ordinary functions wrap every construct losslessly.
2. **Nesting keeps both scopes.** `with W1 { with W2 { b } }` is not, in general, one `with` of an overlaid context: `W2`'s initializers see `W1`'s bindings, and `W1`'s providers keep their startup errors and releases ([With](#with), rule 3). The body `b` sees `W2`'s entries over `W1`'s.
3. **Overlay is a law of context declarations only.** `let Test = context { Live, replace Orders: MemoryOrders{} }` is `Live` with the `Orders` entry replaced: the replaced constructor is never built, so its startup errors and release leave `Test`. *Prior art:* Effect's `Layer.provide` against `Layer.merge` keeps the same distinction between nesting and composition.
4. **Capability rows of nesting.** In `with W1 { with W2 { b } }`, the body `b` has `binds(W1) ∪ binds(W2)` discharged. `W2`'s own needs are checked against `W1`'s bindings and the enclosing function, not against `W2`.
5. **Row idempotence.** `with W { with W { b } }` has the rows of `with W { b }`. It still builds `W` twice, once per `with`.
6. **Identity.** `with context {} { b }` has the rows of `b`.
7. **Catch subtraction.** A partial catch that names every type of `rows(e)` has the rows of the total catch. A `try` over it has nothing to pass on, so it is a redundant `try` (S108, Catch 5).
8. **Several operands are the nesting.** `with W1, W2 { b }` is `with W1 { with W2 { b } }`, with the same rows, the same diagnostics and the same facts, for every operand kind ([With](#with), rule 7; `TestSeveralOperandsAreNesting`). Rules 2 and 4 hold for it; it is not an overlay (rule 3).
9. **A local context is its literal at each with.** After `let w = context { … }`, `with w { b }` has the rows of `with context { … } { b }` written at that `with`, where the literal's names mean what they meant at the `let` ([Context](#context), rule 9; `TestLocalContextChargeSite`). So `needs(w)` charges at each `with` of `w`, and each `with` builds `w` again. One exception: in a function whose capability row is inferred, a need of `w`'s providers that no enclosing `with` provides is S102 at the operand, but the same need of the inline literal widens the inferred row (Context 9: a need of a local context never widens an inferred row; `TestLocalContextLawNine`). The law holds in every function that writes its capability row.
