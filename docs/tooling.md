# Developer tooling

Every `ergo` command reads one `.ef` source through one front end, `internal/sketchfront`, which checks, formats and builds the language of [`docs/spec/`](spec/README.md). There is no manifest and no edition. One table in `cmd/ergo/commands.go` gives every command word one fate, and dispatch, `ergo --help` and the stubs read only that table.

| Command | Fate | Output and exit |
| --- | --- | --- |
| `check FILE\|DIR [--target go]` | Runs | The check envelope as JSON; exit 0 when the source checks, 1 when it does not |
| `diagnostics FILE\|DIR [--strict] [--json] [--target go]` | Runs | One finding per line, or the diagnostic report as JSON; exit 0 when policy passes, 1 when it fails, 2 for an invalid invocation |
| `build FILE\|DIR [-o PATH] [-work] [--target go]` | Runs | Builds a native executable, `dist/NAME` by default (NAME is the file's name without `.ergo`, or the folder's name), and prints its path; a source that does not check prints its check envelope and builds nothing |
| `run FILE\|DIR [--target go]` | Runs | Builds, then runs the program; SIGINT and SIGTERM are forwarded and the program's exit status passes through; a program that a forwarded signal ends exits 128 plus the signal number (130 for SIGINT, 143 for SIGTERM), with no message of `ergo`'s own |
| `fmt FILE... [--check] [--json]`, `fmt --stdin` | Runs | Canonical formatting; files are replaced atomically |
| `test FILE\|DIR [--seed N] [-work] [--target go]` | Runs | Builds the test binary into a private temporary directory and runs it: one `ok` or `FAIL` line per test in source order, then `PASS (N tests)` and exit 0, or `FAIL (K of N tests)` and exit 1; a defect stops the run with exit 2. `--seed N` (or `--seed=N`, a decimal number) replays a property's cases; a malformed seed is an invalid invocation, exit 2, and runs nothing. Signals are forwarded as for `run` |
| `edition` | Removed | `removed in v1; there is one language and no editions (#205)`, exit 1 |
| `lint`, `lint rules`, `lint test`, `lint receipt` | Removed | `removed in v1; linting returns on the new checker (#203)`, exit 1 |
| `inspect`, `explain`, `query`, `type`, `graph` | Removed | `removed in v1; semantic tooling returns on the new front end (#203)`, exit 1 |
| `lsp`, `mcp` | Dark | `unavailable until ported to the new front end (#203)`, exit 1 ([language server](lsp.md), [MCP](mcp.md)) |

A command that does not run prints one line to stderr, `ergo NAME: ` and the text in the table, prints nothing to stdout and exits 1, before it reads its arguments: `ergo inspect --help` prints the stub too. `ergo --help` lists only the commands that run. An unknown word is `unknown command X; use ergo --help`, exit 1. The [retirement record](receipts/retire-ef.md) lists what [#203](https://github.com/cevr/ergo/issues/203) restores.

Go is the only target. `--target` accepts only `go`, the default; any other value is the EF110 refusal. `--strict` and `--json` belong to `diagnostics`, `-o` to `build`, `-work` to `build` and `test`, and `--seed` to `test`; any other option is unknown: exit 2 for `diagnostics`, `fmt` and `test`, exit 1 for `check`, `build` and `run`.

## Source admission

A command locates its source once (`internal/receipt.LocateSource`): the spelling is made absolute, which applies a `..` to the spelled name, and the links of that admitted path are then resolved. Diagnostics and `//line` directives name the admitted path; the bytes come from one non-blocking open of the resolved file (`internal/source.Open`), which refuses a directory, a FIFO or any other file that is not regular, so a FIFO swapped in after a stat never blocks. A source must have the `.ef` extension. An `ergo.json` beside a source is ignored.

A path that names a folder, and does not end in `.ergo`, is a package (196b U3; [grammar](spec/grammar.md#source-files) rule 1): the loader (`internal/sketchfront`, `CheckDir`) finds the nearest `ergo.mod` at or above it, reads every `.ergo` file of the folder in name order, and reads the local packages it imports, each once. Each finding then names its file relative to the module root: `lib/x.ergo:2:9: error S104: …` in text, and a `file` field in the check envelope and the report (omitted for a program of one file; additive). The build key holds a digest of each local package the program reaches, by admitted path and bytes, so an edit of an imported package builds again. `ergo test DIR` runs the tests of that package only, as `go test` does. A file path keeps its one-file meaning: such a program imports std only.

## Check envelope

`ergo check` prints one JSON object: `schemaVersion` (10), `checked`, `target`, `revision` (a SHA-256 digest that identifies the source), `diagnostics` (at most 100, each with `code`, `message` and a UTF-8 byte `span` with one-based line and column), `diagnosticsTruncated`, the `producer` that made the facts, and the `snapshot` that binds the schema, revision, target and producer together. Producer identity follows the executing artifact: its digest when the executable can be read, and a process-scoped qualifier when it cannot. `ergo build` and `ergo run` acquire a producer identity only when they refuse a source. The emission cache keys on its own digest of the compiler executable, which needs no producer identity ([runtime.md](spec/runtime.md), Host and lowering notes).

## Diagnostic reports

`ergo diagnostics --json` prints the report (`schemaVersion` 2). Its `source` identifies the file with a canonical escaped `file:` URI and the origin `disk`. It includes the source `revision`, the `target`, the `checked` state, the `strict` policy, `policyPassed`, exact `totalCounts` and `returnedCount`, `truncated`, the `producer` and `snapshot` of the check envelope, and the findings. Every finding keeps its UTF-8 byte `span` and reports `code`, `origin`, `severity` (`error`, `warning`, `information` or `hint`) and `message`. A finding with a source location also has a zero-based UTF-16 `lsp.range`; `locationAvailable` is false for a finding without one, such as the unsupported target refusal.

**Finding order.** The report lists its findings, in JSON and in text alike, in this order: findings with a location first; then by `file` (byte order of the path relative to the module root, the empty `file` of a one-file program first); then by byte `offset`, span `length`, `code` and `message`. A finding without a location comes last. Identical findings (same code, file, message and span) are listed once. So the findings of one file of a package are never interleaved with another's (`internal/report` `TestReportOrdersFindingsByFileThenOffset`).

Errors always fail policy. Strict mode changes only the policy decision for warnings; it does not change a finding's severity. Text output prints one finding per line with one-based UTF-16 lines and columns. Exit 0 means policy passed. Exit 1 with a JSON report on stdout means the source failed policy; exit 1 without a report is an operational failure, explained on stderr. `ergo diagnostics --help` documents the same.

## Formatter

`ergo fmt` formats with the one formatter and reports one formatter identity, at the top level and per file. `--stdin` writes only formatted source to stdout. Human file statuses and operational errors go to stderr. File `--json` and `--check --json` reports use stdout and keep stderr empty; `--stdin` with `--json` is an invocation error. Exit 0 means formatting completed (or the check found no differences), exit 1 means the check found differences, and exit 2 means an invocation, syntax, I/O, stale-source or limit failure.

| Boundary | Limit |
| --- | ---: |
| File count | 100 files |
| Input per file | 2 MiB |
| Input per request | 8 MiB |
| Formatted output per file | 4 MiB |
| Formatted output per request | 16 MiB |

Completed file entries include `path`, `requestedPaths`, digests, `changed`, `written` and `completed`; a failed entry never receives a successful human status. The stable operational codes are:

| Code | Meaning |
| --- | --- |
| `EFMT_INVOCATION` | Incompatible options, missing input, or file-count admission failure |
| `EFMT_PATH` | Empty, non-`.ef`, or otherwise invalid path |
| `EFMT_READ` | The source could not be admitted or read |
| `EFMT_SYMLINK` | A mutating request named a symlink leaf |
| `EFMT_SPECIAL_FILE` | A directory, FIFO or other non-regular source |
| `EFMT_INPUT_LIMIT` | A per-file or aggregate input budget is exceeded |
| `EFMT_OUTPUT_LIMIT` | A per-file or aggregate formatted-output budget is exceeded |
| `EFMT_SYNTAX` | The source does not parse |
| `EFMT_FORMAT` | Any other formatter failure |
| `EFMT_ALIAS` | Several requested names resolve to one underlying inode |
| `EFMT_STALE` | The source identity or exact bytes changed before replacement |
| `EFMT_WRITE` | A temporary-file, permission, rename or other replacement failure |

Mutating paths keep the requested display spelling while the operating system resolves ancestor symlinks and `..` components. The leaf must stay regular and not a symlink at each replacement check. Lexical spellings that resolve to the same path are deduplicated; distinct hardlink or inode aliases in one request are rejected. A requested hardlink is replaced through an atomic same-directory rename, so that directory entry splits from unlisted hardlinks. A read-only regular file may be replaced when its directory is writable, and its permission, setuid, setgid and sticky bits are kept. These cooperative checks do not claim hostile-filesystem race protection or directory-fsync durability.

The formatter does not refuse invalid UTF-8. It formats such a source and writes the invalid bytes of comments and string literals back unchanged; an invalid byte where an identifier may start is the parse error S001, `EFMT_SYNTAX`. The earlier front end refused every invalid byte with EF001.

## Gate prerequisites

The gate needs Go and Git. It needs no Node, Bun, TypeScript or Effect installation: since 2026-10-26 Go is the only target.

## Merge gate

`scripts/gate.sh` runs `go run ./scripts/gate`, a small Go runner that owns the check graph ([design and measurements](research/gate-throughput.md)). Every check is a step with declared dependencies. Independent steps run concurrently. Each step's output is printed whole, in declaration order. A failing step fails the gate and blocks only the steps that depend on it. `--list` prints every step and its command, `--no-cache` runs every step without whole-gate records or step receipts (Go's test cache still applies to the hermetic step, below), `--merge` runs the merge tier (below), and `--record-durations` re-measures the slow Go packages.

- **Memory budget.** Every step runs under a hard memory cap that covers the step and every process it starts: `ERGO_GATE_STEP_MEMORY` (default `8G`) per step, `ERGO_GATE_MEMORY` (default half of physical memory, in whole gigabytes) for all the steps of one gate together, and the bound of the gates' slice for all the gates of the host together. `ERGO_GATE_HOST_MEMORY` (default three quarters of physical memory) lowers only this gate's own budgets to it; it never changes the slice's bound. Go processes in a step get `GOMEMLIMIT` at 3/4 of the step cap unless the caller set `GOMEMLIMIT`. `--record-durations` runs its packages under the same budget.
  - *systemd scope (Linux with a working `systemd-run --user`).* The gate runs itself in one transient scope in the user slice `ergo-gates.slice`. The scope has `MemoryMax` = gate budget + 512M for the gate process itself, and `MemorySwapMax=0`; the swap setting holds for every cgroup below the scope. The gate moves itself to a `gate` leaf, and every step runs below a sibling `steps` cgroup with `memory.max` = gate budget. So when steps reach the step or gate budget, the kernel's out-of-memory killer chooses among the steps' processes and never the gate, even when a stopped step's memory is not yet freed. (The kernel chooses a victim by size and `oom_score_adj` alone; `memory.min` and `memory.low` do not change the choice, and an unprivileged gate cannot lower its own `oom_score_adj`.) The gate reads both bounds back before every step and refuses to start a step without them. If a named scope cannot set them up, the gate fails instead of switching to the RSS watch. The slice's `MemoryMax` belongs to the host: a gate sets it only when the slice has none, and then only to the default, three quarters of physical memory (a runtime setting, which every gate writes alike). A gate never lowers or raises a set bound, so one gate's `ERGO_GATE_HOST_MEMORY` cannot stop another gate. To change the bound for every gate, set it on the slice: `systemctl --user set-property --runtime ergo-gates.slice MemoryMax=<size>`. When the bound is below this gate's budget, the budget line says so (`…, 24G across gates in ergo-gates.slice, below this gate's 31G`). Each step starts in its own cgroup below `steps` with `memory.max` = step budget and `memory.oom.group=1`, so an out-of-memory kill stops the whole step. When the gate or host budget is reached, the kernel stops the largest process under it, and it can stop two steps when the first one's memory is not yet freed. The gate waits for the kernel's `cgroup.events` `populated 0` state before finishing step cleanup and draining output. The gate reads the step's `memory.events` (and the `memory.events.local` of `steps` and of the slice) to say which budget stopped it. A gate started inside another gate's step opens no scope: the outer step's caps hold, and it watches its own steps' RSS.
  - *RSS watch (darwin, a container, no user bus, or `ERGO_GATE_MEMORY_MECHANISM=rss`).* Each step runs in its own process group, and the gate samples resident memory every 250 ms. It stops a group over the step budget, and the largest group when the sum passes the gate budget. A fast step can pass its budget between two samples: peaks of 639.9M to 724.5M under a 512M budget were measured (up to 41% over). This mechanism has no bound across gates, and a process that leaves its step's process group leaves the watch.
  - The gate prints the mechanism once (`gate: memory budget: systemd scope 8G per step, 31G per gate, 47G across gates in ergo-gates.slice`). A step over its budget fails with `memory budget exceeded (<budget>)` (`gate memory budget exceeded`, `host memory budget exceeded` for the larger caps) and its output, and is never recorded as passed. The other steps keep running. Each step line reports its peak memory. Do not cap the gate with `ulimit -v`: Go reserves far more address space than it uses.
- **CPU budget.** A gate uses at most its CPU budget, `ERGO_GATE_CPUS` (default half of the usable CPUs, at least 2; never more than the usable CPUs). The usable CPUs are the CPUs of the gate's affinity mask (`taskset`), lowered to the tightest `cpu.max` of its cgroup and every cgroup above it, rounded up; not the host's CPU count. A value that is not a positive whole number fails the gate before it starts, with one line (`gate: ERGO_GATE_CPUS: "x" is not a positive whole number of CPUs such as 4 or 8`). The budget bounds how many steps run at once, the shards of a package (below), the host packages' `-parallel` (at most 8), the gate's own `GOMAXPROCS`, and the `GOMAXPROCS` of every step's Go processes: the caller's `GOMAXPROCS` when it is a whole number within the budget, else the budget. It also bounds the go command's `-p` (`stepGOFLAGS`): the gate appends `-p=<n>` to every step's `GOFLAGS`, after the caller's flags, where `n` is the caller's last `-p` when it is a whole number within the budget, else the budget. cmd/go applies `GOFLAGS` in order and the last value wins, so a caller's `GOFLAGS=-p=16` cannot raise it; every go command a step starts inherits it. A test binary's `-parallel` defaults to `GOMAXPROCS`, so it follows the budget. Each step's receipt key holds the budget, so a step's pass under one budget is not replayed, or promoted into a whole-gate record, under another. The gate passes `GOMAXPROCS` explicitly because Go's runtime reads only the `cpu.max` of the cgroup its process is in, and none in the merge tier's sandbox, which has no `/sys`: there a Go process without it took all 16 CPUs of this host (measured 2026-11-05).
  - *systemd scope.* The kernel also enforces the budget. The scope has `CPUQuota=<budget × 100>%`, and the gate checks that the scope's `cpu.max` reads back as the budget; else it fails before any step, as it does for the memory bounds (`gate: cpu budget: systemd scope <unit> does not enforce the CPU budget: …`). Each step's cgroup has `cpu.max` at the budget too, so a Go child that drops `GOMAXPROCS` still sees the budget (Go's runtime never sets fewer than 2). The merge tier's sandboxed steps run in the same step cgroups. The gate prints the budget once (`gate: cpu budget: 8 CPUs, systemd scope CPUQuota=800%, cpu.max 800000 100000 per step`).
  - *Elsewhere* (RSS watch, darwin), the budget bounds the steps at once and `GOMAXPROCS` only (`gate: cpu budget: 8 CPUs, steps at once and GOMAXPROCS (no cgroup)`).
- **Step lifetime and temp files.** After a step leader exits, the gate stops the remaining members of its process group or systemd cgroup before finishing output. The RSS watch waits until no process of the group can hold the output pipe: a zombie leader whose other threads still run (`Zl` in Linux `ps`) still holds it, and a zombie without threads does not. Its leftover diagnostic names live processes only. The systemd path waits for `cgroup.events` to report `populated 0`. It drains buffered output without waiting for an outside writer; a process that still holds a pipe makes the step fail with a diagnostic. Each step gets a stable per-checkout, per-step `TMPDIR`, protected by an exclusive file lock across gates. The gate restores directory permissions and empties the directory before launch and after the step stops.
- **Scope setup comes first.** In its systemd scope the gate opens its limiter before it starts any process: it moves itself to the `gate` leaf and enables the controllers for the scope's children, and only then runs git and `go list ./...` to find the checkout and declare the steps. The kernel refuses the controllers (`EBUSY`) while any process stays in the scope's own cgroup, and a command that returned can leave a descendant: `go list` starts Go's telemetry sidecar, which can outlive it. A process started after the setup is born in the gate's leaf, where it does no harm (`TestScopeSetupPrecedesDiscovery`). Before it enters the scope, the gate starts only the scope probe and, on the replay path, its fingerprints; these stay in the caller's cgroup.
- **Stop.** `SIGINT`, `SIGTERM` and `SIGHUP` stop the gate, in both tiers, unless it was started ignoring the signal (`nohup` ignores `SIGHUP`, a background job of a non-interactive shell ignores `SIGINT`): then the signal stays ignored. On the first one the gate starts no new step and no new command, and kills every running step whole: its cgroup (`cgroup.kill`) in the systemd scope, its process group under the RSS watch. The merge tier's sandboxed processes are among them: nsenter starts them in the step's cgroup and process group. Every other process the gate starts (`git`, a tool query of a fingerprint, `go list`, `systemctl`) runs in a process group of its own, and the gate kills that group too (`runCommand`, `scripts/gate/stop.go`). The gate waits until each of those steps is empty and each command has ended, and then closes the merge tier's sandbox, which removes its run directory. In the scope it also kills every process left in its own leaf, such as a descendant that left its group or a telemetry sidecar, until it reads the leaf back empty. Then it exits with 128 plus the signal's number (130 for `SIGINT`, 143 for `SIGTERM`), and its last line says only what the stop proved: `gate: stopped by SIGTERM; every process it started has ended` when the leaf read back empty; under the RSS watch, which has no leaf to read, `gate: stopped by SIGTERM; every step and command it started has ended, with its process group`; and `gate: stopped by SIGTERM; not every process it started has ended: <reason>` when a cleanup failed. A second stop signal during a stop exits at once, as a second Ctrl-C does in Bazel, with `gate: stopped by SIGINT, then SIGTERM before the stop ended; processes it started may remain` (`TestStopperServeExitsOnASecondSignal`); this is the way out of a stop that cannot finish. No process the gate started outlives it, so none keeps a descriptor that the gate inherited from its caller, such as the lock of `flock gate.lock ./scripts/gate.sh` (`TestGateStopsItsStepsOnSignal`). Before this change, a `SIGTERM` to a gate in its scope left its steps running with ppid 1 and still holding the caller's lock (measured 2026-11-05 and 2026-11-06). Under the RSS watch, the gate does not stop a descendant that has left its step's or command's process group, because it has no cgroup to find it; its last line then claims no more than the groups. `scripts/gate.sh` starts the gate with `go run`, and `go run` does not pass on `SIGTERM`. So send the signal to the gate's process, or to the whole process group, not only to `gate.sh`.
- **Step output.** A step's stdout and stderr go to an unlinked spool file in `output/` under the gate cache (below; `$TMPDIR/ergo-gate` when there is no cache directory), not to the gate's memory. The gate prints the spool in declaration order through a 32K buffer, so what it holds in memory for a step does not grow with what the step prints, and a step's output cannot fill the gate's 512M reserve in its scope. A file on tmpfs or ramfs keeps its pages in memory charged to the process that writes it, so on Linux the gate writes step output only to a destination it admits, judged on the opened file and not on its path (a link to tmpfs does not pass): a pipe, a terminal, a socket, a device, or a regular file on a disk file system. The admitted disk file systems are ext2/ext3/ext4, xfs, btrfs, f2fs and zfs. Every other file system is refused, overlayfs (its upper directory can be tmpfs), FUSE and NFS included. Each refusal names the file system it found and how to fix it:
  - an output spool refused: the gate exits 2 before any step runs (`gate: output spool in <dir> is on file system <name> ...`); set `ERGO_GATE_CACHE` to a directory on disk whose `output/` is on disk too;
  - the gate's standard output a refused file: the gate exits 2 before any step runs (`gate: standard output is on file system <name> ...`); redirect standard output to a disk file or a pipe;
  - a cache output file refused: the step passes and prints its output whole, but its pass is not recorded (`gate: <step>: pass not recorded: cache output file in <dir> is on file system <name> ...`), so the next run executes it again; set `ERGO_GATE_CACHE` to a directory on disk.

  Off Linux the gate admits every destination: the RSS watch bounds only the steps' resident memory there. A spool write that fails, such as on a full disk, fails the step, and the gate still reads the step's output pipe to its end. Output the gate cannot print whole fails the step (`gate: <step>: print output: <error>`).
- **Which layer may reuse which result.** Three layers can skip a check: Go's test cache inside a `go test` step, a step receipt (`Inputs`), and the whole-gate record (below). A layer may skip a check only when its key holds every input the check reads. A whole-key miss does not empty the inner layers, so each inner layer must be sound alone.
  - *Go's test cache.* cmd/go rechecks a cached result only against the files the test process opened inside the package's own module, and a step can start a program that starts a `go test` in a way no reader of the step's argv sees (`go run -exec`, `-toolexec`, `-vettool`, a shell expansion; gate-testcache-gap rounds 1 to 3). So the gate's go tests are uncached by default and cached only by declared exception: every step runs with `-count=1` added after the caller's `GOFLAGS` (`stepEnvironment` in `scripts/gate/main.go`), which every `go test` the step starts inherits at any depth and which `go build`, `go vet`, `go run` and `go list` ignore, and only the hermetic step (`Step.Hermetic`, the packages below `scripts/gate/` that `TestCachedGatePackagesAreHermetic` checks) runs without it and replays from Go's cache. `TestTestCommandsHaveCacheCoverage` proves this on the environment the gate builds for each step, not on argv shapes, and `TestProgramsStartUncachedGoTests` runs each of round 3's forms as a real step twice and requires a rerun. Threat model: the guard protects against an accidental gap, a new step or test whose `go test` could replay a stale pass; a step that sets `GOFLAGS` or a `-count` other than 1 on purpose is out of scope, and a literal tripwire fails the test on either word in a step's argv, its `Env` or a reviewed script, so the change shows in review. This default is hygiene for the inner tier, not a merge verdict: a tool that gives its child its own environment (a fresh `Cmd.Env` without `GOFLAGS`, its own `HOME`, `XDG_CACHE_HOME` or `GOENV` naming a `GOCACHE` on the host) can still replay a stale pass from a cache on the host (gate-testcache-gap rounds 4 and 5), and the inner tier and its whole-gate record can carry that pass. Only `--merge` gives a merge verdict: its uncached run is in a sandbox with no cache that outlives the run (Merge tier, below). As hygiene, a step starts only a program on an allowlist, by its exact name (`go`, `env`, `timeout`, `sh`, `./bin/ergo`), sets only `ERGO_REPO_ROOT` or `CGO_ENABLED`, and runs a shell only as `sh -c SCRIPT` with SCRIPT byte for byte an entry of `reviewedScripts` (`scripts/gate/reviewed.go`); `TestReviewedScripts` refuses an entry that no step runs. The cost: a real run reruns every observed main-module test that Go's cache used to replay; a whole-gate replay runs no step and is unchanged. Measured 2026-11-05 on this 16-CPU host, interleaved, with a 1-minute load of 14 to 33 and so no speed verdict: a `--no-cache` run took 337 s after against 364 and 378 s before (the `go test (other packages)` step 1,025 s of CPU against 964 s on the warm run before), and a no-op replay 0.66 to 0.93 s after against 0.74 to 1.16 s before (gate-testcache-gap cost-r4.log). The provenance analyzer's controls (`tools/provenance`, its own module) read the checker's syntax sources in their own process and through `analysistest`, so they run with `-count=1`: before, a field removed from a syntax source replayed their pass while a fresh run failed (measured 2026-11-04, gate-testcache-gap). The sketch9 kernel tests run with `-count=1` for the same reason. Running the controls every time the step runs adds about 2.3 s to that step (planner minima at a 1-minute load of 15 to 26); a whole-gate replay runs no step.
  - *Step receipts.* A step with no receipt runs on every whole-gate miss. A step whose result depends on an input that no digest of declared paths, tools and variables holds gets no receipt. The Effect mapping check (`effect conformance mapping`) asks Git whether each evidence file is tracked, and the index is not a declared input: untracking an evidence file kept its receipt and replayed a pass (measured 2026-11-04). The step has no receipt now. It takes about 0.15 s, less than the 0.4 s receipt lookup it replaces (measured at a 1-minute load of 22 to 29).
  - *Whole-gate records.* The key holds the index and every path, so a whole replay covers both reads above.
  - `TestGateCacheParityModel` checks the three layers together on a fixture checkout, with real Go test caching and the real mapping validator: a nested module whose controls read a main-module source, a main-module test that reads it only through a child process under observation, and the mapping step over a tracked or untracked evidence file. It runs gates, merge-tier runs, source and index edits, restores and cache sweeps, and after each invocation it compares the gate with a reference model: replay or not, exit code, each step's verdict, and which inner cache answered. With the gate's own steps, no step passes while its fresh run fails. Two negative controls put back the removed reuse (the controls without `-count=1` and in the hermetic exception, the old mapping receipt); each must show a stale pass from a real cache hit, and the merge tier must withdraw a stale whole record so that the next gate does not replay it. The model assumes inputs that do not change during a run: an edit made and reverted during a run (ABA) is still found only by the merge tier.
- **Go tests** in the inner tier rely on Go's own test cache where the step lets it (above); the merge tier's uncached run starts with an empty one. `cmd/ergo` is split into at most the CPU budget of processes using the measured durations in `scripts/gate/durations.json`. Every shard but the last selects tests by exact name; the last shard skips exactly the names the others selected. So the union of shards covers every test, including tests added since the durations were last recorded. A stale durations file costs wall time, never coverage.
- **The gate's own tests: host and hermetic.** Go's test cache records the files, environment variables and module source a test reads. It does not record the programs a test runs or the shared libraries they load, so no list of program names can make a cached result safe. The gate's own tests are therefore in two kinds of package:
  - *Host packages* (`hostTestPackages` in `scripts/gate/steps.go`) hold tests whose results depend on the host: programs (git, `sh`, `ps`, `systemd-run`, the go command), cgroups, the user's service manager, and the file systems of the temporary directories. `scripts/gate` is one: the gate runs git and `ps` on every run, and its output-storage property runs gates in real systemd scopes. The gate runs each host package with `-count=1` in its own step (`go test ./scripts/gate (host, every run)`), so Go's test cache never replays a host test. The step replays only inside a whole-gate replay (below): that key holds the host fingerprint, which includes every program the host tests start. The step passes `-parallel 8`, or the CPU budget when it is below 8 (`hostTestParallel`): every host test that sets no process-wide state (`t.Setenv`, the working directory, package variables, the shared test slice) runs in parallel, at most 8 at once. Go's default is the step's `GOMAXPROCS`, which is at most the CPU budget, so the bound can lower it only when that is above 8. The 8 was measured before the CPU budget, when the storage layouts ran as parallel gates: at 4, 6 and 8 on a 16-CPU host the package took 151 s, 126 s and 114 s (2026-11-04). No parallel host test starts a gate in a systemd scope now. The 24 output-storage layouts run one at a time on 31 MB of step output, and check the gate's resident memory directly, so the property takes about 60 MiB of disk at its peak; with 1.09 GB of output, eight layouts at a time took 14.2 GB (measured, 2026-11-05).
  - *Hermetic packages* are the other packages below `scripts/gate/`. They replay from Go's test cache. Each runs no program except its own test binary (through `os.Executable()`, in one helper), and its step (`go test (hermetic gate packages)`) builds it with `CGO_ENABLED=0`, so it loads no shared library. The host test `TestCachedGatePackagesAreHermetic` checks this on every gate: for every gate package that a step lets Go cache, it lists the test binary's packages (`go list -deps -test -export`, in the step's environment) for Linux on amd64 and arm64 and for macOS on arm64, and checks them with `scripts/gate/hermetic`. That check type-checks the module's source in each of those configurations, with the standard library's types from the export data, and decides what a name denotes from the types, never from its spelling: a local value, a parameter or another package named `os` cannot stand in for `os.Executable`. A program it admits is a local variable defined once by a call of the `os` package's `Executable` and never written again or address-taken. A file that none of the three configurations builds, or a package that does not type-check, is refused. It refuses a call that runs another program, a program lookup on PATH, a raw system call that can be `execve`, cgo, plugins, `go:linkname`, a standard-library package that imports `os/exec` (except the fuzzing engine), and a package from outside the module and the standard library.
- **Go test inputs are observed.** Go's test cache keys a result on the files and variables the test process reads through package `os`. It cannot see what a child process reads: git, `sh`, a C compiler, or a `go build` that a test or the code under test starts. So every test package's `TestMain` calls `testinputs.Main(m)` (or `testinputs.MainFunc` when it prepares the test process). Main runs the test binary again as a child. The child installs a seccomp filter with a user-notification listener, writes the listener's number on a socket to the parent, which takes the listener itself with `pidfd_getfd` (Linux 5.6). Sending the listener by `SCM_RIGHTS` would need a `sendmsg` the filter lets through unnotified, since no one serves the listener before it arrives, and a process forked before that gap closed could use it to pass a socket address by the observer; taken this way, the filter has one rule for every process and no exception. `pidfd_getfd` needs the access ptrace would (`PTRACE_MODE_ATTACH_REALCREDS`: the same user, a dumpable child, and Yama's consent, which `ptrace_scope` 0 and 1 give a parent). The parent first takes a descriptor the child holds from its start, its end of the socket, and tells the child whether to install the filter at all, so a host that refuses (`ptrace_scope` 2 or 3) runs the tests unfiltered and refuses the result instead of leaving the child waiting on a listener no one serves. This workbox has no Yama (kernel 6.12, LSMs capability, landlock and selinux, not enforcing), and the take succeeds. Then the child runs the test binary again by exec: the filter survives exec, so every package initializer runs observed, including those Go ran before testinputs' own. The filter suspends every open, stat-like lookup, write that depends on what exists (`mkdir`, `unlink`, `rename`, `link`, `symlink`, `chmod`, `setxattr` and the like), `chdir`, exec, and `connect`, `bind`, `sendto`, `sendmsg` and `sendmmsg` with an address, the child and its descendants make until the parent has read the call's path; the call then continues unchanged. The test process trusts the observer's variables (`ERGO_TESTINPUTS_LISTENER`, `ERGO_TESTINPUTS_FILTERED`) only once it proves the observer exists: the descriptor a variable names must be a socket whose peer is its parent (`SO_PEERCRED`), kept open across the exec, and the exec'd process must run under a seccomp filter. A variable inherited from a shell or another runner fails that proof, and the result is refused as unobserved. When the child exits, the parent appends to Go's test log:
  - `open` for a file read or a program run, with the `#!` interpreters it names, and for a directory listed, which cmd/go keys on every entry's name and metadata;
  - `stat` for every other lookup, failed ones included, so a file added later is an input, for a directory changed to, and for the path of an AF_UNIX socket connected to, bound or sent to (an abstract or unnamed address names no file); a path both read and looked up gets both lines, since `open` does not look at a link itself. After the run, every link inside the root on the way to a recorded path gets a `stat` too: cmd/go rechecks an `open` path by what it leads to, and a retargeted link may lead to a file with the same size and time;
  - `getenv` for every variable in the environment of every program run, plus `ERGO_TOOL_VERSIONS` whenever a program ran.

  A path outside the module root is dropped, because cmd/go never rechecks such paths, unless its lookup reaches the root through a link. The parent resolves it one component at a time, as the kernel does, and records the rest of the path from the point it enters the root, unresolved: a link inside the root that is later retargeted, or a directory there that is missing now and added later, then changes the key. Nothing the observed processes can change is remembered between calls; only what a lookup finds in a directory that another user owns and this user cannot write, on a path of such directories, is (never when the tests run as root, with real, effective, saved or file-system user or group IDs that differ, or with `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_SETGID`, `CAP_SETUID` or `CAP_SYS_ADMIN` permitted or effective). A name relative to a working directory or a directory descriptor reached through a link inside the root (`cd dirs/current`; `openat` on, or `fchdir` to, a directory opened as `dirs/current`, with or without `O_DIRECTORY`) is recorded under the link as well as under the directory. fabricate.py tracks working directories per process and copies one to a child at `clone`, `fork` and `vfork`, which strace reports with the child's pid. A seccomp notification comes before the call, so the observer never learns a child's pid at the fork, and by the child's first lookup its parent may have exited and the child been reparented. So each link inside the root that a `chdir`, or the open of a directory (judged by the file the path leads to), crossed is remembered by the directory it leads to, for the whole run, and any process whose working directory, or a descriptor it names a path relative to, is that directory records its relative names under each such link too: a reparented child, a descriptor passed to another process and an `fchdir` (which is not notified) are covered, and a process that reached the directory another way gets an extra entry, which can only cause a rerun. A read open in the root costs one more `stat` for this, and a directory one more open and `readlink`. `/proc/self/cwd/…`, `/proc/<pid>/root/…`, `/proc/self/fd/<n>/…` and `/dev/fd/<n>/…` are read through the caller's links. Other paths under `/proc`, `/dev` and `/sys` are skipped, judged after `..` is resolved, so `/proc/../<root>/x` is recorded. This happens in Main, so `go test` run by hand observes exactly as the gate does. `internal/testinputs/guard` fails any test package without a `TestMain` that calls Main on every platform; `ERGO_TESTINPUTS_GENERATE=1 go test ./internal/testinputs/guard` writes the missing ones. It finds test packages under any build tags by walking the tree as `./...` does (skipping `testdata`, names starting with `.` or `_`, nested modules and links to directories), with ordinary directory reads that Main records, so a new package, tracked or not, in any clone, worktree or Rift, changes a listing and reruns it. `internal/testinputs` itself is exempt: its end-to-end cases run observed fixture binaries, and observation does not nest (a listener installed below another hides the calls it takes from the outer one). Those cases prime Go's cache, edit what only a subprocess read, and require a rerun, each beside a control with a plain `TestMain` that must replay its stale result.
- **Unobserved results are never cached.** When Main cannot observe, it leaves the test log without its final newline and prints `testinputs: result not cacheable, inputs unobserved: <reason>`; cmd/go then refuses to cache the result (`saveOutput` in `cmd/go/internal/test`), so the package reruns every time instead of replaying a result keyed on a partial list. That happens on another operating system or architecture (observation needs Linux 5.7 or later on amd64 or arm64), when seccomp is refused, when the parent may not take a descriptor from the child (`pidfd_getfd` refused: Yama's `ptrace_scope` 2 or 3, an undumpable test binary), when the parent cannot read a suspended call's memory that the kernel can (`process_vm_readv` fails other than with `EFAULT`, as for a process that made itself undumpable), when a process makes a call that would hide later accesses (`chroot`, `pivot_root`, `unshare`, `setns`, `mount`, `umount2`, the new mount API (`open_tree`, `move_mount`, `fsopen`, `fsmount`, `fspick`, `mount_setattr`), a namespace-creating `clone` or `clone3`, `open_by_handle_at`, `fanotify_mark`, `quotactl`, `quotactl_fd`, `bpf` (which watch or open paths without a lookup the observer sees), its own seccomp listener, a call of another ABI, a system call numbered above the last one of Linux 6.12, which the observer cannot classify), for a path or variable name that holds a newline, which the log cannot carry, when an observer variable is set without an observer behind it, and when the log cannot be marked (the test then fails, since cmd/go never caches a failure). `io_uring_setup` fails with `ENOSYS` under observation, because a ring opens files without system calls; a program that uses one must fall back to ordinary calls.
- **What observation does not key.**
  - Files outside the module root: tool installations, `~/.gitconfig`, user caches, system libraries. `ERGO_TOOL_VERSIONS` stands for the installations (below); tests that run git isolate it from user configuration (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`). In a linked worktree or a Rift, `.git` is a file naming metadata outside the root, so the HEAD, index and objects a test's git reads there are not keyed either.
  - A variable that was unset when a result was cached, read by a program the test runs. A program's lookup of a variable is a library call, not a system call, so it leaves no trace, and cmd/go's log cannot say "every variable, present or not". The gate closes this for its own runs: a Go test step receives only the variables `internal/testinputs/testenv` names, whose values join `ERGO_TOOL_VERSIONS`, and the gate log prints the list. `go test` run by hand passes the caller's whole environment, so exporting a variable after a cached run can replay a result the variable would change; run `go test -count=1`, or use the gate. Every variable a started program receives is keyed, so running the tests by hand from a shell with a different environment reruns the packages that start programs.
  - Extended attributes: cmd/go's log has no entry for them, and changing one changes no modification time. `setxattr` and `removexattr` are recorded as lookups of their paths.
  - Two changes of a file inside one clock tick with the same size, and a change made with the old modification time restored (`touch -r`, `tar -x`, `rsync -a`, `cp -a`), for files: cmd/go rechecks a file by size, mode and modification time, not content. A directory listed is rechecked by its entries, so an entry added under a restored directory time is still seen.
  - A relative `#!` interpreter, which the kernel resolves against the working directory, and the dynamic loader an ELF program names (`PT_INTERP`). Every program here names an absolute interpreter and the system loader, both outside the root.
  - Races inside one run: a file the observed tree changes between the parent's lookup and the call it suspended, and a thread that changes the shared working directory, or reuses a descriptor number, while another thread's call waits. A link a `chdir` or a directory's open crossed is matched to working directories and descriptors by the directory it led to when the call was notified, which a link retargeted in between changes.
  - A runner that fakes the observer on purpose. The test process proves only that its parent created the socket it inherited and that some seccomp filter is installed (`Seccomp: 2` in `/proc/self/status`), not that the filter is this observer's: a `go test -exec` wrapper that makes a socket pair, sets `ERGO_TESTINPUTS_FILTERED` and runs the binary under an unrelated filter makes the tests run unobserved while believing they are observed. Any check the test process could make, such as a nonce the parent echoes, is one more message such a wrapper can answer, so the proof is aimed at what happens by accident (a variable inherited from a shell, a runner or a nested test), which it catches, and a deliberate wrapper is out of scope, as one that rewrites the test log is.
  - Processes a test leaves running after it exits: once the observing parent exits, their filtered calls fail with `ENOSYS`. The filter sets `no_new_privs`, so a setuid program does not gain privileges under a test.
- **What observation costs.** An observed call waits for the parent: a stat takes about 15 µs instead of 1.4 µs with synchronous wake-up (Linux 6.6 and later), most of it the kernel's round trip. The go command makes most of the calls: on every run it stats each standard-library source it builds on, and a seccomp filter sees registers, not paths, so it cannot pass those calls through. Measured 2026-10-11 on the 16-CPU workbox, with other lanes running:
  - each package's tests alone, observed against `-count=1`, two rounds: 2,060 s against 1,626 s of CPU time in total (+27%; `cmd/ergo` +24%, the legacy compiler package +28%, `scripts/gate` +43%). Wall time at a 1-minute load of 14–62 was 1,272 s against 822 s; an earlier measurement at load 13–73 gave 1,933 s against 1,551 s of CPU (+25%), with the wall times reversed, so the load swamps wall time;
  - the full gate, with every step and every Go test rerun: 108.2 and 135.5 s against 95.3 and 67.7 s on main (1-minute load 27–92 when each started, 68–91 when it ended; earlier pairs measured 99.1 and 149.1 s against 82.2 and 70.9 s, and 74.9–76.6 s against 50.1–60.8 s);
  - a gate with nothing changed: 4.6–7.0 s at a 1-minute load of 68–94, every Go test `(cached)` except the guard (below). On main, at loads of 62–75, the first no-op after a full run took 5.8 and 14.5 s (rerunning 1 and 7 test packages), and the second 5.5 and 3.2 s.

  A no-op stays a no-op only if no test reads what the gate rewrites. The gate therefore builds `bin/ergo` beside its cache and moves it into `bin/` only when its bytes change (`go build` touches its output even when it relinks nothing), and a test that builds a command inside the repository passes `-buildvcs=false`: VCS stamping runs `git status`, whose walk would make the result depend on every file in the working tree, build outputs included. For the same reason the gate's own tests declare its steps over the packages `durations.json` names instead of running `go list ./...`, which lists every directory in the module, including the ones the gate's own steps write. The guard is the exception: it must see every new package, so it walks the tree and reruns whenever a listing changes, such as when the gate writes `bin/`; it takes about a second.
- **Each test package records only its own inputs.** Go keys a cached test result on every file and directory the test opened or examined, and on each variable it read (its test log). A test that reads the whole tree reruns after every edit. The rule: a test package reads the directories of its dependencies (`go list -deps -test`), its own `testdata`, and a short list of declared paths, each with a reason. `internal/closure` holds that list and checks it. Each declared path has a grant: one file, the listing of one directory, a flat pattern of files (`docs/research/ef-migrate/*.ergo` grants no subdirectory), or a subtree, which only a measured walk deeper than one level earns. The check resolves each recorded path as the kernel does, so a path is classified by the object it reaches and not by its spelling: each symbolic link on the path is an input too, and a path the check cannot resolve (a `..` after an absent component, a loop of links) is outside the closure. `TestEveryPackageRecordsOnlyItsClosure` builds the test binary of every test package of the module, runs it with `-test.testlogfile`, and fails on a recorded path inside the checkout that is outside the package's closure, and on a declared path that no recorded input uses. It runs each test binary in a sandbox built as Bazel's linux-sandbox builds one, in an unprivileged user and mount namespace that every child process inherits. Every mount of the file system is read-only, recursively from `/`. The only writable places are scratch directories that the sweep makes fresh and empty for each run: `TMPDIR` (also `GOTMPDIR`), `XDG_CACHE_HOME` (with `GOCACHE` in it), the directory of the test log, and a fresh tmpfs at `/dev/shm`. Each is a mount of its own outside the checkout, so Linux refuses a hard link or a rename of a checkout file into it (EXDEV). A package can declare a cgroup2 mount that its tests write (`scripts/gate` writes its memory budgets), because cgroup2 holds no file that can be a name of a checkout file. The tests hold no capability, run with `no_new_privs`, and cannot make a user namespace, so they cannot remount anything. Before the first package runs, the sweep checks this from inside the sandbox: the mount table, the capability sets, and that a remount, an unmount and a new user namespace fail. It also refuses a checkout that has another name: a bind mount of it, a mount inside it, or a hard link of one of its files outside it, because a read by that name is not classified. Thus the tests cannot change the checkout or anything above it. A process outside the tests can, if they ask it to: a service of the host that they reach by a socket (the systemd user manager, for example). So the observer (`internal/testinputs`) records each path with its identity at the time of the access: every location that the lookup of the path passed, with the device and inode of the object there and the target of each link. Before it looks up a name, the observer watches (inotify) the directory, if a process of this user outside the tests can change it. It also watches every directory of the checkout and the mount table. The check classifies each path by the objects that its accesses reached, and compares them with what the path names after the run. A path whose object changed after the run is outside the closure, unless a declared path names the object of the access exactly. A path that met a change during the run, and a change in the checkout that no access looked up, are outside the closure, and no declared path covers them. A path that has no identity is outside the closure unless a declared path names it exactly. The observer cannot observe its own package's tests (Linux refuses a second seccomp listener), so the sweep gives `internal/testinputs` no identity. Its log is the test log that Go writes in the test process, which records each path as the test spelled it, and the exact declared paths of that package cover what those paths name in the checkout. The sweep classifies each run's log before it removes the run's scratch directories, so a path through a link that a test left in its scratch resolves through that link, and a read of the checkout that way is outside the closure. This holds only while the link stays as it was at the read. A scratch link that a test of `internal/testinputs` removes or changes after the read (one in `t.TempDir`, which the testing package removes; one pointed elsewhere) no longer shows where it led, and no identity does: the read is then classified by what the link names after the run, or by nothing. Only an observer of that package's tests closes both forms. A path that leaves the checkout after it entered it is outside the closure. A test that writes outside its scratch directories fails with EROFS, and the sweep reports a closure violation that names the package: write to `t.TempDir` instead. If any part of the sandbox cannot be made or checked, the sweep refuses to run and says which part; on a system without Linux namespaces (macOS) it reports unsupported and fails. The tests of the sandbox make a namespace, so they run only with `-count=1`. It runs every test binary (about 10 minutes, because each run builds with an empty `GOCACHE`), so the gate does not run it; the gate runs the unit tests of the rule. Run it after a change that adds a test input: `ERGO_CLOSURE_SWEEP=all go test -count=1 -run TestEveryPackageRecordsOnlyItsClosure ./internal/closure`. `ERGO_CLOSURE_SWEEP` also takes a comma list of package directories, and `ERGO_CLOSURE_KEEP=<dir>` keeps the logs and each package's inputs outside its closure. The checks that read every tracked file (the residue checks) live in `internal/residue`, whose declared input is the whole tree. A test that builds a command of the module passes `-buildvcs=false`, or builds it once per test process outside the tree, as `internal/sketch/lower` does with `cmd/ergo`. Thus an edit of this page reruns neither the checker's tests nor the lowerer's tests.

  Limit: the closure rule covers what the tests and the processes they start do, except a read in `internal/testinputs` through a scratch link that the test removes or changes after the read (above). It does not cover a change that a process outside the sandbox makes while a test runs: another process of this user, a service of the host, or a service that runs as root. The identity and the watches find some of these changes, but not all of them. Examples that are not found: a hard link of a checkout file made from outside; a link in the scratch directories of the tests changed between the observer's lookup and the kernel's (scratch directories are never compared, so the change need not be undone); a file of `internal/testinputs` swapped and restored, since that package has no identity; data or a descriptor that a service reads for the tests and sends through its socket; and a change in a directory that the observer does not watch. The follow-up unit `sandbox-host-services` closes this class: a constructed root, a network namespace, and no IPC to the host unless a package declares it.
- **Other steps** declare their inputs: repository paths, tool fingerprints (below), environment variables and installed directories. A step that walks a directory itself, rather than Git's view of it, such as the Foldkit snapshot check, declares that directory as installed: every entry on disk, files Git ignores included; a link out of it back into the repository contributes only its target. A file's digest carries its content and the permission bits that can change a result: the three executable bits, which a check can read and which decide what a step can run, and owner-read. Steps run as the checkout's owner, so no group or other read or write bit decides their access, and no check asserts one; checkouts made under different umasks share receipts. A symlink among a step's inputs keys its target text and what it reaches, by the link rule of the whole-gate key (below). A link that reaches a directory, or a place outside every keyed root, cannot be keyed: the step runs without its receipt and prints why (`gate: <step>: not cached: <path> reaches <target> outside every keyed root`). These steps replay a recorded pass while those inputs are unchanged. Receipts live under `ERGO_GATE_CACHE`, else `$XDG_CACHE_HOME/ergo-gate` (by default `~/.cache/ergo-gate`), in `ergo-gate-v4/`, never in the tree, and every worktree shares them. A receipt names the size and SHA-256 digest of the step's output, which is in a `.out` file beside it. A replay prints that file only when both match; otherwise the step runs again. Failures are never recorded. A pass the gate cannot record still passes, and the gate says why (`gate: <step>: pass not recorded: <reason>`).
- **Example programs (`examples (default)`).** After `build bin/ergo`, the step runs `go run ./scripts/examples`: it builds each program under `examples/` tagged `default` with that `bin/ergo`, runs its own tests (`ergo test`), and compares each recorded case's stdout, stderr and exit status byte for byte (`examples/README.md`). It writes nothing into the checkout. Its key holds `examples/` as an installed directory (the runner walks it on disk, so a file Git ignores there counts), the runner's sources without its tests and `testdata/`, `go.mod`, the `go` and `sh` fingerprints, and `bin/ergo` as a built file (`Inputs.Built`). A built file is a file a step in `Needs` writes: the gate digests it as it digests a repository path, but only when it keys the dependent step, after its `Needs` passed, and never from a memo, so the key holds the compiler that step built. A missing or unreadable built file fails the step (`gate: hash inputs: …`) and never replays; a FIFO there runs it without its receipt. `bin/ergo` has no VCS stamp and embeds the runtime that `ergo build` emits, so its digest stands for the compiler. The emission cache under `XDG_CACHE_HOME` is not keyed: it is addressed by content. Cost, measured on 2026-11-04 on this host with one program (`tidewalk-replay`) and a warm Go build cache: the runner alone, after a change under `examples/`, takes 0.3 s (0.7 s with an empty emission cache); a replayed receipt costs the digests of `examples/`, the runner's sources and the 11 MB `bin/ergo`.
- **Whole-gate replay (the inner tier).** Before the gate runs a step, it computes one key over every input of every step (package `scripts/gate/replay`; the collectors are in `scripts/gate/wholegate.go`). The key is SHA-256 over:
  - the version `ergo-gate-v4` and the SHA-256 of the running gate executable;
  - the absolute path of the checkout root, which steps see through `TMPDIR` and `ERGO_REPO_ROOT`;
  - the HEAD commit and every index entry (mode, blob, stage, path), so a change between tracked and untracked is a key change, and so is a commit with the same tree (Go's VCS stamping reads HEAD);
  - every path below the root except `.git`, with its class (tracked, untracked or ignored) and its kind (file, symlink, directory or other). A tracked or untracked file gives its content and its keyed permission bits. An ignored file gives its stat tuple: size, modification and change time in nanoseconds, inode and mode. A FIFO, a socket or a device makes the key unreplayable (`<path> is a FIFO: only regular files, directories and symlinks can be keyed`; see "What a key can read" below): what a step reads from it is not in any stat field (a FIFO keeps its inode and times when a step drains its buffer), as a step receipt refuses it too. The gate does not read the content of ignored files (379 MB below `dist/` in the warm source). Go's test cache keys the ignored files a test reads, so the whole-gate key must hold them too. A directory gives its path: a test that lists its parent sees an empty directory. A symlink gives its target text and what it reaches (the link rule below);
  - each variable a step can receive (Environment, below), set or not, with its value;
  - the gate's settings: every `ERGO_GATE_*` variable, `XDG_CACHE_HOME` and the cache directory;
  - the host fingerprint: GOOS and GOARCH; the kernel release and version; the CPU count; the CPU budget, which sets the shards, the steps at once, `GOMAXPROCS` and the host packages' `-parallel`, so a verdict can differ under another budget (a test with a timing bound, a race that shows only at some parallelism); physical memory; the memory mechanism, the budgets and the bound of `ergo-gates.slice`; the cgroup v2 facts (the file system of `/sys/fs/cgroup`, and `cgroup.controllers` and `cgroup.subtree_control` of the user manager's cgroup); the file system type of the checkout, the temporary directory, `GOTMPDIR`, `GOCACHE`, the gate cache and its output spools; the user id; `RLIMIT_NOFILE`; and the tool fingerprint (below) of every declared host program (`hostPrograms`). A declared host program is each program that a step or its shell script starts, and each program that the code and tests of `scripts/gate` start. `TestHostProgramsDeclared` fails when a step or a test starts a program that is not declared. A program that is not on `PATH` is a distinct value. On darwin the gate reads the kernel and memory facts from `sysctl` and the file system types from `statfs`; darwin has no cgroups. A fact that the gate cannot read makes the key unreplayable: it never matches, so the gate neither replays nor records. The gate reads physical memory again at every collection, and only a positive size it read is a fact; an unknown size gives `the physical memory cannot be read`, and a size that changes during a run keeps the run from recording.

  When every step passes, the gate stores the output of each step and then writes a whole-gate record under the key. A later gate at the same key starts no step: it prints the record. The replay needs no systemd scope, so the gate replays before it opens a scope. After the identity line, a replay prints `== <step>: ok, replayed (passed in <s>s at <time>)` and the recorded output for each step, then `gate: replayed <n> steps (key <12 hex>, recorded <time> at head <sha>)`. The durations are the recorded ones. Thus the host step replays only inside a whole-gate replay. Measured on 2026-11-04 on this 16-CPU host: a no-op gate replayed its 15 steps in 0.53 to 0.59 s wall (three runs, 1-minute load 20.5). Before, a no-op gate took about 116 s, almost all of it the host step (load 32 to 50).
  - *Changes during a run.* At the end of a run the gate computes the whole key again. It records only when the end key equals the start key, and when no stat-keyed path changed within 2 s before either computation (as Go's test cache does with `modTimeCutoff`). Otherwise it prints `gate: no whole-gate record: <reason>`. So a step that writes into the checkout stops the record. In a new worktree the first gate writes `bin/ergo`, and the tests of `internal/sketch/lower` run `ergo run` in the checkout root, which builds `dist/main`; the second gate runs those tests again, because their inputs changed. The third gate records (measured 2026-11-04). A change that is made and then reverted inside one run (ABA) is not found: the merge tier is the guard.
  - *Failures.* The gate never records a failure. A run that does not replay and fails a step withdraws the record at its key (`gate: withdrew whole-gate record <key>`). A concurrent pass at the same key can record again after a withdrawal; the merge tier runs every step again before a change reaches main.
  - *Store.* `<cache>/ergo-gate-v4/objects/<sha[:2]>/<sha>` holds the printed output of a step, named by its SHA-256. The gate writes an object once: it links a temporary file into place, and it keeps an object of the same name that verifies (it replaces one that does not). `<cache>/ergo-gate-v4/whole/<key[:2]>/<key>.json` holds the record: for each step its object, size, outcome (ran, or cached from a step receipt) and duration, and the head, tree, clean flag and time of the run. The gate writes the record last, by one atomic rename. Any process can delete or damage an object or a record at any time (a manual clean, a withdrawal, a future eviction). A replay opens the record and each object. It verifies the size and digest of each object through the descriptor that it reads, and it copies the object into a private file. Then it prints from those private files and never opens an object by name again. A missing or damaged object makes the gate run the steps. Records are per worktree, because the key holds the root path; objects are shared. Nothing evicts records yet: each passing gate with a new key adds about 10 KB.
  - *The link rule.* A symlink in the checkout keys its target text and what it reaches. A target in the checkout is covered by its own entry, and a target in a fingerprinted installation (`GOROOT`, the file of a tool) by the fingerprint. A link that reaches any other place, that dangles outside, that loops, or that passes through such a place makes the key unreplayable. The gate then does not replay or record, and prints `gate: no whole-gate replay: <path> reaches <target> outside every keyed root`.
  - *What a key can read.* One rule (`replay.KindOf`) decides it for every file that any key reads, wherever the walk reaches it: an entry of the checkout, the target of a link (relative or absolute, in the checkout or in a fingerprinted installation) and every path below a directory it reaches, a path below a fingerprinted installation, and a file a step receipt hashes. Only a regular file, a directory and a symlink can be keyed, and a symlink only when what it leads to can be keyed by the same rule. A FIFO, a socket, a device or a file type the walk does not know makes the whole gate unreplayable: the gate does not replay, does not record, and refuses a record that already sits at the key. The reason names the path and the kind, for example `gate: no whole-gate replay: stream reaches /…/go/stream, a FIFO: only regular files, directories and symlinks can be keyed`. A fingerprint that fails, for such a file in the installation or for any other reason, makes the key unreplayable in the same way (`program go cannot be fingerprinted: <path> is a FIFO: …`).
  - *Not keyed.* Go's build cache and module cache: the build cache is addressed by content, with the toolchain in each action id, and `go.sum` verifies the module cache, so Go trusts both. User configuration outside the checkout, such as `~/.gitconfig` (as for Go's test cache; see Tool fingerprints). A test that depends on the time replays until the key changes; the merge tier runs it again.
- **Merge tier (`--merge`).** Run it before a change reaches main. If the key of the checkout has no record, the gate first runs the inner tier, which records on a pass; if the inner tier fails, the gate exits 1. Then the gate runs every step uncached. It does not use step receipts or whole-gate records, and it drops the hermetic exception, so every step, the hermetic one included, runs with the uncached default (`-count=1` in `GOFLAGS`, above) and no `go test` it starts replays a result. The run is in a sandbox (below), so it starts with an empty build cache and test cache, a module cache that holds only archives the gate built from module contents `go.sum` verifies, and no Go cache from before the run in any tree it reads (*Input contract*, below). Then the gate prints one line for each step, `merge: <step>: inner <pass|none>, uncached <pass|FAILED|not run>`, and `merge: verdicts equal (<n> steps)` or `merge: FAILED: verdicts differ: <steps>`. A difference exits 1 and withdraws the record at once, before the gate collects the end key, so a change or a collection error at the end cannot keep a discredited record. A tracked or untracked file, HEAD, the index, a variable, a setting or a host fact that changed during the uncached run also exits 1. The inner tier's steps write ignored files into the checkout (`dist/main` from the tests of `internal/sketch/lower`); the uncached run writes into its export (below), not the caller's checkout. A change of ignored files and directories is named (`merge: the run wrote into the checkout: …`) and does not fail the merge tier. The merge tier writes no whole-gate record. A flaky step shows as a difference. The merge tier is the clean-against-incremental check (Fai's F6): it finds an input that no key holds.
  - *Policy.* Only the merge tier gives a merge verdict. The inner tier (a plain gate, and the merge tier's first run) is hygiene: it can replay a stale pass from a cache on the host that a tool chose itself (Go test cache, above), and its whole-gate record can carry one. The merge tier's verdict is its uncached run, and that run is in a sandbox with no persistent state.
  - *Sandbox.* The uncached run is in a bubblewrap (`bwrap`) sandbox the gate makes without privilege (`scripts/gate/sandbox.go`, `scripts/gate/sandbox_linux.go`). The gate starts a holder process in a new user namespace that maps only its own user and a new pid namespace (`startSandbox`), and bwrap joins them (`--userns`, `--pidns`, `--unshare-pid`, `--die-with-parent`). One function, `sandboxArgv`, builds bwrap's argv from a plan (`sandboxPlan`); nothing else decides a mount. The root is a tmpfs. Before the sandbox starts, the gate exports the head commit on the host into the checkout's new empty directory (`exportCommit`, `scripts/gate/inputs.go`): `git init`, `git fetch` of the head by its hash from the repository, and `git checkout --detach`, with no user or system git configuration. The object store is not bound into the sandbox. So the run checks a fresh export of the commit, never the caller's working tree; a checkout with changes gets no verdict (`the checkout has changes; ...`). Every step of the run enters the sandbox through `nsenter` (`sandboxWrap`, applied in `execute` in `scripts/gate/main.go`), so it still runs as the gate's child, under the gate's memory budget, with its output in a spool on the host. Closing the holder ends the pid namespace, and the kernel stops every process left in it.
  - *Writable paths.* Each path a step may write by name is bound read-write from its own new empty directory (`sandboxScratch`): `/tmp`, `/var/tmp`, `HOME`, `XDG_CACHE_HOME`, `GOCACHE`, `TMPDIR`, `GOTMPDIR`, the gate cache, the checkout and the module cache (`go env GOMODCACHE`). Those directories are under the run's own directory, `<gate cache>/sandbox/<random name>`, which the gate creates (it fails if the name exists) and removes when the run ends, so a cache a step fills (Go's test cache wherever a tool puts it, under HOME, XDG_CACHE_HOME or GOCACHE) lives only as long as the run and two runs never share one. They are on disk, not tmpfs, measured: on tmpfs the gate's own tests refused their output spools (Step output, above), a directory-order test of `internal/sketch/build` failed, and every byte a step wrote, a cold build cache of gigabytes included, would count against the step's memory budget. No host path outside the run's directory is writable.
  - *Read-only paths*, the minimal set, each found necessary by running `--merge` without it (2026-11-05; `sandboxReadOnly`): `/usr`, the programs the steps run (`sh`, git, the C compiler, `ps`) and their libraries (without it: `bwrap: execvp /bin/sh: No such file or directory`), with the host's `/bin`, `/lib`, `/lib64` and `/sbin` links into it recreated; and `GOROOT`, the toolchain `go.mod` selects (without it: `go: downloading go1.27.0 ...`, which fails). Here `GOROOT` is in the host's module cache; only `GOROOT` is bound, never the cache around it. The steps in the sandbox get `GOROOT/bin` first on `PATH`, `GOTOOLCHAIN=local`, `GOPROXY=off` and the run's own `GOMODCACHE` (`sandboxEnvironment`). `/etc` is not bound: `--merge` passed without it, so the host's git, resolver and user configuration are not inputs of the verdict. bwrap adds `/proc` and a minimal `/dev`. `checkSandboxPlan` refuses a plan whose read-only set exposes `HOME`, the host's module cache or a parent of either, `/tmp`, `/var/tmp`, the caller's `GOCACHE`, `XDG_CACHE_HOME`, `TMPDIR` or `GOTMPDIR`, `$HOME/.cache`, `$HOME/Library/Caches`, the directory of the runs, or the checkout. `TestSandboxArgvProperty` checks these rules over generated plans; `TestSandboxPlanOfThisHost` checks the plan of this host and starts it.
  - *Input contract.* The guarantee: no byte that a process of this user could write before the run is visible in the run, except the commit and module file contents verified against the commit's go.sum. The run reads three inputs from before it. (1) The commit, exported as above. (2) The modules, built by construction, as a Nix fixed-output derivation is: for each line of each `go.sum` tracked at the head, the gate reads the host's `<GOMODCACHE>/cache/download/<module>/@v/<version>.zip` or `.mod`, checks that the line's `h1:` hash, which covers file names and contents only, matches, and writes into the run's empty module cache only those verified contents (`seedModules`). A `.mod` file is written as read, since `h1` covers all of its bytes. A `.zip` is written as a new archive built from the verified members alone (`moduleZip`): members sorted by name, stored without compression, each with the date 1980-01-01, no flags, attributes, extra fields or comment, and no archive comment and nothing after the central directory. So the bytes the run gets are a function of what `h1` covers, and no byte of the host's container reaches it: not a ZIP comment, a header field, an extra field or data around the archive. No other host file is read: not `.info`, `.ziphash`, `.lock` or `list`. Go needs none of them offline to build from a module cache that `go.sum` pins (the provenance analyzer step builds `tools/provenance`, which requires golang.org/x/tools, x/mod and x/sync, from the constructed archives alone), and it writes its own `.ziphash` into the run's cache. `TestModuleZipByConstructionProperty` generates module trees and, for each, host archives with equal `h1` hashes that vary member order, method, times, modes, extra fields, member and archive comments, and data before and after the archive, each beside host `.info`, `.ziphash`, `.lock` and `list` files: every variant seeds the same bytes, which hash to the `go.sum` line, have the fixed shape and hold no host byte, and nothing else is written. `TestSandboxModuleZipIsConstructed` is round 7's verifier probe as a regression: a host zip whose comment holds a marker seeds, and inside the sandbox the run's zip exists without the marker. A file the host does not have is not copied, and the step that needs it fails (`GOPROXY=off`); a file whose hash differs fails closed (`the module inputs: <file> does not match go.sum`); a `go.mod` with a `require` and no `go.sum` beside it fails closed (`requires modules but has no go.sum`); a `go.work` anywhere in the commit fails closed (`the merge tier runs with GOWORK=off and admits no workspace`). Go then extracts each module from the constructed zip, and checks it against `go.sum` again, as `go mod download` does. In the sandbox every step runs with `GOWORK=off`, `GOPROXY=off`, `GOTOOLCHAIN=local` and `-mod=readonly` last in `GOFLAGS`, after the caller's flags and `-count=1`, so no flag in `GOFLAGS` lets a step change a `go.mod` or `go.sum` (`TestSandboxEnvironmentPinsModules`). (3) The declared read-only trees, `/usr` and `GOROOT`. Each is admitted by its resolved identity (`admitInputs`, `scripts/gate/inputs.go`): the declared path with every symbolic link in it and its parents followed, component by component, as the kernel follows them (`resolvePath`, checked against `filepath.EvalSymlinks` by `TestResolvePathMatchesKernel`). The forbidden paths, HOME, the checkout and the runs' directory are compared with both the declared and the resolved path, each by its own spelling and resolved. The check walks the resolved tree, and bwrap binds the resolved tree at the declared path (`--ro-bind <resolved> <declared>`), so the tree checked is the tree bound whatever its spelling. `sandboxArgv` reads only that admitted set. At the start of every run, `checkInputs` (`scripts/gate/inputs_linux.go`) reads each resolved tree entry by entry and finds every path this user could have written: one the user owns with its owner write bit, one of a group of the user with the group write bit, one any user may write, and one `access(2)` says is writable (ACLs). It also finds a Go build or test cache (a `trim.txt`, a `testexpire.txt`, cmd/go's `README`, or a 64-hex-digit `-a` or `-d` entry in a two-hex-digit directory), and a directory this user cannot read. The walk does not follow a symbolic link. Each link's target is resolved as the sandbox resolves it: through the trees as bound, the masks and the sandbox's top-level links. A target inside a tree is checked there; a target in a scratch path is the run's own; a target in `/proc` or `/dev` is the kernel's; a target that holds one of these shows only them. Any other target, absolute or relative, is masked with an empty read-only directory, so the link shows nothing, whatever a later change binds there. A finding in `/usr` is masked: a directory is bound as an empty read-only tmpfs, a file as `/dev/null`. A finding that is the root of a tree, that is in, at or above `GOROOT`, or that is at or above a program the steps run (each `hostPrograms` name, resolved) is not masked: the merge tier fails closed with `gate: --merge needs its sandbox and gives no verdict without it: the input contract: <path> (<reason>) ...`. On this host (2026-11-05) the check masks 11 paths, every one writable by this user: `/usr/bin/{bsondump,mongodump,mongoexport,mongofiles,mongoimport,mongorestore,mongostat,mongotop}`, `/usr/local/bin/{docker-credential-porter,porter}` and `/usr/share/doc/mongodb-database-tools`; it finds nothing in `GOROOT`. It also masks 177 targets of links in `/usr` that leave both trees: 176 under `/etc` and `/var/lib/ghostscript/CMap` (`/usr/share/X11/rgb.txt` to `/etc/X11/rgb.txt`, for example). The other outward links in `/usr` reach `/dev/null`, `/bin` and `/sbin` (the sandbox's links into `/usr`), or HOME, a scratch path. Inside a user namespace (the gate's own tests during the merge tier's run) an unmapped group reads as the overflow group, which is also one of the process's groups, so the check masks more there: measured, `/usr/local/share/fonts` (root:staff, mode 2775) as well. `TestInputContractProperty` checks the check and the mask plan against a reference over generated trees; `TestInputAdmissionResolvesLinks` does so with each tree declared through links (the tree, a parent, a chain, a relative link) and links inside to and out of the trees; `TestSandboxAdmitsSymlinkRoots` and `TestSandboxArgvBindsAdmittedRoots` start the sandbox over a tree declared as a link; `TestSandboxMasksContaminatedInputs` makes such a tree, starts the sandbox and reads the masked paths inside; `TestSeedModulesVerifiesGoSum` and `TestSeedModulesRefusesUnverifiedRequirements` check the seeding; `TestMergeTierInputContractRegression` is round 6's finding as a regression: a tool keeps a Go build cache in `$GOMODCACHE/cache/go-build` and restores it into a fresh `HOME` for its child; the cache is primed on the host until it replays, the bad input is committed, and the second merge tier must fail on the test's own failure.
  - *Fail closed.* Where the sandbox cannot run, `--merge` exits 2 with one line, `gate: --merge needs its sandbox and gives no verdict without it: <reason>`, before it runs anything: off Linux (`scripts/gate/sandbox_other.go`), without `bwrap`, `nsenter` or `cat` on `PATH`, without user namespaces, with a mount bwrap cannot make, with a dirty checkout, with an input the input contract refuses, with a module that does not match `go.sum`, or with a plan `checkSandboxPlan` refuses (`TestMergeTierFailsClosed`, and `TestSandboxArgvProperty` for the plans). There is no unsandboxed merge verdict and no switch for one. The plain gate does not need the sandbox.
  - *Threat model.* The sandbox protects the merge verdict against state that outlives a run: a stale pass in a cache a step or a tool it starts chooses, in a writable path (each starts empty) or in a declared read-only tree (the input contract masks it or fails closed), and the caller's uncommitted files. `TestMergeTierSandboxRegression` runs the merge tier twice with the checked input changed in between, once for each way a child picks its cache (the inherited environment; a fresh `Cmd.Env` with and without `GOCACHE`; a tool-chosen `HOME`, `XDG_CACHE_HOME`, or `GOENV` with its own `GOCACHE` under a host path; and round 5's verifier probes verbatim), and the second run must fail on the new input. `TestEnclosedRunWrapsEveryStep` requires every step of the run to enter the sandbox, and `TestMergeTierSandboxConcurrent` runs two merge tiers at once over one cache-sensitive check and each gives its own verdict. Residuals: a step can still change an input during the run and change it back (ABA within one run); a module file's contents come from the host and are admitted on the strength of `go.sum`'s `h1` hash (SHA-256 over the names and contents), so they are what the commit pins unless SHA-256 is broken, and what `h1` does not cover (order, modes, times, the container) the gate sets itself; the network is not cut, but with no `/etc` there is no resolver configuration, so a name lookup fails, and `GOPROXY=off` stops the go command's downloads, so only a step that fetches on purpose (by address, or with its own `GOPROXY`) reaches the network; a file in `/usr` that root owns and a privileged process wrote is admitted, because no process of this user could write it; a path this user owns without a write bit (all of `GOROOT` here, which Go extracts read-only) is admitted, so a process of this user that adds the bit, writes and removes the bit again before the run is not found (no step of the run can write it: the tree is bound read-only); the host's `GOENV` file (under `HOME`) is not visible, so a setting kept only there (`GOPROXY`, `GOPRIVATE`) does not apply in the uncached run, while one passed as a step variable does; the sandbox has no network namespace, so a step can still reach a server on the host's loopback or an abstract Unix socket, which could hold state; and a gate that is killed leaves its run's directory under `<gate cache>/sandbox/`, which no later run reuses (each name is new) and the gate prints when it cannot remove it (`gate: the merge sandbox's run directory ... was not removed`).
  - *Cost.* Measured 2026-11-05 on this 16-CPU host, interleaved, each side with its own caches, against f830a312 (the uncached run on the host); the 1-minute load was 13 to 45 throughout, so there is no speed verdict (gate-testcache-gap cost-r6.log). With the inner tier replayed, the uncached run took 333.7 s (load 22 at start, 13 at end) and 335.1 s after, against 277.4 s (load 16 to 22) and 265.4 s (load 13 to 31) before; the whole `--merge` took 347.9 s after against 266.9 s before. The steps start 23 to 28 s into the run (the export, and an empty build cache) against 2 to 4 s. With an empty build cache the steps compile everything again: the host step used 1,080 to 1,100 s of CPU against 241 to 246 s, and `go test (other packages)` 1,275 to 1,286 s against 965 to 995 s, with a peak of 6.4 to 7.1G against 2.3 to 2.4G, close to the 8G step budget. The input contract (measured 2026-11-05, against cd112257, which bound the host's module cache and object store; load 15 to 80, so again no speed verdict; gate-testcache-gap cost-r7.log and check-cost-r7.log): `checkInputs` over `/usr` and `GOROOT` took 0.69 to 0.78 s (five runs, load 17), the export 1.42 to 1.49 s and the module seeding (8 files) 0.11 to 0.22 s (three runs each). The uncached run took 374.0 s (load 16 to 46) and 306.4 s (load 18 to 37) after, against 330.1 s, 305.9 s and 302.8 s before (load 15 to 64); `go test (other packages)` peaked at 6.6 to 6.7G after against 6.7 to 7.3G before.
- **Environment.** Each step gets a stable `TMPDIR` under the caller's temp directory, unique to its checkout and step. After the step's process group or cgroup is stopped and its output is drained, the gate removes that directory; a cleanup error fails the step. The stable path lets Go's test cache reuse tests that read `TMPDIR`, while files created by a killed process do not survive the step. Every step, and every tool query of a fingerprint, receives only the variables `internal/testinputs/testenv` names, as Bazel's strict action environment and Nix's pure builds pass only declared variables: `PATH`, `HOME`, `TMPDIR`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, the go command's settings, the Go runtime's variables and `ERGO_TOOL_VERSIONS`. A step's own settings come over them (`CGO_ENABLED=0` for the hermetic step). So the whole-gate key, which holds each of these variables set or not, covers all that a step can read from its environment. A step that declares an input variable outside the list fails: no step can receive it. The gate log prints the list once (`gate: steps receive only …`). Go test steps receive `ERGO_TOOL_VERSIONS`, a digest of the git and `sh` fingerprints and the values of every one of those variables, set or not. The gate derives it; it never passes the caller's `ERGO_TOOL_VERSIONS` to a step or a tool query. So every variable a step receives is a key input or derived from key inputs (`TestReceivedVariablesAreKeyed`). Observation records a read of it for every test that runs a program, so a Go test result cached under other tools or settings is not reused, and no other variable can reach a cached test. The `go` tool fingerprint of a cached step carries the same Go runtime variables: `GODEBUG=inittrace=1`, for example, changes what a Go program prints without changing its bytes. The runner sets umask 022 and `GIT_OPTIONAL_LOCKS=0`, and `GOGC=400` unless the caller sets `GOGC`.
- **Tool fingerprints.** A tool's fingerprint keys what the tool prints about itself (`--version`; for `go`, `go env` with the toolchain settings) and every byte the gate can locate that running the tool executes or loads, each under its absolute path:
  - `go`: the file PATH resolves to and the whole `GOROOT` that `go env` reports. That file may be a launcher that selects another toolchain (`GOTOOLCHAIN`); the reported `GOROOT` is the selected toolchain's, so its `bin/go`, compiler, linker and standard library are keyed.
  - `git`: the binary and its exec path (`git --exec-path`), whose helpers git runs.
  - Any other file that is not a script: the file.
  - A script (`#!`): nothing. A script can exec any file, and the gate cannot locate what it runs, so its fingerprint never matches a recorded pass, and every step that keys that tool runs. (Until 2026-10-26 a script inside an npm package, such as the `tsc` launcher, keyed its package closure; that rule went with the Node toolchain.)

  The bytes are keyed because another build that prints the same version must not replay a pass. The path is keyed too, never in place of the bytes, because the same build under another prefix may load its helpers from another place. Every installation is hashed again on every run: 0.6–1.0 s for all five tools of the time (go, node, bun, tsc and git) together and 1.6–2.6 s one tool at a time, at a 1-minute load of about 39 on this host's 16 CPUs (measured 2026-10-11, before the Node toolchain was removed; the three tools now keyed take at most that). The gate starts every fingerprint its steps name as soon as it starts, so this overlaps loading the files and the first steps. No digest is remembered between runs, so no file timestamp, which a coarse clock can leave unchanged across a same-size rewrite, decides whether bytes are hashed. On darwin the kernel kills a signed binary that was rewritten in place and run, and keeps killing that file after its bytes are restored, until a new file replaces it (measured on darwin/arm64, 2026-10-30): such a tool answers nothing, so its fingerprint differs from the one recorded with the same bytes, and every step that keys it runs. Not keyed:
  - the system shared libraries the dynamic loader maps (libc and the like), which belong to the operating system rather than the tool;
  - git subcommands found on PATH outside the exec path, which git looks up only when a command is not built in;
  - a wrapper named in `GOFLAGS` by `-exec` (which `go run` runs the program under) or `-toolexec` (which wraps every compile and link): the caller's `GOFLAGS` string is keyed, the wrapper's bytes are not, and the caller's `GOFLAGS` is empty here (the gate adds `-count=1` to it for its steps, which names no wrapper);
  - git configuration (`~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`, `/etc/gitconfig`), which can name programs git runs (`core.hooksPath`, `core.fsmonitor`, filters, `!` aliases) and change what tests see (`init.defaultBranch`): it is user state outside every tool installation, and isolating the tests' git from it (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`) belongs to the tests that run git.

  An installation the gate cannot read, or a tool that does not answer the gate's question within 10 s, never matches a recorded pass. The gate never waits on a tool longer than that deadline plus 1 s: at the deadline the tool is killed, and a process it started that still holds its output open is cut off 1 s later. That process is not killed and may outlive the question. Questions run in the gate's own process group, so terminal signals (Ctrl-C, a hangup, `nohup`) reach them exactly as they reach the gate.
- **Log identity.** The second line is `gate: head <sha> tree <tree> clean=<bool>`, so a log names the commit it checked. `clean=false` means staged, unstaged or untracked (non-ignored) changes, submodules included even when a submodule's `ignore` setting hides them from `git status`; the gate still runs, and the line says the log does not certify that commit alone. Each step line ends with when the step started, so a log shows its critical path.
- **Process smokes** that drive the CLI run as Go tests in `cmd/ergo` (`*_smoke_test.go` and `*_process_test.go`). Each one works in a private workspace whose files are copied in the test process; observation makes what the CLI reads there inputs of Go's test cache too.
- **Test addresses.** A test learns a server's address from the server: the server binds port 0 and reports the address it bound (an `onListen` callback, or the program's `listening http://…` line), as `net/http/httptest` does. A test that must name an address before the server starts, or that binds it again after the server released it to prove the release, must keep the kernel from assigning the port to any other socket in between. `internal/testport` reserves the port for the whole test (off Linux, `testport.Reserve` skips the test). No test closes a probe listener and hands its port on: another test can take the port in between (#112).
