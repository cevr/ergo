# Developer tooling

Every `ergo` command reads one `.ef` source through one front end, `internal/sketchfront`, which checks, formats and builds the language of [`docs/spec/`](spec/README.md). There is no manifest and no edition. One table in `cmd/ergo/commands.go` gives every command word one fate, and dispatch, `ergo --help` and the stubs read only that table.

A source that checks also has its pure tests and laws run in process, with no Go build ([testing](testing.md#check-time-evaluation)), and the envelope carries the `evaluation`. Exit 1 when the source does not check or an obligation is refuted, 2 when a defect stopped the evaluation, else 0 (a skipped, incomplete or not-run obligation leaves 0, since `ergo test` decides it; with `--strict` it is exit 1, naming each such obligation and its reason, and each machine law that passed with evidence `tested` (sampled runs, not a proof): a law that was not decided is not a pass) |

A command that does not run prints one line to stderr, `ergo NAME: ` and the text in the table, prints nothing to stdout and exits 1, before it reads its arguments: `ergo explain --help` prints the stub too. `ergo --help` lists only the commands that run. An unknown word is `unknown command X; use ergo --help`, exit 1. The [retirement record](receipts/retire-ef.md) lists what [#203](https://github.com/cevr/ergo/issues/203) restores.

Go is the only target. `--target` accepts only `go`, the default; any other value is the EF110 refusal. `--strict` and `--json` belong to `diagnostics` and `lint` (`--json` also to `run` and `test`), `--preset` to `lint`, `-o`, `--platform` and `-report copies` (one `COPY file:line:col form: why` line on stderr per `Append` and `Concat` site: in place, one extender or copy; [types.md](spec/types.md#bindings); and per Map or slice operand of a Go call: copy, no copy or shared, with the foreign facts on it, [interop.md](spec/interop.md#foreign-facts)) to `build`, `-work` to `build` and `test`, `--debug` to `build`, `run` and `test` (each links stripped unless it is given; compile-speed CS7; without it `run` and `test` also compile the program's own packages with the dev profile, inlining off and no DWARF, from Go text that is not run through go/format, while `build` always compiles as a release; test-speed FT5: without inlining a test run costs up to 20 % more instructions, which on the measured packages gives back at most 1.1 % of the compile it saves; the dev profile would lose only for a test run of about 35 G instructions under release, against 4 to 7 G saved per build), `--locked` to `build` and `run` (a stale or missing `ergo.laws` entry refuses the build; [runtime.md](spec/runtime.md#tests), Tests 10), `--go-trace` to `build`, `run` and `test` (the program links Go's tracer; `ERGO_GO_TRACE` picks a full trace or a flight recorder; [runtime.md](spec/runtime.md), Go's tools), `--seed` to `check` and `test`, and `--eval-steps` and `--eval-bytes` to `check`; any other option is unknown. Every command refuses an invalid invocation with exit 2: an unknown option (`unknown option X`, `bind` and `gen` too), an option given to a command that does not take it, a missing or extra source, a source without the `.ergo` extension, and an unsupported target or platform. A source path that names no file is an operational failure, exit 1.

## Platforms

The target list is darwin/amd64, darwin/arm64, linux/amd64 and linux/arm64 (`gobind.Platforms`). New Go bindings hold for this list ([interop](spec/interop.md#gos-standard-library), Platforms). Each command checks module bindings against its selected platform: `--platform OS/ARCH` (build only), else `GOOS` and `GOARCH` of the environment, each unset or empty one meaning the compiler's own. Thus `GOOS=linux GOARCH=arm64 ergo check DIR` checks the same binding platform as `ergo build --platform linux/arm64 DIR`. A binding that does not state that platform is S104: the diagnostic names the binding, its platforms and the target, and gives `ergo bind go <package>` to regenerate it for all four. No Go tool runs during this check. `ergo build`, `ergo run` and `ergo test` link for the checked platform. The go env file's `GOOS` and `GOARCH` are not read: the Go build action always states the platform, with `CGO_ENABLED=0`, so `ergo build --platform darwin/arm64` on Linux needs no C toolchain. The phone platforms ios/arm64, android/arm64 and android/amd64 (the Android emulator; `gobind.Phones`) are on the list too. A phone checks against the bindings of the platform Go's build constraints read it as: ios against darwin/arm64, android against linux/arm64 and linux/amd64 ([interop](spec/interop.md#gos-standard-library), Platforms). `ergo build --platform` for a phone writes the generated Go module and stops before the link, because the phone's packager links the program as a library with cgo and the platform's C compiler (a c-archive on iOS, a c-shared library on Android). On stdout it prints `WORK=DIR`, the module; `GO=FILE` and `GOROOT=DIR`, ergo's go command and the root that holds the patched compile (the only compiler that reads the module's IR bodies; stock Go stops at "missing function body"; the root's `bin` is the release's, so `GO` finds the patched compile only with `GOROOT` set); and `GOFLAGS=…`, the per-package `-gcflags` that hand each package its `ergoir.json`, then the build's `-tags` and the user's `GOFLAGS`. A packager runs `GO build` in `DIR` with that `GOROOT` and `GOFLAGS`, plus its own `GOOS`, `GOARCH`, `CGO_ENABLED=1`, `CC` and `-buildmode`. The go command builds ios/arm64 and android/amd64 only with cgo, so any compile for them needs the phone's C compiler. android/arm64 also compiles with cgo off. A `-gcflags` it passes for `.` on its own command line replaces the IR flag of the root. On a phone the program's `main` runs on a Go thread that the packager's host starts, not on the system's UI thread. A host module that needs the UI thread reaches it through its own Go code. `-o` and `-go-text` are refused for a phone, and `ergo run` and `ergo test` refuse a phone as the platform from `GOOS` and `GOARCH`. A platform outside the list is the EF110 refusal, `unsupported target go on windows/amd64; the platforms are darwin/amd64, darwin/arm64, linux/amd64, linux/arm64, ios/arm64, android/arm64, android/amd64`, exit 2, and nothing is built. The platform is part of the Go build action, which Go's action cache keys, and the executable's Go build settings (`go version -m`) name it (`GOOS`, `GOARCH`, `CGO_ENABLED=0`); the emission key does not hold it, because the emitted module is the same for every platform: one module serves all four links (`TestBuildCrossCompilesEveryPlatform`). The default output is `dist/NAME` for every platform, so a cross build names its file with `-o`.

**CPU level** (U3 CPU-LEVEL). `ergo build --platform OS/ARCH/LEVEL` builds for a CPU level of the architecture, spelled as an OCI platform's variant and as Go's `GOAMD64` or `GOARM64`: `linux/amd64/v3` (v1 to v4), `darwin/arm64/v8.2,lse` (v8.0 to v9.5, with `,lse` and `,crypto`). `ergo run` and `ergo test` take the level from `GOAMD64` or `GOARM64` of the environment, as `build` does when `--platform` names none; with neither, Go's default, v1 or v8.0, so a build that names no level is the same as before. A spelling the architecture has no such level of is an invalid invocation (exit 2). The level chooses instructions only: the emitted module is the same at every level (a float product rounds, [types](spec/types.md), Numeric types 5, so no level fuses a multiply-add and a float result or a law verdict is the same), and the level keys the Go build action, the direct path's compiles, the pin sets' names ([build](spec/build.md), Pin archives) and the warm answer (`TestBuildIdentityCarriesLevel`). A binary built at v3 refuses to start on a CPU without AVX2, BMI2 and FMA, with Go's own message. A counted receipt (`scripts/opcount`) records the level it built at (`host.level`). The pin sets are made at Go's default levels; another level compiles std and the runtime once, to the same bytes a set would hold.

## Native build path

`ergo build`, `ergo run` and `ergo test` link the generated module without the go command: `internal/sketch/build/direct.go` runs Go's compiler and linker itself (`go tool compile`, `go tool link` with an import configuration), with the exact flags cmd/go uses for the module under `-trimpath`, from an action cache under the emission cache root (`go/plans`, `go/actions`, `go/blobs`). The key of a compile holds the compiler's content digest, the toolchain version, the target and its level (`GOAMD64`, `GOARM64`), the import path, `-lang`, each file's trimmed name and content, and each import's export data digest; the key of the link holds the linker's digest, the target, the C compiler name, the build information and every linked archive's digest. The module's directory is no input: `-trimpath` writes it out. A plan, keyed on the go command, its environment, the go env files, the go.mod files, the tags and the standard imports, records what `go env` and `go list -export` answer once: the toolchain, the target and a copy of each standard archive. An unchanged build then starts no go command and links nothing; it copies the cached executable. An edit compiles the packages whose inputs changed; a body edit that keeps a package's export data does not recompile its importers.

The executable equals go build's but for the build ID and what the linker derives from it (the GNU build ID note on ELF; LC_UUID and the ad hoc signature on Mach-O): `TestDirectMatchesGoBuild` (in `internal/sketchfront`, since it lowers Ergo programs; `internal/sketch/build`'s own tests import no part of the checker, so a checker edit does not rerun them) checks every example program and seeded generated ones, and `TestDirectRebuildsOnEachInput` edits each key input and counts the actions that run again. The direct path refuses what it does not key or reproduce, and go build then builds: cgo, assembly and other non-Go files, `//go:debug`, a go.mod with `godebug`, `toolchain` or a require that no replace maps to a local directory, a go line that is not the toolchain's language version, `default.pgo`, a non-empty `GOFLAGS` or `GOEXPERIMENT`, `GOFIPS140`, a development toolchain, and a target outside linux and darwin on amd64 and arm64. Any failure on the direct path (a compile error, a blob the trim took) also falls back to go build, which reports the error. `//go:embed` takes the direct path: `internal/sketch/build/embed.go` resolves each pattern on every build by cmd/go's rules (a walk skips `.` and `_` names unless `all:`, version control directories, nested modules and symbolic links; an invalid name, a match in another module or through a symbolic link, an irregular file, an empty directory or no match is go build's error to report), writes the `-embedcfg` file, and keys the compile on each embedded file's name and content, so adding, removing, renaming or editing an embedded file compiles the package again. `TestDirectEmbedMatchesGoBuild` checks this against go build on seeded trees; a non-ASCII name is left to go build. A compile's back end runs on `-c = min(4, max(2, GOMAXPROCS / compiles in flight))` goroutines, counting the compiles of every ergo process with the same cache root (a flocked slot file each in `<cache>/compiling`; a slot whose owner died is removed by the next count): one compile on an idle host keeps cmd/go's `-c=4`, and once half as many compiles run as there are processors each takes `-c=2`, which on the IR path does 2.4 % to 6.9 % less work than `-c=4` and 4.8 % to 5.8 % less than `-c=1` (test-speed FT5b). `-c` changes no compiled byte, so no key holds it. `ERGO_GO_BUILD=go` selects go build, the reference path, for every build; `-work` prints `LINK=` with how the build linked. The output of a direct build is a hard link of the executable's blob in the store, read-only (mode 0555); on another file system than the cache it is a copy. A request that changed nothing since its last answer is answered from the store with no parse, check, compile, link or process ([build](spec/build.md#warm-answer)); `ERGO_BUILD=full` selects the reference path, which always does the work.

Measured on 2026-11-11 on the exe workbox (user-mode instructions of the whole `ergo build` process tree, millions, go build against direct; shared host): `lookup` warm 934 / 513, warm to a new output path as `ergo run` builds 2,240 / 507, comment edit 983 / 546, body edit 2,693 / 2,305; `deploys` warm to a new output path 2,780 / 992, body edit 5,697 / 5,415. A cold build compiles the standard library either way (about 166,000). What remains is the Ergo check (410 for `lookup`, 927 for `deploys`) and, after an edit, the compile of `main` and the link (about 1,300); `-ldflags=-s -w` takes about 590 off the link, and every program links the 203 standard packages (93 MB of archives) the runtime imports.
## Go toolchain

Ergo manages its Go (owner, q136, 2026-11-12). Each ergo binary pins one Go release, `toolchain.Version` in `internal/toolchain` (go1.27.4), and `ergo version` prints it. go.mod's `toolchain` line names the same release (`TestGoModPinsTheRelease`), so the go command builds and tests ergo itself with it on every host, and the IR patch is ported to that one release. `ergo build`, `ergo run`, `ergo test`, `ergo bind go` and `ergo get` run the go command that `ERGO_GO` selects:

- unset or `managed`: the pinned release. The first build downloads it as GOTOOLCHAIN does (`go help toolchain`): the module `golang.org/toolchain@v0.0.1-<version>.<goos>-<goarch>` for the host's platform, from `GOPROXY` (default `https://proxy.golang.org`; a list with `,` and `|` as in Go; `direct` is skipped, because a toolchain comes only from a proxy; `off` fails at once). Before it uses a byte, ergo proves the zip's `h1` hash with the checksum database (`GOSUMDB`, default `sum.golang.org`): it checks the signature of the signed tree head with the database's key and proves from the log's tiles that the record is a leaf of that tree (RFC 6962; the protocol of `golang.org/x/mod/sumdb`, in process, with the standard library only). A wrong hash, a bad signature, a record the tiles do not prove, a cut download and a zip entry outside the module are refused, and nothing is installed. `GOSUMDB=off` is refused: ergo never installs an unverified toolchain. `GONOSUMDB`, `GOPRIVATE` and `GOINSECURE` do not apply.
- `system`: the go command on PATH, as before ergo managed Go.
- any other value: the path of a go command.

The release is installed under ergo's cache directory (the emission cache's root, [runtime](spec/runtime.md), Emission cache), never in Go's module cache:

```
<cache>/toolchain/<version>.<goos>-<goarch>/release   the GOROOT
<cache>/toolchain/<version>.<goos>-<goarch>/lock      the install lock (flock)
<cache>/toolchain/<version>.<goos>-<goarch>/tmp-*     an install in progress
```

An install downloads into `tmp-*`, verifies, unpacks into another `tmp-*` (the commands of `bin/` and `pkg/tool/` made executable, as cmd/go does) and renames it to `release`, under the lock. So `release` names a whole toolchain or nothing, two ergo processes that start at once download once (the second waits for the lock and finds the release), and an install that died leaves only `tmp-*`, which the next install removes under the lock. With a warm cache, a build reads no network, offline too; offline with a cold cache, the build fails and names `ERGO_GO=system`. A build with the managed release runs it with `GOROOT` set to the release and `GOTOOLCHAIN=local`, so neither the user's `GOROOT` nor a toolchain line chooses another Go. A later artifact built from the release (the IR tier's patched compiler, q131) goes beside `release` as `patched-<digest>`, keyed by its patch digest, under the same lock. The emission cache's trim reads only `modules`, `staging` and `private`, so it never removes a toolchain. There is no command that removes an old release yet. The pin archive sets (prebuilt std and runtime archives and the patched compile) install beside the releases as `toolchain/pins/NAME`, fetched from `ERGO_PIN_URL` when it is set and verified against `toolchain/pin/lock` ([build](spec/build.md#pin-archives)).

### The patched compile (IR)

Every `ergo build`, `ergo run` and `ergo test` lowers through typed IR (plan-tier §1.1, IRT0b): `sketchfront.Build` with `IR` uses `lower.LowerIRSplit` (the package split of `lower.LowerIR`, and of `LowerIRTests` for tests; [Package split](#package-split)), and each Go package of the module is compiled with `-ergoir ergoir.json` from its folder, a flag only ergo's patched `cmd/compile` reads. The patch is `toolchain/ir/go1.27.0.patch`, embedded in ergo (`toolchain/ir`). `toolchain/ir/lock` records its sha256 and one `port <release> <patch>` line for each Go release it is ported to (a row of `toolchain/ir/ports.md`). On a build, ergo takes the GOROOT of the release it runs (the managed one, or what `go env GOROOT` reports in a module with the generated modules' go line, so `GOTOOLCHAIN` picks the release a build would run; the answer is kept beside that module under a key of the go command's file, the go variables and the go env files, so only the first build runs `go env`), and `internal/toolchain.Patch`:

- refuses a release the lock does not port (`Go go1.27.1 has no port of the IR compiler patch (toolchain/ir/lock ports …)`), and a patch whose content is not the lock's;
- else builds the compile once, under the release's install lock, into

```
<cache>/toolchain/<release>.<goos>-<goarch>/patched-<key>/goroot   the release with the patched compile
<cache>/toolchain/<release>.<goos>-<goarch>/patched-<key>/src      the patched files
```

`key` digests the patch and the release's GOROOT; the directory names the release and the host, since `compile` is a host program for every target. The patch is applied in process (`toolchain.ApplyPatch`: a hunk applies where its old lines stand, at its line or the nearest one, never in part; `scripts/irport` applies it with the same function), and `compile` is built by the release's own go command with `go build -trimpath -overlay` from the release's source: no copy of the release, no git. `goroot` holds a symbolic link to each entry of the release but `pkg/tool/<goos>_<goarch>/compile`. The first build costs a compile of `cmd/compile` (100 s of CPU, measured, cold Go build cache); with a warm Go build cache it is a link (1.3 s). A build prints `ergo: building the IR compiler for <release> (once per Go release and patch)` then.

The patched compile without `-ergoir` compiles as the stock one does (stock equivalence, checked on every port) and prints the stock `-V=full` line, so Go's build cache shares the standard library and the runtime packages with stock builds. A package's compile is keyed by its inputs: on the direct path by the compile's digest, its Go files and its IR file's content (`ergoir` in the action key); on go build by the `-gcflags` text, which names the module's directory in ergo's emission cache, keyed by what the module is emitted from. `main.go` carries no digest of the IR (batch-18 M2: one key). A user's `-gcflags` in `GOFLAGS` is replaced by ergo's on go build.

Building ergo itself from source still needs Go. The gate and the CLI's tests run with `ERGO_GO=system` (the gate sets it unless the caller does), so no test downloads Go; `internal/toolchain` tests the managed path against a module proxy and a checksum database served in process.

## Which ergo a module needs

`ergo version` prints ergo's own version first (`--json`: `"version"`), then the Go release it pins. The version is the Go module version the go command stamped into the binary (`internal/ergoversion`): a tag when installed with `go install …@v1.2.3`, else the pseudo-version of the commit it was built from (`v0.0.0-20261117152120-c501620891c0`, with `+dirty` for a modified tree), else `devel`. A build with `-buildvcs=false`, which the gate's builds are, and a test binary are `devel`. The producer declaration of `ergo check` reports shows the same string.

A module's `ergo.mod` may hold one line `ergo VERSION` ([grammar](spec/grammar.md#source-files) rule 1, Which ergo): the lowest ergo that may build it. An older ergo refuses the module with one S108 at the line, which names both versions and the install command (`go install github.com/cevr/ergo/cmd/ergo@VERSION`; until the module path is `github.com/cevr/ergo`, build ergo from a clone at that commit instead); a newer one builds it. The highest line of the build list counts, a required module's included. A `devel` ergo accepts every line and says so once on stderr, so the gate's own builds accept every line. ergo never switches to the version a line names.

## Recorded cases (`ergo test --cases`)

`ergo test PKG --cases DIR` runs a program's recorded cases: it reads every case folder of DIR, builds the main package PKG into a private temporary folder (as `ergo run` does: never `dist/`, the working directory or the module), and runs each case against the built program, byte for byte, by the rules of [examples/README.md, Cases](../examples/README.md#cases): `args`, `stdin`, `env` and `setup.sh` in, `expected.out`, `expected.err` and `expected.status` out. Each case runs in a fresh empty folder that is also its `HOME`, with exactly `PATH`, `HOME` and its `env` lines, in its own process group, under the program memory bound (`ERGO_PROGRAM_MEMORY`, 2 GiB by default; [Test memory](#test-memory)); it has no deadline. It prints `ok NAME` or `FAIL NAME: WHAT` with a unified diff of each stream that differs, then `PASS (N cases)` or `FAIL (F of N cases)`. The exit status is 0 when every case passes; 1 when a case fails, when DIR's layout has a problem (a file a case may not hold, a case with no `expected.out`), when DIR holds no case (no tests is red), or when PKG does not check or build; 2 for an invalid invocation (`--cases` with no folder or twice, a pattern, `-o`, `--emitted`). Cases sit beside their binary, `cmd/NAME/cases/`, as a module may hold several binaries. The runner is `internal/cases`, which the examples runner also runs, so the two give one verdict (`TestCasesAgreeWithTheRunner`). A std `clitest` package, once std `exec` test hosts can run a built binary, is the way to reverse this flag.

## Downstream check

Ergo builds pinned commits of the repositories it must not break, as Rust's `cargotest` builds pinned crates in rustc's CI. `downstream/pins` holds one line per repository, `NAME URL COMMIT`. COMMIT is a full commit hash, never a branch or a tag (`models/downstream`, `FloatingPin.NeverArrives`: with a floating pin no breaking change can land safely).

- `go run ./scripts/downstream fetch [NAME...]` is the only command that reads the network.
  - It brings each pinned commit into the cache, `downstream/NAME@COMMIT` under the user's ergo cache (`$XDG_CACHE_HOME/ergo`, else the user's cache directory; `ERGO_DOWNSTREAM_CACHE` moves it, `-cache DIR` too).
  - Each entry is a clone with no blobs until checkout (`--filter=blob:none`), checked out detached at the commit, with its `.git` removed. It is renamed into place, so an entry is whole or absent.
  - A pin already in the cache costs no Git work.
  - The integrator runs it before a batch gate.
- `go run ./scripts/downstream [NAME...]` reads no network. For each pin it copies the cached tree to scratch and runs these legs with the checkout's `bin/ergo` (`-ergo`), never an ergo found on `PATH`:
  - `ergo check ./...`;
  - `ergo test ./...`, whose `skip ` lines must equal the tree's `expected-skips`;
  - `ergo build` of each `cmd/NAME`;
  - `ergo test ./cmd/NAME --cases cmd/NAME/cases` ([recorded cases](#recorded-cases-ergo-test---cases)) where that folder exists.

  It prints `ok NAME COMMIT` or one `FAIL NAME COMMIT: LEG: WHY` line per failed leg with the leg's output. A pin that is not in the cache fails with `run go run ./scripts/downstream fetch`; it is never skipped.
- A pin's own `ergo` line is not enforced: the checkout's ergo is newer by design.
- Exit codes: 0 when every pin passes, 1 when one fails, 2 for a usage error or a malformed pins file.
- With no pin it prints `downstream: 0 pins` and passes, but only while `downstream/moved` holds no path. Once a path has moved, zero pins is red.
- The gate's full tier runs it as the step `downstream`, after `build bin/ergo`. Its key holds `downstream/`, the runner's closure and `bin/ergo`'s bytes. The cache is not keyed: each entry is the pinned commit's tree.
  - It does not run in the fast tier, which cannot promise the cache and stays offline.
  - A lane that changes the language runs `go run ./scripts/downstream NAME` by name.
- A breaking change follows the protocol `models/downstream/pins.ergo` checks:
  - The unit that breaks a downstream repository ports it on that repository's `ergo-next` branch, and moves its pin to that commit in the same ergo commit.
  - Once ergo's main is pushed, the downstream's main takes `ergo-next` and raises its `ergo` line.

`downstream/moved` holds one `PATH TREEHASH REPOSITORY` line for each path that moved to its own repository at the source head F. TREEHASH is `git rev-parse F:PATH`.

- `TestMovedPathsAreFrozen` (`internal/residue`) fails when `HEAD:PATH` is another tree: `PATH moved to REPOSITORY at F; make this change there`. So no lane's late commit to a moved path is lost silently.
- A path that is gone passes (the delete of unit D1).
- With no line the test passes and says so.
- The integrator fills the file at F and sets `movedAt` in `internal/residue/moved_test.go` to F.

## ergo get

`ergo get MODULE[@VERSION]...` (MD2) requires each module in the Ergo module at or above the current folder ([grammar](spec/grammar.md#source-files) rule 1, Required modules). It runs `go get` with the selected go command in the module root (first `go mod init NAME` when `ergo.mod` has no `go.mod` beside it), so `go.mod` pins the module, `go.sum` holds its two hashes and Go's module cache holds its copy. The fetch is Go's: `GOPROXY`, `GOPRIVATE`, `GONOSUMDB`, `GOFLAGS` and the checksum database apply, and VERSION is any query `go get` takes. Then it reads each module as an import does, with no process: the copy's hash must be go.sum's, and an Ergo module's `ergo.mod` must name its path. When one fails, ergo get puts `go.mod` and `go.sum` back as they were (it removes a file that was not there), prints why and exits 1. A module with no `ergo.mod` is a Go module: it is required and printed as one, and `ergo bind go` binds its packages. On success it prints `required PATH VERSION` per module. `MODULE@none` is a usage error (exit 2): `go get` removes a requirement. `go mod tidy` drops a requirement that no Go file imports, so it drops an Ergo module's; a module with Ergo requirements does not run it.

## ergo work

`ergo work COMMAND [ARGS...]` (SEMWS WS0) runs `work` from `PATH` (the npm package `@cvr/work` installs it) with the arguments as they are, with this process's standard streams, and exits with its status; with no `work` on `PATH` it says how to build one and exits 1 (`TestWorkRunsErgoWorkFromPath`). `work` is the binary of module `work` (`modules/work`, built from `examples/work`): copy-on-write workspaces of any Git repository (SEMWS WG0: it needs no `ergo.mod`, and `work.toml` is its configuration), `init`, `new` (with `-from`, `-branch` and `-on`, a stack; it answers the workspace's path and id), `adopt`, `list`, `rm`, `gc`, `du`, `ready` (a snapshot and the branch handed to the parent, never to origin), `sync` (Git's merge of the parent's branch), `env`, `deps` (an install only when the lock file changed), `trust` (the hooks and install of `work.toml` run only once allowed), `doctor`, `refresh`, `bases`, `shell-init`, `import-rift`, and `merge-file`, the Git merge driver of the classes in `.gitattributes` (mutant ledgers by row, gate durations by key, allowlists by line, generated files kept whole) ([modules/work](../modules/work/README.md)). It is a binary of its own until the mixed binary links an Ergo module into `ergo` (capstone S1).

## Source admission

A command locates its source once (`internal/receipt.LocateSource`): the spelling is made absolute, which applies a `..` to the spelled name, and the links of that admitted path are then resolved. Diagnostics and `//line` directives name the admitted path; the bytes come from one non-blocking open of the resolved file (`internal/source.Open`), which refuses a directory, a FIFO or any other file that is not regular, so a FIFO swapped in after a stat never blocks. A source must have the `.ef` extension. An `ergo.json` beside a source is ignored.

A path that names a folder, and does not end in `.ergo`, is a package (196b U3; [grammar](spec/grammar.md#source-files) rule 1): the loader (`internal/sketchfront`, `CheckDir`) finds the nearest `ergo.mod` at or above it, reads every `.ergo` file of the folder in name order, and reads the local packages it imports, each once. Each finding then names its file relative to the module root: `lib/x.ergo:2:9: error S104: …` in text, and a `file` field in the check envelope and the report (omitted for a program of one file; additive). The build key holds a digest of each local package the program reaches, by admitted path and bytes, so an edit of an imported package builds again. `ergo test DIR` runs the tests of that package only, as `go test` does. `ergo test A B C/...` takes several targets (files, folders, patterns) and runs them in order, each under its own `package` line, a failing one not stopping the rest; `--law`, `--skip-law`, `--run`, `--receipt`, `--emitted` and `--explore` take one target, and a target named twice is a usage error. `ergo check A B C/...` takes several targets the same way: each target prints its check envelopes in order (a pattern one per package), a target that does not check does not stop the rest, and the run exits 1 when one failed. A file path keeps its one-file meaning: such a program imports std only. A package of another Ergo module is read from Go's module cache through a requirement in the `go.mod` beside `ergo.mod`, after its hash is checked against `go.sum`; the check runs no go command and reaches no network, and a module it cannot read names `ergo get PATH@VERSION` ([grammar](spec/grammar.md#source-files) rule 1, Required modules; MD1).

## Inspect

`ergo inspect deps DIR [--json]` (MD3) lists each required module the program reads, as `PATH@VERSION (Go trusted)` or `(Go not trusted)`, and below it each of its packages the program reads with the capabilities its exported functions need (`needs Console | go.Foreign`, `needs nothing`, or `not checked` when the program has diagnostics) and its uses of Go, one per line (`import go strings`, `extern go strings.ToUpper`). It is the list to read before a `trust go` line ([grammar](spec/grammar.md#source-files) rule 1, Trusted Go), so it prints also when the program does not check, and then exits 1. It starts no process.

`ergo inspect` prints one JSON object (`sketchfront.InspectGo`, the one core a later MCP tool prints too, #203) about what the program reaches of Go ([interop](spec/interop.md)). It reads the checker's model and the bindings' text only, and starts no Go process.

- `imports`: each Go package the program's packages import with `import go`, once: `path`, `provenance` (`go1.27 std (embedded)` for Go's standard library, or `module <path> <version>` from the binding's stamp, IG7), and `refused`, each declaration the binding does not import with its `reason`.
- `functions`: each function of the program with an Ergo body (std excluded), with `package`, `name`, `file` (the file name in its package; absent for a program of one source text), `line`, `reach` and `waits`. `reach` are the Go symbols the function's code can reach: the Go functions, methods and interface operations that its body and the function literals written in it call, name as a value, or put into an operation type, and those of each function of the program that it reaches the same way. A user extern (Level 2) reaches its Go target. A std function is a leaf. `waits` are the uninterruptible host waits among them.
- `symbols`: each Go symbol reached, with `target` (`net/url.Parse`, `net/url.URL.Hostname`), `go` (the declaration as Go writes it, from the binding), `ergo` (its Level 1 Ergo signature), `tier` (`pure`: the reviewed list, no `go.Foreign`; `foreign`: `needs go.Foreign`), `provenance` and `wait`: `none` for a pure call, `interruptible` for a foreign call that gets the task's context (IG10), `uninterruptible` for any other foreign call, which an interruption reaches only after Go returns.
- `rewriteSites`: each rewrite site of the root package's run build ([types.md](spec/types.md), Laws 14; [runtime.md](spec/runtime.md#tests), Tests 10), with `file`, `line` and `column` (the window's first call), `law` and `provider` (package-qualified, as `ergo.laws` names them), `instance` (the site's constants, `(c, …)`, or empty), `verdict` (the ledger entry's: `proved`, `tested`, `skipped`, or empty when there is none), `ledger` (`current`, `stale` or `missing`) and `applied` (whether the build rewrites the site: a current, proved entry only). It lowers the program in process. `ergo check` reports the rewrite verdict text as the skip reason of each rewrite law's obligation, since check-time evaluation does not run one.

Not followed: a call of a function value or of an operation of an operation-type value whose provider a `with` chooses; the provider's functions are reached where its value is made.

## Check envelope

`ergo check` prints one JSON object: `schemaVersion` (11), `checked`, `target`, `revision` (a SHA-256 digest that identifies the source), `diagnostics` (at most 100, each with `code`, `message` and a UTF-8 byte `span` with one-based line and column), `diagnosticsTruncated`, the `producer` that made the facts, and the `snapshot` that binds the schema, revision, target and producer together. Producer identity follows the executing artifact: its digest when the executable can be read, and a process-scoped qualifier when it cannot. `ergo build` and `ergo run` acquire a producer identity only when they refuse a source. The emission cache keys on its own digest of the compiler executable, which needs no producer identity ([runtime.md](spec/runtime.md), Host and lowering notes).

When the source checks, the envelope also has `evaluation`, the result of running its pure tests and laws at check time ([testing](testing.md#check-time-evaluation)). A source that does not check has no `evaluation` key. The object has:

- `schemaVersion` (1), and `revision`, the digest of the text that the evaluation ran on, which equals the envelope's `revision`;
- `status`, the worst status of its obligations: `defect`, `refuted`, `incomplete` (a budget ran out), `skipped`, `passed`, or `none` when there is no obligation;
- `steps` and `stepsLimit`, `bytes` and `bytesLimit`: the work and the value bytes used, of their budgets (`--eval-steps`, `--eval-bytes`). `stepsLimit` is one case's: an obligation of `totalCases` cases may spend that many times it. They are counts, not times;
- `obligations`, one record per test or law run, in the order `ergo test` runs them. Each has `name` (`BurstThenWait`, `law RefillNeverOverfills`, `law Router.CanStop`), `status` (`passed`, `refuted`, `defect`, `skipped`, `incomplete` or `not run`), `site` (`file`, one-based `line` and byte `column`: where it was refuted, hit its defect or stopped, else its declaration), `steps` and `cases`. Then, when they apply: `reason` (why it did not pass, or what decided a machine law), `evidence` (`evaluated` for an example, `tested` for sampled cases, `proved` for every value of a listed domain or a decided machine law), `totalCases`, `seed`, `case` (the first bad case, one-based) with `arguments` (each `name` and `value` as an Ergo literal), `replay` (the `ergo test` command that runs the same cases, on each record that did not pass), `advice` on the record of a top-level rewrite law in scope ([types.md](spec/types.md#laws) Laws 14) whose `ergo.laws` entry is missing, stale or not validated (`law L is a rewrite in scope, and ergo.laws has no entry for it: it changes no code until ergo test's licence run validates it`, or `… and its ergo.laws entry is stale: …` or `… is tested: it changes no code until ergo test's licence run validates it`; LF6c; the ledger is read as a warm input, so a changed `ergo.laws` changes the answer), and `machine` for a reachability law: the search's `states`, `edges`, `depth` (the longest shortest run of a state seen), `checked` (the run length up to which every run was checked), `complete` (the search saw the whole graph it searched), `steps` (the step calls, replays included), `runs` (the generated runs, when the graph could not be listed) and `run` (the run that decided the law).

For a refuted law, `site` is the failing expression (or the reachability clause). The optional `declaration` is the law's declaration as related information, with the same `file`, `line` and `column` shape. Native `ergo test` uses the same primary site and prints the declaration on an indented related line. A law run that did not run because the law verdict store held its verdict (below) has `cached: true`, `steps` 0, and the stored `evidence` and `cases`.

## Law verdict store

A law run is judged once per set of inputs (v1 audit 3, F7: before, an unchanged law ran at check time, again in `ergo test`, and again in the ledger's check build). `internal/sketch/lawcache` keeps the verdict of each law run that held. The key is the run's label (`law Counter.Joins for Tally`), `lower.TargetDigest` (the tokens of the law's declaration, of each bound provider's type, of every function, type and package `let` its conversion and constructor reach, of each reached type's generator (its constructor, and an operation type's builder), and whether each provider's construction is closed; no position, space or comment), or, for a run under a named context (`law Counter.Joins under Live`), `lower.ContextDigest` (the law's owner, the tokens of the context's declaration and of the contexts it embeds, every function, type and `let` their provider expressions reach, each provider constructor among them, the acquired providers' conversions, and the generators of the types reached), the seed, the state budget, and the compiler's identity, which stands for the evaluator, the lowering and the prover. A machine's search (`law Switch.Lights`) is keyed by the machine's declarations (its type, its initial value, its step and start, its laws and the functions they name), and per runner: check time reports its search (`machine` in the JSON) and the test build its own line, so each reuses only its own verdict. A cached search prints its witness again. The ledger's check run of a law is keyed the same way, plus the site instances it takes, the contexts it runs under, and whether it runs as a post law. `ergo check`, `ergo test` and the ledger writer read the store before they run a law, and write each verdict that held: a later run with the same key prints `ok LABEL (TEXT) (cached)` and does not run (as `go test` prints `(cached)`), and the ledger's check build is not built when every law it would run is cached. An edit of any declaration a law reads makes a new key, so that law runs again; other laws stay cached. Only a pass is stored: a refuted law, a defect, an exhausted budget and a skip run every time. Not stored: every run of `ergo test --receipt` or `--explore`. The store is `laws/v1/` under the emission cache's root (`$XDG_CACHE_HOME/ergo`, or `ERGO_CACHE`), one small file per key, written by one rename and marked used (its modification time, at most hourly) when a command reads it. The emission cache's trim bounds it: a due trim removes the verdicts unused for a day and a crashed writer's temporary files, and a command that wrote verdicts counts them and, past 65,536, removes the least recently used, the whole excess in one pass. A verdict is read whole and never held, so a removal needs no lock: a command that misses it runs the law again. A compiler with a process-scoped identity (`go run`, `go test`) keeps it in memory. `ERGO_LAWCACHE=off` turns it off: every law runs, nothing is stored. The examples runner's check leg sets it, so its agreement check compares check-time evaluation with a native run, never a verdict with itself.

## Diagnostic reports

`ergo diagnostics --json` prints the report (`schemaVersion` 3: version 3 adds the lint fields, a finding's `fix`, the edit `ergo fix` applies, and a rule pack finding's `related` places and `suggestions`). Its `source` identifies the file with a canonical escaped `file:` URI and the origin `disk`. It includes the source `revision`, the `target`, the `checked` state, the `strict` policy, `policyPassed`, exact `totalCounts` and `returnedCount`, `truncated`, the `producer` and `snapshot` of the check envelope, and the findings. Every finding keeps its UTF-8 byte `span` and reports `code`, `origin`, `severity` (`error`, `warning`, `information` or `hint`) and `message`. A finding with a source location also has a zero-based UTF-16 `lsp.range`; `locationAvailable` is false for a finding without one, such as the unsupported target refusal.

**Finding order.** The report lists its findings, in JSON and in text alike, in this order: findings with a location first; then by `file` (byte order of the path relative to the module root, the empty `file` of a one-file program first); then by byte `offset`, span `length`, `code` and `message`. A finding without a location comes last. Identical findings (same code, file, message and span) are listed once. So the findings of one file of a package are never interleaved with another's (`internal/report` `TestReportOrdersFindingsByFileThenOffset`).

Errors always fail policy. Strict mode changes only the policy decision for warnings; it does not change a finding's severity. Text output prints one finding per line with one-based UTF-16 lines and columns. Exit 0 means policy passed. Exit 1 with a JSON report on stdout means the source failed policy; exit 1 without a report is an operational failure, explained on stderr. `ergo diagnostics --help` documents the same.

The report merges lint advice ([Lint](#lint)) after the compiler's findings, in the same order among themselves: a lint finding has `origin` `lint`, its `rule`, and its configured `severity`. The report adds `lintComplete` (every enabled rule completed; false on unchecked source) and `suppressions`: each admitted directive's `rule`, `status` (`applied`, `unused` or `not-evaluated`), `reason` for not-evaluated, the directive's `span` and `range`, and the `line` it covers. An incomplete lint run fails policy.

## Lint

`ergo lint` runs the lint rules (`internal/sketch/lint`) over checked source. A rule reads the checker's facts (resolved objects, types, rows and footprints) and never an identifier's spelling; `internal/residue` `TestLintRulesReadNoSpelling` holds every rule to that. `ergo check`, `build`, `run` and `test` never run lint.

- **Rules.** The `recommended` preset is on by default; it holds the rules whose published precision is at least 0.80, and none reaches that yet, so by default no rule runs. `silent-catch` (L101, warning): a catch arm that binds no failure value it reads, never returns or fails through `try`, and calls nothing that adds to its frame's footprint. `foreign-error-public` (L102, warning): an exported function with a body whose written `fails` row holds `go.Error` (map it to a closed union at the boundary, [interop](spec/interop.md)).
- **Runner codes.** `L000` is a lint-runner failure: a rule that panicked or reported outside its file. Its findings are dropped and the run is incomplete. `L001` is an invalid suppression: malformed, an unknown rule, a reserved namespace (`ergo/`, `builtin/`), or unused. Both are errors; no configuration or directive changes them. Compiler diagnostics are never suppressible.
- **Configuration.** `ergo.lint.json` beside the module's `ergo.mod` (searched upward from the linted path) is read when present: `{"version": 1, "rules": {"silent-catch": "off", "foreign-error-public": {"severity": "error"}}}`. Severities are `off`, `error`, `warning`, `information` and `hint`. Settings apply in layers: `recommended`, then `extends` in order, then each `--preset` in order, then `rules`; a setting with no severity turns an off rule on at its default. A preset applied twice (`recommended` is always the first layer), unknown fields, duplicate keys, trailing data, an unknown rule or preset, options for a rule that takes none, invalid options and `packs` refuse the configuration: exit 2. Rule packs run only from an explicit selection (`--lint-config`, `--rules`; Packs below). A rule's options are an object (`{"severity": "warning", "options": {"max": 15}}`); a later layer's object replaces an earlier one whole.
- **Precision.** Every built-in rule publishes a precision (`internal/sketch/lint/precision.go`, LINT-HYGIENE): the lower of its precision on its labelled corpus and on a held-out read sample (findings on code never used while writing the rule, each read against the source, every miss kept with what it was), rounded down and capped at 0.95. A finding prints it after its message (`(p0.13)`) and carries it as `precision` in the JSON report; `ergo lint rules` prints each rule's `precision` and its `sample`. A rule with no read sample has no number. A rule is in `recommended` only at 0.80 or above (`TestDefaultRulesMeetTheBar`). ## Formatter

`ergo fmt` formats with the one formatter and reports one formatter identity, at the top level and per file. `--stdin` writes only formatted source to stdout. Human file statuses and operational errors go to stderr. File `--json` and `--check --json` reports use stdout and keep stderr empty; `--stdin` with `--json` is an invocation error. Exit 0 means formatting completed (or the check found no differences), exit 1 means the check found differences, and exit 2 means an invocation, syntax, I/O, stale-source or limit failure.

`ergo fix [--check|--dry-run] [--json] [--std DIR] [--go] PATH...` first writes the declared implementations the old method-set rule used (`implements I` on a type, `..I` in an operation type; `--std DIR` also edits the standard library's source, `--go` the Ergo programs held in Go string literals). Then, for each PATH that is a `.ergo` file or a folder holding one, it writes the `fails`, `needs` and `takes` clauses that the signatures of the file, or of the package folder and the local packages it imports, are missing (explicit local signatures, owner 2026-11-12). It only adds clause elements and the imports they need, writes each changed file once by rename, and prints one line per widened signature, public contracts first under "public contract widened:". `--dry-run` writes nothing; `--check` writes nothing and exits 1 when a signature would change. Any other diagnostic goes to stderr and the exit status is 1. `check`, `build` and `test` never run it ([diagnostics](spec/diagnostics.md#s102-missing-capability)).
`ergo fix FILE|DIR [--check] [--json]` writes the `fails` and `needs` clauses that the signatures of a file, or of a package folder and the local packages it imports, are missing (explicit local signatures, owner 2026-11-12). It only adds clause elements and the imports they need, writes each changed file once by rename, and prints one line per widened signature, public contracts first under "public contract widened:". `--check` writes nothing and exits 1 when a signature would change. `--lint` then applies the safe lint fixes of the module's lint configuration ([Lint](#lint)) and prints one line per fix; with `--check` it exits 1 when one would apply. Any other diagnostic goes to stderr and the exit status is 1. `check`, `build` and `test` never run it ([diagnostics](spec/diagnostics.md#s102-missing-capability)).

| Boundary | Limit |
| --- | ---: |
| File count | 100 files |
| Input per file | 2 MiB |
| Input per request | 8 MiB |
| Formatted output per file | 4 MiB |
| Formatted output per request | 16 MiB |

Completed file entries include `path`, `requestedPaths`, digests, `changed`, `written` and `completed`; a failed entry never receives a successful human status. The stable operational codes are:

| Code | Meaning |
| --- | --- |
| `EFMT_INVOCATION` | Incompatible options, missing input, or file-count admission failure |
| `EFMT_PATH` | Empty, non-`.ef`, or otherwise invalid path |
| `EFMT_READ` | The source could not be admitted or read |
| `EFMT_SYMLINK` | A mutating request named a symlink leaf |
| `EFMT_SPECIAL_FILE` | A directory, FIFO or other non-regular source |
| `EFMT_INPUT_LIMIT` | A per-file or aggregate input budget is exceeded |
| `EFMT_OUTPUT_LIMIT` | A per-file or aggregate formatted-output budget is exceeded |
| `EFMT_SYNTAX` | The source does not parse |
| `EFMT_FORMAT` | Any other formatter failure |
| `EFMT_ALIAS` | Several requested names resolve to one underlying inode |
| `EFMT_STALE` | The source identity or exact bytes changed before replacement |
| `EFMT_WRITE` | A temporary-file, permission, rename or other replacement failure |

Mutating paths keep the requested display spelling while the operating system resolves ancestor symlinks and `..` components. The leaf must stay regular and not a symlink at each replacement check. Lexical spellings that resolve to the same path are deduplicated; distinct hardlink or inode aliases in one request are rejected. A requested hardlink is replaced through an atomic same-directory rename, so that directory entry splits from unlisted hardlinks. A read-only regular file may be replaced when its directory is writable, and its permission, setuid, setgid and sticky bits are kept. These cooperative checks do not claim hostile-filesystem race protection or directory-fsync durability.

The formatter does not refuse invalid UTF-8. It formats such a source and writes the invalid bytes of comments and string literals back unchanged; an invalid byte where an identifier may start is the parse error S001, `EFMT_SYNTAX`. The earlier front end refused every invalid byte with EF001.

## Gate prerequisites

The gate needs Go and Git. Its steps build Ergo programs with that Go (`ERGO_GO=system`, [Go toolchain](#go-toolchain)). It needs no Node, Bun, TypeScript or Effect installation: since 2026-10-26 Go is the only target.

## Emission cache bound

`ergo build`, `ergo run` and `ergo test` emit each program's Go module into the emission cache ([runtime](spec/runtime.md), Emission cache). Its root is `$ERGO_CACHE` when that is set; a relative `ERGO_CACHE` is an error, as a relative `GOCACHE` is to the go command. Else the root is `$XDG_CACHE_HOME/ergo` when `XDG_CACHE_HOME` is absolute, else the user's cache directory with `ergo` (`~/.cache/ergo` on Linux). `ERGO_CACHE` moves only ergo's cache. `XDG_CACHE_HOME` also moves Go's default `GOCACHE`, so a test that set it would build Go from a cold cache.

**Tests and gate steps never write the user's cache.** On 2026-11-12, `~/.cache/ergo/modules` held 18,357 entries (20 GB, about 1.1 MB each, most of it the runtime copy), all younger than one day (measured). By the first source path in each manifest, 9,927 came from the example programs of checkouts (the gate's `examples (default)` step), 5,299 from scratch copies of the examples (mutant, coverage and check runs), 1,991 from programs that Go tests wrote into `t.TempDir()` and ran through the CLI (`internal/sketch/lower`, `TestErgoRun…`), and about 100 from programs made by hand (measured). The trim worked: its stamp was recent, and no entry was older than its one-day limit. An age limit cannot bound a cache that grows by 18,000 entries a day. So:

- Every test process sets `ERGO_CACHE` to a new directory under the temporary directory, and removes it when its tests end: `testinputs.Main` does it, and the guard `internal/testinputs/guard` makes every test package call it. Every ergo command that a test starts with the test's environment uses that directory. A test about the user cache sets `ERGO_CACHE` itself (`t.Setenv`). `cmd/ergo` takes the variable off again: its tests resolve the cache through `XDG_CACHE_HOME`, as a user's command does, with a private `XDG_CACHE_HOME` of their own, and `TestPackageNeverWritesUnderHome` checks that they write nothing under `HOME`.
- The examples runner (`scripts/examples`, the gate's `examples (default)` step and the mutant runner's example suite) gives each compiler command `ERGO_CACHE=<its scratch>/cache`, whatever the caller set, and removes it with the scratch when the run ends.
- Guards: `TestTestsUseAPrivateErgoCache` (`internal/residue`) fails when a test process resolves the cache to the user's; `TestFmtOrBuildFailureFailsOnlyThatProgram` (`scripts/examples`) fails when a compiler command of the runner gets another cache, or the run leaves it.
- *The rule that forgetting cannot bypass (Linux).* A test can start ergo with an environment it builds by hand and forget both variables. So `DefaultRoot` refuses, under a Go test, the user's cache: it walks this process and its ancestors through `/proc` (`internal/sketch/build/root_linux.go`). A process is a Go test binary when its program's name ends in `.test` or an argument is a testing flag (`-test.…`). For each one it reads `/proc/PID/environ`, the environment the test binary was started with, which no `os.Setenv` and no environment a test builds for its programs changes, and resolves the cache from it without `ERGO_CACHE` (`XDG_CACHE_HOME`, else `HOME`). When that is the root this process resolved, the command fails: `no cache directory for generated Go: ROOT resolves to the user's cache under the Go test pid N; a test builds in a cache of its own: set ERGO_CACHE …`. A program a test gives its own `XDG_CACHE_HOME` (the `cmd/ergo` tests) builds there. A user's command runs under no test, and walks a few ancestors' `cmdline` and `stat` (inferred: well under a millisecond). Guards: `TestForgottenCacheIsRefused` runs the rule over a proc tree it writes, in its own process, and over real processes, a test binary that starts the probe with only `HOME`; `TestTestBinaryIsNamedOrFlagged` checks both signs; `TestTestsUseAPrivateErgoCache` also checks that a test process with `ERGO_CACHE` cleared is refused. On other systems no process can read another's starting environment, so the private cache of `testinputs.Main` is the only rule there.
- Cost: a test process, and each examples run, starts with an empty emission cache. The runner took 0.7 s over one program with an empty emission cache and 0.3 s with a warm one (measured 2026-11-04, `tidewalk-replay`). The Go build cache keys each package by its directory, and an entry's directory is `modules/KEY`, so a new root costs a new compile of each program's runtime packages once per run (inferred). Each changed compiler changes every key anyway.

**The user's cache trims as Go's does, with a cap.**

- *Age.* A build that reuses an entry marks it used, through the entry directory's modification time, at most once per hour. A trim removes the entries that no build used for one day (`unusedLimit`), the staging directories older than one hour, and the private roots no build used for one day. A build starts a trim at most once per hour per cache (`trimInterval`), behind the stamp `trim.txt`; the stamp's lock claims a pass across processes, and a build that finds the stamp recent reads only that file. Go keeps an unused entry five days and trims daily; ergo's entries are cheap to emit again, so one day is enough.
- *Cap.* `modules` keeps at most 2048 entries (`entryCap`), about 2.3 GB at the measured 1.1 MB an entry. A build that published a new entry counts the names in `modules` (at most 2049, with no stat); past the cap it claims the trim and runs the cap pass, due or not. A due trim runs the cap pass after its age pass. The cap pass stats each entry once and removes the least recently used, by use mark, the whole excess in one pass: unlike the age pass it has no bound of 64 a pass, so a cache from before the cap (18,357 entries) is within it after one trim. It removes an entry as the age pass does: only under the entry's exclusive lock, taken without waiting, so never one that a build holds, in this process or another, and only when no build marked it used since the pass read the mark. A held entry is passed over for the next oldest. Go's build cache has no cap; ccache and Cargo's automatic clean have one, by size. The cap is counted in entries, which a build counts without a stat.
- Guards: `TestEntryCapHoldsAfterBuilds` counts the entries after each of nine builds of distinct programs with the cap at 3: at most 3 remain, and they are the newest. `TestCapConvergesInOnePass` plants 192 entries (three age passes' worth) with the cap at 3: one trim leaves the 3 newest. `TestCapPassesOverAReMarkedEntry` marks the oldest entry used between the pass's stat and its lock: the pass keeps it and removes the next oldest. `TestCapNeverRemovesAHeldEntry` is a seeded property with two processes, each under a memory bound the kernel enforces (`proclimit`): each builds programs into one cache with the cap at 2 and runs the cap pass while it holds its module, and no build finds its held entry removed or changed. A failing seed prints `ERGO_BUILD_TEST_SEED=<n> go test -count=1 -run '^TestCapNeverRemovesAHeldEntry$' ./internal/sketch/build`. The mutants are in `internal/sketch/build/testdata/mutants.json`.

**Other caches under the root (batch 18).** BUILD-direct puts Go's action cache under the same root (`go/plans`, `go/actions`, `go/blobs`), and TOOLCHAIN puts the managed Go release there (`toolchain/<version>.<goos>-<goarch>/release`). Both follow `ERGO_CACHE`, so tests get private ones. When they merge with this unit:

- The action cache takes the same rules: its entries are marked used and locked as modules are, and the trim reads its directories as further parts of the one bounded pass, behind the same `trim.txt` claim, with an age limit and a cap of their own. Until then the trim reads only `modules`, `staging` and `private`, and the action cache has no bound (follow-up).
- The toolchain release is one directory per Go version, written once and verified. The cap does not count it, and the trim does not read it. A private root per test process would download a release for each process, so tests run with `ERGO_GO=system`, as the gate's steps do, or read the release from the user's root without writing it; never a release per test process.

## Bootstrap and release

The v1 capstone writes the compiler in Ergo, so an `ergo` is built by an earlier `ergo`, the **seed** (owner, 2026-11-12; prior art in [PRIOR_ART.md](../PRIOR_ART.md#bootstrapping-a-self-hosted-compiler-2026-11-12)). `scripts/bootstrap` is the driver. Until stage S1 of the capstone, every package of the compiler is Go, so the seed lowers nothing yet; the driver already fetches or rebuilds the seed, checks it and runs it, so the chain is in place before the first Ergo package.

**Commands** (run from the repository; each needs Go and Git):

| Command | What it does |
| --- | --- |
| `go run ./scripts/bootstrap [-o DIR] [-stages N] [-from-source]` | Takes the seed that `toolchain/seed.lock` names (stage 0), from the cache, from its GitHub release, or rebuilt from its source (`-from-source`: never downloaded), and builds stage 1 to stage N (default 2) of `./cmd/ergo` from the working tree. Stage i is built with stage i-1 as its compiler. Writes `DIR/stage<i>/ergo` (default `.bootstrap/`, which git ignores) and prints the sha256 of each stage. The last two stages must be byte-identical, else exit 1. |
| `go run ./scripts/bootstrap verify-seed [-work DIR] [-fresh-cache=false]` | Builds the lock's source commit twice for each platform of the lock, from two clean exports (`git archive`) at different paths, each with an empty Go build cache. Both builds must be byte-identical and equal to the lock's sha256, else exit 1. |
| `go run ./scripts/bootstrap seed-lock [-seed NAME] [-source COMMIT] [-go RELEASE] [-platforms LIST]` | Makes the same two builds and prints the lock that names them. A seed bump commits this output; nobody types a hash. |
| `go run ./scripts/bootstrap capstone` | Prints the 15 rows of the capstone probe, each with the stage that makes it hold (S0 to S6), and exits 1 while a row is red. The test `TestCapstoneRowsOfLandedStages` fails only on a red row of a stage at or before `landedStage` in `scripts/bootstrap/capstone.go`; each stage's swap unit raises that constant. |

**The seed lock.** `toolchain/seed.lock` has one key and value per line (`#` starts a comment):

- `seed NAME`: the seed's name, which is also the git tag of its source (`seed-0` first);
- `source HASH`: the full commit that the seed is built from;
- `go RELEASE`: the Go release that builds it (the release that `ergo` pins);
- `package ./cmd/ergo`: the main package;
- `url TEMPLATE` (optional): where the seed is downloaded. The template is https only, and the driver replaces `{seed}`, `{goos}` and `{goarch}` in it. Seeds are published as assets of a GitHub release named after the seed (owner, 2026-11-12): `https://github.com/cevr/ergo/releases/download/{seed}/ergo-{goos}-{goarch}`;
- `sha256 GOOS/GOARCH HEX`: the seed's digest, one line for each platform (linux/amd64 and darwin/arm64).

The seed is never a trusted blob. When `ergo`'s cache (`<ergo cache>/seed/<seed>.<os>-<arch>/ergo`) has no seed with the lock's digest, the driver does two things in order:

1. It downloads the lock's `url` for the platform (at most 512 MiB) and keeps the download only when its digest is the lock's. A download with another digest is refused with both digests named. It is not replaced by a rebuild, because a published binary that differs from its source is a finding.
2. When the release has no such asset (any status other than 200), when the host cannot be reached, when the lock has no `url`, or with `-from-source`, it exports the source commit, builds it, and refuses the result unless its digest is the lock's.

Until a seed's release is published, step 2 runs. Until S1, a seed's source is all Go, so the driver builds it with Go alone; S1 makes `verify-seed` and `seed-lock` build a source that has Ergo compiler packages through its own stages. A tag of the seed's name must name the lock's source commit, else the driver refuses.

**What a build depends on.** Every build of the driver is `go build -trimpath -buildvcs=false` with `CGO_ENABLED=0`. Its environment keeps only the variables that find programs, caches and the module proxy (`PATH`, `HOME`, `TMPDIR`, `GOTMPDIR`, `XDG_CACHE_HOME`, `GOCACHE`, `GOMODCACHE`, `GOPATH`, `GOPROXY`, `GOMAXPROCS`, `GOMEMLIMIT`, `GOGC`). It sets `GOENV=off`, `GOWORK=off`, an empty `GOFLAGS`, `GOOS`, `GOARCH` and `GOTOOLCHAIN`. So the user's go env file, a `go.work` above the tree, `GOAMD64` and the like, a C compiler, the checkout's path and its git state do not reach the binary. A build is a function of the source and the Go release only (`TestBuildIsAFunctionOfSourceAndGo`). `ERGO_GO` selects the Go release as for `ergo`: unset or `managed` is the lock's `go` release, which the go command on `PATH` fetches through `GOTOOLCHAIN` (from the module proxy, checked against the checksum database); `system` is the go on `PATH`; an absolute path is that go command. A seed built by another Go release than the lock's is refused.

**The compiler is written in the seed's language.** `compiler/` and the std packages it imports use only what the seed accepts. Stage 1 is built by the seed, so a violation fails the first step of the bootstrap.

- A new construct lands in the compiler but the compiler does not use it. After the next seed bump, the compiler may use it.
- A construct is removed or changed in three commits: stop using it; bump the seed; remove it.
- A change of `runtime/v1` that seed-lowered code cannot link with follows the same three commits.

**Seed bump.** Before 1.0, any gated commit of main may become the seed. After 1.0, the seed is the previous release.

1. Choose the commit `C` (a gated commit of main, or the release tag).
2. Run `go run ./scripts/bootstrap seed-lock -seed seed-<n> -source C > toolchain/seed.lock`. It builds each platform twice from clean exports and fails if the two builds differ.
3. Commit the lock alone (`chore(toolchain): bump the seed to seed-<n>`). The batch integrator owns the lock: before the batch lands, it runs `go run ./scripts/bootstrap verify-seed` and `go run ./scripts/bootstrap`, then creates the tag `seed-<n>` on `C` and pushes it with main. Publishing the seed needs an owner request. To publish it, rename the binaries that `seed-lock` built to `ergo-<os>-<arch>` and attach them to a GitHub release of the tag: `gh release create seed-<n> ergo-linux-amd64 ergo-darwin-arm64 --verify-tag`. Then run `go run ./scripts/bootstrap` with an empty `ergo` cache: it must download the seed and not rebuild it.
4. Keep every seed tag. The chain can then be replayed from Go source: Go builds `seed-0`, and each seed's `scripts/bootstrap` builds the next.

**Release.** A release needs an explicit owner request (publishing).

1. At the release commit, run `go run ./scripts/bootstrap -stages 3` (from S6 on, `TestFixpoint`: stage 2 and stage 3 are byte-identical).
2. Run `go run ./scripts/bootstrap seed-lock -seed vX.Y.Z -source <commit> -platforms linux/amd64,darwin/arm64,linux/arm64,darwin/amd64`. The binaries it builds are the release binaries, and their digests are the release's checksums. Run `verify-seed` with that lock on a second host (the Mac check host): the digests must be equal.
3. Tag `vX.Y.Z`, publish the binaries as `ergo-<os>-<arch>` assets of the GitHub release `vX.Y.Z` with the printed digests, and commit the lock as the next seed bump. The lock's `url` template names the release through `{seed}`.

## Test memory

A test or a runner that starts a program gives the program a memory limit of its own, and makes it the first process that the kernel's out-of-memory killer stops. `GOMEMLIMIT` does not do this: it is a soft goal of one Go runtime, and it does not bound a child process.

**The incident (measured, kernel OOM report of 2026-11-08 21:10Z).** The 64 GB workbox ran out of memory. One generated program, `machinerun_05`, which a lowering test started, had 46.7 GB resident. Its `oom_score_adj` was -900, so the kernel stopped most other processes first. The test ran outside the gate's scope, with `nice go test` and `GOMEMLIMIT=6GiB`.

**Where -900 came from (measured).** No code of this repository writes `oom_score_adj`. The SSH service of the workbox (a sshd unit) has `OOMScoreAdjust=-900`. sshd gives that score to every session, and a child process inherits the score of its parent. So every process that an SSH session starts has -900: the agent, its shell, `go test`, the test binary and the program the test starts. In the kernel report, 97 processes had -900, among them `opencode`, `codex`, `herdr`, `zsh`, `go`, `lower.test` and `machinerun_05`. After the restart, the sshd session processes and the `herdr remote-client-bridge` processes they start still have -900; the agent sessions that the user's service manager starts have 200. A process without privilege can raise its score, and can lower it again only to the lowest value that a privileged process set for it (here -900).

**What the tools do now.**

- `internal/testinputs.Main`, which every test package's `TestMain` calls, sets the test process's `oom_score_adj` to 1000. Every process the test starts (`go build`, a generated program, `sh`) inherits 1000 from its first instruction.
- `internal/proclimit.Start` starts a program, sets its `oom_score_adj` to 1000, and sets its `RLIMIT_DATA` to the limit with `prlimit`. `RLIMIT_DATA` counts every private writable mapping, where the Go runtime puts its heap and goroutine stacks; Go's address-space reservations (`PROT_NONE`) do not count. A Go program over the limit usually stops with `fatal error: runtime: out of memory`, and the caller reports `program <path> exceeded its memory limit of <size> (set ERGO_PROGRAM_MEMORY to change it, 0 for none)`. A process the program starts inherits the limit.
- **Go 1.27 does not always report out of memory** ([golang/go#82667](https://github.com/golang/go/issues/82667), open). The Green Tea collector allocates the ring of a span queue (`newSpanSPMC`, `runtime/mgcmark_greenteagc.go`) and does not check whether the kernel refused it. When the limit refuses that mapping, the collector stores through a nil ring, and the program stops with `SIGSEGV: segmentation violation`, `addr=0x0`, in a `runtime.(*spanQueue)` frame, with exit status 2 (measured on go1.27.0 under a 256 MiB and under the default 2 GiB limit, batch 15; the issue's reporter saw it on go1.27.3). `proclimit.Check` and the watcher of `ergo test` read this fault as the limit and add the issue to the line: `...; the Go runtime stopped it with SIGSEGV in its collector's span queue, not with an out-of-memory report (Go runtime bug golang/go#82667, ...)`. They need all three facts: the fatal signal line, the address 0 and a first frame in `runtime.(*spanQueue)`. Every other segmentation fault, a nil dereference of the program included, stays a crash. `scripts/examples` and `scripts/mutants` use the same `proclimit.CauseOf` classifier for a failed child under a cap, so they report this fault as memory too. The mutant runner watches the whole output before its display tail drops bytes. The shared classifier also reads `cannot allocate memory`, the runtime's refused-mapping report previously read only by the mutant runner. `go.mod` notes the first Go release that fixes the bug; until one exists the note is empty. `TestQueueFaultIsNamed` and each runner's `TestCappedFaultIsMemory` read recorded output in process (measured).
- The limit is `ERGO_PROGRAM_MEMORY`: a number of bytes, or a size with `KiB`, `MiB` or `GiB`; `0` or `off` means no limit. The default is 2 GiB.
- A bounded `ergo test` program gets `GOMEMLIMIT` at three quarters of that limit and `GOGC=100`, not the caller's collector settings. This leaves room for stacks, metadata and other data before the hard cap. The CLI and build tools keep their own settings. With `ERGO_PROGRAM_MEMORY=0` or `off`, the program inherits the caller's settings too. These settings help collection; only the hard cap bounds memory.
- These callers use it: the test kit of `internal/sketch/lower` (`runProgram`, which every helper that runs a built program calls; its `TestMain` also sets the variable, so a program that a test runs through `ergo run` has the limit); `ergo test`, for the test binary it runs; `scripts/examples`, for each built program a case runs (and the score for every command it starts); `ergo run`, only when `ERGO_PROGRAM_MEMORY` is set. `ergo run` keeps the terminal as the program's stderr, so it does not add the named line; the Go runtime's message shows.
- The gate's steps already run in cgroups with `memory.max` (Merge gate, Memory budget). The closure sweep runs test binaries, whose programs go through the same helpers.

**Limits of the mechanism.**

- `proclimit.Start` sets the limit right after the program's `exec`, so the first instructions of the program run without it (inferred: the Go runtime maps a few MiB before `main`). The test process's score is inherited from the start, so the score has no such gap for tests.
- A program built with `-race` maps large shadow memory that `RLIMIT_DATA` counts; such a program needs `ERGO_PROGRAM_MEMORY=0` or a larger limit (inferred, not measured).
- A sandbox with a read-only `/proc` (the closure sweep) keeps the score as it was; the limit still holds.
- Darwin has no `oom_score_adj` and no `prlimit` for another process, and its kernel does not enforce `RLIMIT_DATA` or `RLIMIT_AS` on `mmap`, which the Go heap uses. There a program is bounded only by the scope its caller runs in. On a Mac, run a long test inside a bounded process.

**Run ad hoc checks in a bounded scope.** A test, build, mutant or probe that is not a gate step runs in a scope of its own: `systemd-run --user --scope -q -p MemoryMax=8G -p MemorySwapMax=0 -- nice -n 19 <command>`. The scope bounds every process in it, whatever its score.

**Guards.** `internal/sketch/lower` `TestRunProgramBoundsAGrowingProgram` builds a generated program that reserves 1 GiB and runs it under a 256 MiB limit: it must stop with the named error. `internal/proclimit` `TestQueueFaultIsNamed` reads the Go 1.27 span-queue fault as the limit and every other segmentation fault as a crash. `internal/proclimit` `TestStartedProgramsDieFirst` checks that the test process has score 1000, lowers it to 999, and checks that a started program has 1000.

## Counted receipts

`scripts/opcount` writes the counted receipt of a speed claim; it is a tool, not a test, and pins no count. `go run ./scripts/opcount [-control] [-text] [-rounds N] [-o FILE] NAME`, from the repository root, reads `examples/NAME/workload` (examples/README.md, "Workload"), builds the program with an exit hook added through `go build -overlay` (the checkout and the emission cache are not written), builds the workload's hand Go control with `-control` (and its Go-runtime floor, a hand-optimized program at the least work the Go runtime allows, when the workload names one: `floor DIR`; the receipt then compares the program with both), and runs each side at both sizes, with the default collector and with `GOGC=off`, the sides alternating (A B, then B A). Per side it writes user-space instructions per unit, the same with `GOGC=off`, allocations and bytes per unit, the GC share of instructions ((default − off) / default), GC cycles, the runtime's GC CPU share, the live heap after a final collection and the peak resident set (`VmHWM`). Every side builds with the release ergo builds with and its patched compile. The program builds as the product does: ergo's own go build action (`build.Toolchain.Command`) compiles each package that has an IR file with its `-ergoir`, and the receipt's case names the path (`ir`) and, per package of the emitted module, how many of its functions took their body from IR (`bodies`). `-text` builds the module `ergo build -go-text` writes instead, the same IR bodies printed as Go text and compiled without `-ergoir` (path `text`), for comparison. `go run ./scripts/opcount -cmd -base BIN -head BIN -each GLOB -- ARGS…` compares two commands on each target (`{}` in ARGS) by instructions, CPU time and peak resident set; it replaces the run-dir `check-cpu.sh` scripts, which timed at 10 ms and read a failed `ergo check` as a fast one.

**Profiles for release builds** (U4 PGO-RELEASE). `go run ./scripts/opcount -profile FILE [-control] NAME` builds the program with a profile hook added the same way (`internal/opcount` `ProfileHook`: `runtime/pprof`'s CPU profile from `init` to exit), runs it `-rounds` times at the workload's large size, merges the runs' profiles with `go tool pprof -proto` into FILE, and counts nothing; with `-control` it writes the control's to `FILE.control` and the floor's to `FILE.floor` by the same method. `ergo build --release DIR` compiles with `DIR/default.pgo` (`go build -pgo`; Go's own convention puts the profile beside the main package): copy FILE there. A missing `default.pgo` stops a release build with the command that writes one; a build without `--release` never reads it. A profiled build rebuilds std and the runtime with the profile, so it goes through `go build`, takes no pin set and is outside the cold-build budget; release mode only. The profile's bytes key the warm answer; the emitted module is the same with and without it. A profile names functions and line offsets, so after a rename Go matches less of it and the build is slower, never wrong. `go run ./scripts/opcount -pgo FILE -control NAME` counts the profiled build (each reference side with `FILE.SIDE` when it exists), beside a plain count of the same workload.

The receipt is a `bench.v1` JSON file (`internal/opcount/receipt.go`): per case its series (side, counter, kind `exact`, `counted`, `sampled` or `timed`, one value per round, median and spread) and, with two sides, a comparison with the median ratio. opcount takes no verdict: the paired test belongs to the bench referee (the STROBE plan); a comparison carries a verdict only when it is refused. A count is a number only when it is whole: `internal/opcount.Count`, the repository's one `perf_event_open` site, counts the program's whole process tree from its exec, and refuses a count with `NoCounter` (no hardware counter), `Multiplexed` (the kernel ran the counter for part of the run only) or `RunIncomplete` (the program exited with a status other than 0, was killed, or left a process of its group running). `NotEquivalent` refuses the comparisons when the control prints other output than the program on the small input, and `NoMetric` a counter the exit hook did not report. opcount exits 1 when anything is refused. `internal/experimental/irspike` and `TestStationStatsCountsAsHandGo` count with the same function.

**Servers.** `scripts/servercount` writes the same receipt for an HTTP service: `go run ./scripts/servercount [-rounds N] [-conns N] [-procs N] [-kinds K,…] [-o FILE] [BENCH]`, BENCH by default `benchmarks/server/registry` (a package mirror: a constant catalog listing of about 330 KB, pins kept per client in a `sync.Ref`, a status route and an HMAC-signed hook), which holds the Ergo program (`cmd/NAME`), `control/` (net/http and encoding/json, as a Go programmer writes it) and `floor/` (a raw HTTP/1.1 loop, append encoders, state changed in place, constant answers encoded once), all under the same limits. It builds the three as opcount does, adding opcount's exit hook and a probe that ends a server, with status 0, when its standard input ends, so the hook runs and no signal stops a counted process. Per route kind (`listing`, `pin`, `show`, `status`, `hook`) it starts each side under `opcount.Count`, waits for the address the server prints, replays the kind's script over `-conns` connections, the server at `GOMAXPROCS=-procs` (default 1, so idle processors do not spin into the count), and checks every answer's status and body digest against a model of the service written in the tool (`registry.go`), at two script lengths, sides alternating, and writes per request the slope of user instructions, bytes and objects allocated, and GC cycles per 1,000 requests, with the program compared with the control and with the floor. A wrong answer voids the run: the side's series and the case's comparisons are refused (`NotEquivalent`). `TestSidesAnswerAsTheModel` (full tier) holds all three sides to the model on seeded mixed scripts, refusals included.

**Parts (the runtime share).** Each run with the default collector also says where its instructions went. `opcount.CountShares` opens one sampling event per online CPU next to the counting event: user instructions, inherited by the whole tree and enabled at its exec. It records the instruction pointer every `sample_period` instructions (the receipt's host field) and looks each one up in the binary's pclntab, which stripped binaries keep too.
- **The parts:** `InstrProgram` (the program's code, Ergo std and Go std), `InstrErgo` (Ergo's `runtime/v1`), and Go's runtime in six: `InstrGC` (mark, sweep, assists, scavenging), `InstrAlloc` (`mallocgc` and its caches, `growslice`, `makemap`), `InstrBarrier` (write barriers), `InstrSched` (the scheduler, parking, timers, locks, preemption), `InstrStack` (`morestack`, stack copies) and `InstrRuntimeOther` (what the runtime does on the program's behalf: `memmove`, maps, channels, hashing). `InstrOutside` holds a sample in no function of the binary or in another process (proclimit's helper before the program's exec, a command the program runs).
- **How a part is measured:** its share of the samples times what the sampling events counted, per unit between the sizes like `Instructions`. `RuntimeShare` is the five parts RT-SPIKE asks about (collector, allocation, barriers, scheduler, stacks) over all parts. `Samples` is the large run's sample count, so a reader can judge the spread.
- **Kind `sampled`:** the parts contain no time, so load moves them no more than it moves a count, but they carry the binomial spread of their samples.
- **The parts sum to the run's instructions.** The sampling events count the same instructions as the counting event, so `Shares.Check` refuses the parts (`PartsShort`) when the two counts differ by more than `PartsTolerance` (10⁻⁴). On this host they are equal. They differ when the kernel throttled the sampling, when a CPU had no event, or when a thread did not inherit one.
- **The period** is 2·10¹⁰ instructions a second over `perf_event_max_sample_rate`, odd. On a VM whose rate the kernel lowered to 1750, that is 11.4 M instructions, and a shorter period was throttled. `OPCOUNT_SAMPLE_PERIOD` sets it by hand.
- **A host that cannot sample** (no PMU interrupt, a ring buffer over `perf_event_mlock_kb`) refuses the parts with `NoSampler` and still counts.
- **Why not the alternatives:** `GOGC=off` against on gives the collector's share only, and allocation, barriers outside marking and the scheduler stay in the program's count. `runtime/metrics` gives events (cycles, allocations) and CPU-seconds estimates, which are time.
- **Command mode** writes the same parts per run, with no slope.

## Graph rows

`ergo graph export [DIR|DIR/...] [--json]` prints the checker's graph of a program as rows ([graph](spec/graph.md)): modules, packages, files, declarations and tasks, and the imports, uses, needs, fails, provides, reexports, testof, lawof, input and, at a workspace root, requires edges between them. `internal/sketch/graphrows` builds them from the loader's imports, SEM's fact tables and the verdict store's digester; a task's key is the store's digest and its input rows the declarations that digest covers. std `codegraph` and the affected selector read these rows, never the checker's structures. The queries are `ergo graph [--in DIR|DIR/...] cycles [--level package|file|decl] [--tests] | why A B | affected BASE | hidden | chains [--min N] | fan [--level L] [--tests] | layers PATTERN...`, each `--json`: each one std `codegraph` function, run by the linked package `graph` (below) over the rows the command writes. `affected BASE` reads the base's rows from a rows file, or checks the tree `git archive BASE` gives in a temporary folder, and starts from `codegraph.Changed` (top-level declarations whose digest differs). `scripts/graphreceipt` counts a query in Ergo against hand-written Go over the same rows.

## Linked Ergo packages

Some of the `ergo` binary's code is written in Ergo. Until capstone stage S5 builds `ergo` from `compiler/` with the seed binary, such code is a **linked Ergo package**: an Ergo module whose lowered Go is checked in and compiled into the binary like any Go package.

1. **The list.** `linked.Packages` (`internal/linked/linked.go`) names each linked package: its name (the Go package `internal/linked/<name>`), its Ergo module (`Source`, by default `internal/linked/<name>/ergo`), the package of the module whose exported functions Go calls (`Exports`, by default the module's root), whether it lowers through the IR (`IR`), and the std operation types whose command lines `ergo gen cli` generates into the module. `compiler` is the compiler written in Ergo (`compiler/`, exports `compiler/api`), which `internal/hostsyntax` and `internal/sketch/syntax` call. `code` is `ergo code` ([code](spec/code.md)), and `graph` is `ergo graph`'s queries over std `codegraph` ([graph](spec/graph.md)).
2. **The generator.** `go run ./scripts/linked` writes every listed package: it generates the command lines, checks the module in memory, and lowers it. A row with `IR` (`compiler`) lowers it through the IR as `ergo lib` lowers a library (`lower.LowerIRLibrary`: each body the IR builder expresses is an IR body), builds it with the patched compile, and writes the Go text the compile printed of what it compiled (`-ergoirtext`; capstone §12 Decided 5); a body the IR builder cannot express yet keeps the Go body the lowering wrote, and the IR report names its reason. The other rows lower as `ergo lib` does ([interop](spec/interop.md#go-calls-ergo)). Either way the Go is formatted with gofmt. Never edit the generated files by hand.
3. **Fresh.** `cmd/ergo`'s `TestLinkedGoIsFresh` (full tier) regenerates every listed package in process and fails when a checked-in file differs or a generated folder holds a file the generator does not write. An edit of a linked module, of a std package it imports, or of the lowering therefore fails the gate until the generator has run.
4. **The compiler row.** `compiler` exports `compiler/api`: the formatter, which `internal/hostsyntax` calls, and, passed through from `compiler/syntax/dump`, the canonical dumps of compiler/syntax's scan and parse, and the parse packed as one `[]uint32` (`Columns`, with `Failure`). `internal/sketch/syntax`'s `TestDecodeAgreesWithView` compares the parse dump, in process, with the dump of the Go nodes `ParseRows` decodes from the columns, on the corpus and on seeded sources. The Go scanner and parser were deleted at S2e: the parse laws hold the parser to the formatter instead (`TestFormatParseRoundTrip`: parse(format(t)) is t but for positions, on seeded generated programs; `TestFormatIsTheCorpusFixpoint`: the same on the corpus, and the formatted folders `compiler/` and `examples/` are exactly what their trees format to). Since S2d `syntax.Parse` is `ParseRows`, so `go run ./scripts/linked` parses `compiler/` with the generated `internal/linked/compiler` it is about to replace: the parser builds its successor. A change to compiler/syntax that cannot parse `compiler/` any more cannot regenerate itself; a mutant run therefore puts the good generated file back before each mutant.
5. **The seam.** Only basic types and slices cross an `ergo lib` function. Go passes a linked package its input as text (an encoded tree, JSON; `code` decodes it with std `json`) and gets back strings. This seam goes when the parser is Ergo (S2d).

`ergo work` is not linked: it runs `ergo-work` from `PATH`, as git runs its subcommands.

## Mutant ledger

`internal/sketch/check` and `internal/sketch/lower` each keep a mutant ledger, `testdata/mutants.json`. A mutant is one edit of the package's source (`file`, `from`, `to`) that some test, law or example must notice, with the rule it breaks (`rule`), the owner to tell when it goes stale (`origin`) and the tests known to kill it (`killers`, as `SUITE:NAME`). A mutant that no test kills has a `gap` that says why: a gap of the suite, which a new test may name. A mutant inside a string literal (an emitted Go template, a rule-text constant) has no coverage block of its own: its `anchor` names a text in the file (or in `anchor.file`) whose lines stand for it, and the tests that read the source (`anchor.tests`). `anchor.tests` also names the killers whose run the coverage pass cannot see: a test that reads the source rather than runs it, a test that runs the code in a program it builds (runtime/v1 under a lowered program, an `ergoexplore` worker), and a mutant of a `.ergo` std file, a `_test.go` file or a `const` declaration, which have no Go coverage block. The runner's copy of the checkout is a Git repository with one commit of the copied files, so a test that reads the repository (`git ls-files`, internal/residue's rules) runs there as in the checkout.

`runtime/v1` keeps one too (batch 14): the runtime's parked waits and the manual clock's one-Advance rule, in `runtime/v1` and the `runtime/rt` files they park on. `go run ./scripts/mutants ./runtime/v1` judges it by `runtime/v1`'s own tests, with coverage of the packages its mutants edit; a ledger of check or lower takes the suites below (`suitesFor`). `internal/sizes` keeps one for the size receipt's budget check (binsize BS0), judged the same way.

`go run ./scripts/mutants check lower` runs the ledgers. The runner copies the checkout under `-work` and never writes the checkout, except the ledgers with `-write`. The default `-work` is a directory of the run alone under `$TMPDIR` (`ergo-mutants-*`), removed at the end, so two runs at once never share coverage counters; pass `-work DIR` to keep the coverage for a later run. First it measures per-test coverage of check and lower once per tree and scope and keeps it under `-work`: every top-level test of `check`, `lower` and `std` and every default example program, each in its own process (the `ergo` CLI and the examples runner are built with coverage, their main packages included, or they write no counters). The scope is what can cover the selected mutants (`-run`): a suite whose test binary, or a tool it runs, compiles the package of a selected mutant's Go file (`go list -deps`), since a binary records blocks only of what it compiles; a suite that compiles none is neither built nor measured, and a test an anchor names is measured alone (MQ-tell: `-run ^mq- lower runtime/v1` passed its 90-minute bound measuring every suite). It logs each test as it ends (`coverage: 12/340 lower:TestX 4.1s`), so a stall shows, and ends with a receipt: tests measured, suites, builds, seconds of tests; a coverage read or reused says so. Then, for each mutant, it applies the edit to a copy, builds only what the next test needs, and runs only the tests that cover the mutated lines: the known killers first, then the cheapest, until the first one fails (`-all` runs them all and prints "killed only by"). Each child runs as the leader of its own process group, under `RLIMIT_DATA` (`-memory`, default 4 GiB; Test memory) and a deadline of ten times its time in the coverage pass (at least 2 minutes for a test, 10 for a build); its group is stopped when it ends. So a mutant that makes a program grow without end is a kill of that test (reason `memory`, including Go 1.27's span-queue fault: Test memory, golang/go#82667), not an out-of-memory kill of the runner. Each child has `ERGO_MUTANT` set to the mutant's name. At the end each copy is compared with the checkout: a mutant left in place fails the run.

Another package's ledger (`go run ./scripts/mutants runtime/v1`, the ledger at `DIR/testdata/mutants.json`) is judged by that package's own tests: the coverage pass records `DIR`'s blocks over the tests of the suite named `DIR` (killers `DIR:TestName`). A killer or anchor test in a suite the ledger's scope does not bring is run too, and only the tests the ledgers name: an ergo suite by its name (`std:`, `lower:`, `examples:NAME`, with the tools it runs), another package of the module by its directory, and `DIR[TAGS]` as `DIR` built with `-tags=TAGS` (runtime/v1's `ergoexplore` tests, whose other tests hang without the explored worker). So no row is run by hand (`namedSuite`, `TestKillerInAnotherSuiteIsRun`). An id whose suite is none of these, or whose test is no `Test` func of the suite's package (no example program of `examples:`), is an error of the runner and of `TestLedgerEditsApplyOnce`: before, the runner left such killers out without a word (`v1:`, `sched:`, `rt-explore:`, `tsproj:`, prose ids such as `example:jobs test api (law …)`; MUT-names). A package ledger's `env` (NAME=VALUE entries) is the environment of every run of its own suite, in the coverage pass and the mutant pass, and is part of the tree key: tsproj's ledger sets `ERGO_TS_TEST=1`, which its TS-leg killers need, so a plain `go run ./scripts/mutants internal/tsproj` judges every row (`TestLedgerEnvReachesItsOwnSuite`). check's and lower's ledgers share the ergo suites and refuse an `env`. A Go test that fails in the coverage pass is run once more from a binary built without coverage; if it passes there, it stays a killer, with the blocks its coverage run recorded. internal/closure's tests run their own binary in a sandbox where only fresh scratch is writable, and a coverage-built test binary writes its coverage at exit under TMPDIR, so they failed under coverage alone and judged nothing (`plainRun`; `TestRunnerMatchesModel`'s TestPlain). Each Go test binary runs with a `-test.timeout` inside its deadline, as `go test` always gives one: a test that bounds its children by `t.Deadline` failed at once without it. The package's own scope runs no check, lower, std or example test (`scopeOf` in `scripts/mutants/main.go`; `TestScopeIsTheLedgersPackage`). With the check and lower scope a mutant of `runtime/v1` was in no covered block, so every one was `uncovered`, after a coverage pass over every check, lower and std test and every example (21 minutes, wf10 H1; M1). Several ledgers take the union of their scopes. The cover tool gives a `case` line of a tagless switch and an `} else if` line no block of their own, though the code that reaches them runs them; a mutant on such a header line in no block takes the tests of the block that ends last before it (`headerLine`, `coverage.covering`; `TestHeaderLineIsCoveredByWhatReachesIt`), where it was `uncovered` before (M1: `client-refused-kind`). With both changes, `go run ./scripts/mutants runtime/v1` measured 170 tests (runtime/v1's own) in its coverage pass and judged 22 mutants in 10m34s on a loaded host: 21 killed, and `r3b-local-exit` uncovered as its gap says (measured). A mutant of such a package that only an example or a lower test kills (a runtime body that only a generated program runs) has no block that the package's own tests run: its row names that killer in `killers` and in `anchor.tests`, and the runner runs it (r3b-local-exit by `examples:limiter`, gapos-* by `std:TestStdHostLawsHold`; measured, MUT-clean). The cover tool sees Go blocks only, so a mutant of a file that is not Go (std's `.ergo` sources, a ledger) is judged by the tests its row names, as killers or anchor tests, that the run's suites hold and that pass on the unmutated tree, with no coverage filter (`coverage.named`; EX2: std's `esc1-*` were `uncovered`). Name them by the suite of the ledger's scope (`internal/sketch/std:TestName`). A leaf package of the runtime (`runtime/v1/http`, `exec`, `rpc`, `redacted`; BS8) keeps its own ledger, judged by its own tests, so a mutant of code that moved into a leaf moves to the leaf's ledger with it (EXPLORE-rt r3). A mutant of code that builds only with a build tag (`runtime/v1/explore_on.go` under `ergoexplore`) names its killers `DIR[TAGS]:TestName`, which the runner builds with `-tags=TAGS` and runs. The ledger of a package in a Go module nested in the checkout (`hosts/mygo`, its `drawing` module) is judged in that module: its own suite and its killers are built and run in the innermost `go.mod` between the package and the checkout (MUT-MODULES). The coverage pass measures the checkout's module only, so such a ledger's rows are judged by the tests they name. A mutant of a generator names the step that writes its output again, `"regenerate": {"dir": "hosts/mygo/drawing", "argv": ["go", "generate", "."]}` (MUT-REGEN; the package with the directive, not `./...`: go generate lists the packages first, and a mutated generator that removes a file makes it fail on that file): the runner runs it in the mutated copy before the killers, so they read what the mutated generator writes, and after the row puts every file under `dir` back as the checkout has it and removes the files the step added. A step that fails makes the row invalid. A killer `DIR:Name` whose `DIR` is an Ergo package with no Go test of its own (`compiler/syntax`) is its Ergo test `Name`, which `scripts/ergotests` runs at check time, as `ergo check` evaluates it, with no Go build; a skipped or incomplete test fails, since a skip is not a pass (ST-0). The gate runs the same tool over `compiler/...` (step `ergo tests compiler/...`), so no Go test bridges a compiler package's Ergo tests into the gate. A law is named `DIR:law:L` (`law:T.L` for a member law), which runs every run of the law and must pass outright: a law skipped or incomplete at check time kills nothing (LAW-KILLER). A std package's law (`internal/sketch/std/text:law:GetIsCut`) runs in-package, as std is checked, so it may call the package's private functions and its trusted runtime Go (a std folder checked as a folder fails S108); the runner builds `scripts/ergotests` in the mutated copy, so it embeds the mutant. A std law check time leaves undecided is no killer: `ergo test` cannot check a std folder (STD-LAW-RUN, #162).

A row's named killers (`killers` and `anchor.tests`) always run against its mutant, first, whether or not the coverage pass saw them reach the mutated lines: a test in another package that kills through a program it builds (check's tests kill eval's mutants through the ergo programs they run) leaves no coverage of the mutated package, and before it was skipped and the row `uncovered` (fu-mutants-xpkg; `TestRunnerMatchesModel`'s `literal-named`). So a named killer that does not kill makes the row `survived`, not `uncovered`. A killer id is `SUITE:TEST`, where `SUITE` is an ergo suite (`check`, `lower`, `std`, `api`, `ergo`), `examples` with `TEST` a program, or a module directory, `DIR` or `DIR[TAG]`; a note after the test, past a space, is the reader's. A Go `TEST` may name a family split into parts (`TESTPart0`, `TESTPart1` …, split to fit the gate's step limit, as irspike's `TestIRAgreesOnExamples`): the runner runs every part in one process (`-test.run=^TESTPart[0-9]+$`), any failing part kills, and its start is any part's, so a split leaves the rows unchanged and no row names a part number (GT-FAMILY; `family-named`, `gtf-family-one-part`). The runner refuses a run whose selected rows name a suite it cannot resolve, or a test a Go suite does not have, rather than drop the row (45 rows named `v1:`, `main:`, `sched:`, `tsproj:`, `example:` … and were never run). A ledger in a directory with no Go tests (an example's, `examples/fetchpool`, whose rows edit `.ergo` files) brings no suite or coverage of its own: its named killers judge it. Only the rows `-run` selects bring their killers' suites (`TestKillerInAnotherSuiteIsRun` counts the suites). `internal/residue`'s `TestLedgerEditsApplyOnce` checks every ledger's killers in the checkout the same way, without a build (`killerMissing`).

Verdicts: `killed` (with the killer and the reason: `fail` or `memory`; a timeout is no kill, below), `survived`, `uncovered` (no test runs the lines and the row names none), `stale` (the edit no longer applies), `invalid` (the mutated tree does not build, a Go file's mutated package does not compile, or an `.ergo` row's mutated file is not written as `ergo fmt` prints it or gets a diagnostic the unmutated file does not, checked by the compiler built from the unmutated checkout on the file's folder; never a kill. A row whose point is that refusal says why in `refused`), and `unjudged`: a test that covers the row or that the row names fails on the unmutated tree, so no verdict on the row would hold (GT8b, after FT11b's cmd/ergo run, where 7 such tests left the rows `uncovered`). The runner prints stale and invalid mutants with their origin, and the unjudged ones with the red tests. It exits 1 when a mutant survives that has no `gap`, or a mutant is unjudged, invalid or hung, and 2 when the run fails. One build failure is a kill: on a row with a `regenerate` step whose mutated source compiled and whose step ran, a named killer's suite that the compiler refuses to build kills the row, its reason `build` and its detail "killed by build failure after regenerate: " with the first compiler error (H3f-layer-dropped: drawgen without raster removes `drawing/raster`, and the host that draws with it no longer compiles; `killedByBuild`, `TestRunnerMatchesModel`'s `regen-breaks-build`; a failed step, an uncompiled source, another suite or a deadline stays `invalid`; batch 23 fallout).

A run is bounded by the rows it judges, not by the suites (GT-BOUND, `scripts/mutants/judge.go`; the runner ran out of 90 minutes on `internal/sketch/check` in the coverage pass before it judged a row). Phase A needs no coverage: each test a selected row names runs once on the unmutated tree (its baseline: red, it leaves its rows `unjudged`; its time is the base of its deadline), then each row runs its named tests on its mutant, and a kill judges it. A kill by a named test that passes unmutated stands even when some covering test is red. Phase B measures coverage only when rows are still open (no named test, or none killed; with `-all` every row), over the run's go test suites (each suite's segment reused from the coverage store where its key holds, GT6), and runs each open row's covering tests that it has not run yet; when phase A judged every row the log says `coverage: not measured`. A row's tests run `-tests` at a time (default 2; `-workers` × `-tests` children run at once, each under `-memory`, so choose them to fit the cap the run is under), and the first kill stops the others. Each verdict line and the end of the report give the receipt: the tests run on each mutant, those stopped by a first kill, and the total. Each build and each test of a mutant logs its start with its deadline (`ROW: build lower (deadline 15m0s)`, `ROW: run lower:TestX (deadline 2m0s)`) and each build its time when it ends, and the baseline's builds log as `baseline:`, so a one-row run that spends minutes building lower's test binary shows where it is and what bounds it (GT-SINGLE). A test whose only failure is a timeout (go test's `panic: test timed out`, or the runner's deadline) kills nothing: a deadline only stops a hung test. A row that no test killed and some test timed out on is `hung`, listed with its origin, and fails the run like an invalid row (LY's `ui-stats-written-uncounted` and `ui-slow-*` were "killed" only by the 600 s timeout). The examples runner's own per-case timeout prints a failed case, which is still a kill. A ledger's `commands` are killers that are not a go test: `"commands": {"NAME": ["{bin:ergo}", …]}`, named `command:NAME`, run with the words `{root}` and `{bin:ergo}`/`{bin:examples}` in the mutated copy; they run only for the rows that name them, never in the coverage pass, and `TestLedgerEditsApplyOnce` checks that each `command:` killer is in its ledger. A run survives its own death (three lanes had full runs killed by server restarts): each verdict and each baseline is appended to the tree's journal under the user cache directory (`ergo-mutants/journal/KEY.jsonl`, synced per line) as it lands, and `-json` is rewritten after each verdict; a run of the same tree takes the journal's verdicts (`resume: N of M rows …`), judges only the rest, and removes the journal when it is complete. `-resume=false` keeps none. `TestRunnerMatchesModel`'s seed 2 stops a run after four verdicts and checks that the next judges only the rest, and its `spins` row is the hung guard. A kill is a failure of a test that started (GT-NOTESTS): Go test binaries run with `-test.v`, and a failure with no `=== RUN   TEST` line (a usage error, a binary that dies in an init, no test of that name) kills nothing; a row that only such failures met is `invalid`, and a named or covering test that passes without starting fails its baseline, so its rows are `unjudged` (Lane A's S2e run counted every row killed when its test command errored before any test ran; `dies-before-tests`, `gtn-started-ignored`). A command killer prints no start line; its baseline on the unmutated tree catches a command that errors.

A mutant that does not compile is invalid, never killed (GT-COMPILE, `scripts/mutants/compiles.go`). Three lanes found rows "killed" only by a compile error: a test that builds a program (lower's tests build lowered Go against `runtime/v1`; an examples case checks its own `.ergo`) fails on it, while the suite's own build does not compile a file outside its closure. So once the mutant is applied, the runner compiles a Go file's package in the copy before any test runs, with `go build -o /dev/null` (`go test -c` for a test file) in its module; an `.ergo` file is judged by the formatter and compiler check above (FK7a, FK12a; `scripts/mutants/source.go`), which counts only diagnostics the edit adds. The detail of a Go file is `does not compile:` and the first compiler line. A file that fails the same way unmutated (a fixture) makes no row invalid. Limits: the importers of the mutated package are not compiled, and a Go file a build constraint leaves out compiles as nothing. `go run ./scripts/mutants -compiles LEDGER...` applies and checks each row and runs no test: a sweep for invalid rows. The verdict store is v2 (`ergo-mutants-reuse-v2`), as a v1 killed verdict may rest on a compile error. A child of the runner sees no `GOFLAGS` (the go command's `-p` defaults to `GOMAXPROCS`, which `-procs` sets): a set `GOFLAGS` makes `ergo build` refuse its direct path, which failed cmd/ergo's direct-path tests in the runner alone. The module's toolchain (`go env GOROOT`/bin) is first on every child's PATH, as `go test` puts it, and no child inherits a `GOROOT` (one of another toolchain fails every build): a test binary run directly found the host's go, and `ergo build` refused it (GT-BOUND: opt9-fail-around-noresult's killer, TestLRUCountsAsHandGo, was red on the unmutated tree). Every child runs as the leader of its own process group, which the runner stops when the child ends; on Linux the runner is also the subreaper of all it starts (GT-REAP, `scripts/mutants/reap_linux.go`): a process a child leaves in a group of its own (an `ergo test` exploration, which the test would stop at its end but a test stopped at its deadline never does) becomes the runner's, and is stopped with its group when that child ends (found by the child's `ERGO_MUTANTS_EXEC` token), or at the run's end. The GT-BOUND full run leaked three `ergo test … fetchpool` processes for 13.8 h before this (`TestAbandonedGroupIsStopped`, `gtr-orphan-left`). `-write` records the killers it found, and a gap for a mutant judged for the first time that nothing kills. `-run REGEXP` judges some mutants; `-coverage FILE` reuses a coverage file of an earlier tree (after a test deletion, a deleted test simply does not run).

When to run it: a change that deletes or folds tests of check or lower runs the ledgers of both packages; every mutant must still be killed. A test that only a deleted test killed comes back. A new test names the ledger mutant it kills. Run it in a bounded scope (Test memory); `-workers 2 -procs 2` is the default share of four threads.

A pass judges a row again only when what its verdict rests on changed (GATE2 GT2, `scripts/mutants/reuse.go`). A row's key holds the row (its name, file, edit and killers), the runner's executable, the go command's settings (`go env GOVERSION GOROOT GOFLAGS …`), the mutated file, and the content of every file its killers read: for a killer in a Go test package of the module, that package's closure as the gate's package key reads it (the test binary's sources and embeds, its `testdata`, its declared inputs in `internal/closure`, its programs; ignored files included) with the closures of the tools its suite runs (`lower` runs `cmd/ergo`); for any other killer (an example program, a tagged build, a nested module) every tracked and untracked file. A `killed` verdict by one of the row's own killers is stored under its key in `$ERGO_MUTANTS_CACHE` (default `~/.cache/ergo-mutants`), one file per key, when the key at the end of the run is the same. While the key holds, the next pass prints the stored verdict with `reused: the verdict at key …` and judges nothing for the row; when every selected row is reused, the pass builds and runs nothing. A survivor and an `uncovered`, `stale` or `invalid` row is judged on every pass. `-fresh` judges every selected row (the reference), and `-all`, which names every killer, reuses nothing. `-write` leaves a reused row as it is. `TestReusedVerdictsAgreeWithAFreshPass` is the guard, a seeded property over a model checkout and judge: after each edit the reusing pass gives every row a fresh pass's verdict, and after an edit outside its Go killers' closures a killed row is reused (`ERGO_MUTANTS_REUSE_SEED=<n>` replays a seed). The limit: an ignored file is keyed only inside a Go killer's closure, so a non-Go suite (the examples) that read an ignored file would replay a stale kill; none does today.

The coverage pass measures only the suites whose coverage may have changed (GATE2 GT6, `scripts/mutants/coverstore.go`). A suite's segment of the coverage (its tests, the blocks each runs, its build time and its tools') is stored in `$ERGO_MUTANTS_CACHE/ergo-mutants-coverage-v2`, one file per key. The key holds the suite (name, package, command, environment, the tests it lists), the covered packages, the runner and the go command's settings, and the content of every file the suite's tests read, as a row's key reads it: a Go suite's closure with its tools' closures, ignored files included; for the examples suite, a tagged build or a nested module, every tracked and untracked file. A pass takes each stored segment whose key holds and measures the other suites alone, building only the tools they run; it stores a measured segment when none of its tests failed on the unmutated tree (a flaky failure must not stick) and the suite's key at the end of the measure is the same. So a lane a few commits past main's head measures the suites its edits reach, not every check, lower and std test. `go run ./scripts/mutants -measure check lower` measures and stores the coverage and judges nothing: run on main's head after each landing, it leaves every lane's segments. `-fresh` measures every suite and uses no store (the reference); `-coverage FILE` still reads a file and measures nothing. `TestStoredCoverageAgreesWithAFreshMeasure` is the guard, a seeded property over the row keys' model checkout with a model measure: after each edit the assembled coverage equals a fresh measure of every suite, no segment with a failed test is stored, a measure during which a file changed stores nothing, and after an edit outside every Go suite's closure only the examples are measured again (`ERGO_MUTANTS_COVER_SEED=<n>` replays a seed); `TestRunnerMatchesModel`'s seed 1 runs the runner twice over one store.

The store's format, its files and its index are the package `scripts/mutants/covfile`, which other tools import (CI-SELECT CS-ROUND). The index says at which commit each segment is a suite's coverage: after a pass over a clean checkout (no changed tracked file, no untracked file), the runner records, under `index/<commit>/`, each suite whose segment the store holds at its key, measured or reused, with the suite's package, the mode (`full`: the coverage pass never runs `-short`, and the key holds the mode) and the go command's settings. A reader finds a commit's segments through the index and diffs that commit against its change; it never computes a key of its own. `TestIndexNamesOnlyCleanCommitsWithStoredSegments` guards the index.

The coverage pass also covers `.ergo` lines that a lowered program runs (GATE2 GT7, `scripts/mutants/ergolines.go`, `internal/sketch/build/cover.go`). The runner sets `ERGO_COVER_GO` for every child of the coverage pass. With it set, the ergo CLI (`build.Toolchain.Build`) links every program it lowers from a coverage copy: the emitted module's own files (main.go, assets, go.mod, go.sum; not the runtime) copied to `$ERGO_COVER_GO/KEY` under the module path `ergo.local/cover/KEY`, so two programs' blocks never share a file name, built with `go build -cover` of the program's package. A program started without `GOCOVERDIR` (an examples case runs with a clean environment) takes its nearest ancestor's from `/proc` and unsets it again before `main`, so its counters land in the running test's directory and it prints no cover warning. The cover tool names a block by the base name of the `//line` directive that governs it, or by the Go file's own name, but numbers it by the Go file's lines. So the runner reads the copy's Go file and maps each Go line of the block through the `//line` and inline `/*line*/` directives to the `.ergo` file and line it came from, and records a block of that checkout file. A `.ergo` row is then covered by the tests that run its lines, as a Go row is. `TestErgoLinesFollowTheDirectives` (a seeded property over generated lowered Go; `ERGO_MUTANTS_ERGO_LINES_SEED=<n>`) and `TestCoverBuildCountsInTheTestsDir` (a real coverage build run as a case is run) are the guards.

Std `.ergo` lines are covered too (GT7b). Std bodies are lowered without `//line` directives, so a coverage build (and every lowering in `internal/sketch/lower`'s tests during the coverage pass) lowers with `lower.Unit.CoverMarks`: a full-line comment `//ergo:cover std/PATH:LINE:COL` wherever a body with directives would write its directive. A comment moves no Go position, and with the marks taken out the Go has the same tokens (`TestCoverMarksOnlyAddComments`, full tier); without a coverage build the lowering is byte for byte as before, and the build key carries the flag `cover-marks`. The runner maps a line after a mark to that std line, in `internal/sketch/std/`. `internal/sketch/lower`'s dispatcher links a coverage copy of its programs in the coverage pass (`coverdispatch_test.go`; its main package is in `-coverpkg`, as a binary whose main is not covered writes no counters), and the runner maps a block of a package below the copy's root (`KEY/p/NAME`). Every coverage build of the pass counts with `-covermode=atomic`, the test binaries too (`go tool covdata` refuses two modes in one directory), so a coverage build that SIGINT or SIGTERM ends (a server a test stops) writes its counters first and then dies of that signal; a module whose own Go registers a handler for signals (`signal.Notify`) gets no flush and keeps its handler, so its counters are written only when that handler lets it exit. Limits: a program the checker's evaluator runs is not lowered and covers nothing; the ancestor lookup reads `/proc`, so on macOS a case's counters go to `$TMPDIR/ergo-cover-orphans`.

A test that reads a file covers it too (GATE2 GT8, `scripts/mutants/reads.go`). A test that parses source (check's `TestMintFormNamesEveryKind` reads `ownership.go`'s switches) runs none of that file's blocks, so line coverage alone never selected it for a row of the file unless the row named it. In the coverage pass each Go test binary runs with `-test.testlogfile`, the go command's test log of every `os.Open`, `os.Stat` and `os.Chdir` of the test process, and each regular file of the checkout the test opened (not `.git`) is recorded as a block at line 0 of that file: its tests cover every line of the file. `TestRunnerMatchesModel`'s `literal-bare` row is the guard: no block of `one/f.go` runs `two:TestReadsOne`, which reads that file, and the runner selects it and it kills. A file read through `go:embed` is not opened, so stdlib (std's sources) and std/gostd (its bindings) observe each embedded file they read, as for the gate's coverage record (gate-speed GS9): with `ERGO_EMBED_OBSERVE` set to the coverage pass's copy, they open and close the file's path in it, so a check test that reads `std/http/http.ergo` covers that file's rows (GT8b); without it nothing is opened. `TestObserveOpensTheCheckoutCopy` (stdlib) and `TestObserveOpensTheBinding` (gostd) are the guards. A suite of a ledger with no covered package (only `.ergo` rows) is built without coverage, and its tests now run without `-test.gocoverdir`, which failed every one of them on the unmutated tree. Limits: a file read by a program the test starts, or embedded by a package that does not note it, is not in the log; such a row still names its killer. A reader covers every row of its file, so a survivor of that file runs its readers too.

*Alpha* (CI-SELECT CS-ALPHA, `scripts/mutants/alpha.go`, `killmatrix.go`). `go run ./scripts/mutants -alpha [-o FILE] [-fail-logs DIR] PACKAGE...` prints one row per Go test of the packages: class (law, model, property, agreement, example or row, by name pattern; `scripts/mutants/testdata/alpha-classes.txt` holds the reviewed exceptions, `DIR:TestName class # why`), seconds (the coverage pass's), unique kills (rows it alone kills), total kills, change coupling (of the last 500 commits that touch the package, those that changed the test's file and a non-test Go file of the package), failures (`--- FAIL` lines in the logs under `-fail-logs`), and held (rows it could kill that were not judged: red on the unmutated tree, invalid or cut). The table is ranked as a deletion list: class `row` with no unique kill and nothing held first, by seconds then coupling, then the rest. The kills are the kill matrix: every row of the packages' ledgers, and every row of another ledger that names one of their tests, is judged with every covering test run (`-all`), not until the first kill; a row that no test of the packages covers gives them nothing and is not run. The matrix is written beside each ledger as `testdata/kills.json` (merge class derived), keyed by GT2's row key over the row with its candidates as killers; a row whose key holds is taken from it and not judged again. Alpha is reported, never enforced by the gate. `TestAlphaAgreesWithAReferenceMatrix` (a seeded generated module whose matrix is known by construction; `ERGO_MUTANTS_ALPHA_SEED=<n>` replays) guards it. Kills by a test outside every suite the run builds are not seen: a row's other killers are those of the suites the ledgers name.

`scripts/mutants` `TestRunnerMatchesModel` (full tier) runs the runner over a generated module whose coverage and kills are known, and checks every verdict, that only covering tests run, that the memory mutant is a `memory` kill, and that the checkout stays equal to `HEAD`.

A mutant a test's comment names is a ledger row: `internal/residue` `TestTestCommentsNameLedgerRows` reads each sentence of a test comment that says mutant (its lines joined) and fails on a name of the mutant shape that no `testdata/mutants.json` holds, unless `testdata/mutant-names-allow.txt` lists it; that list holds the stale names found when the rule started, and only shrinks.

A test never leaves a file in the system temporary directory: `internal/residue` `TestTestsRemoveTheirTemporaryFiles` fails on a function of a `_test.go` file that calls `os.MkdirTemp` or `os.CreateTemp` with `""` or `os.TempDir()` and removes neither the variable or field holding the result (`os.Remove`, `os.RemoveAll`, a deferred closure too) nor calls a `Cleanup`; use `t.TempDir()`. `testdata/tempdir-allow.txt` names the helpers that leave the removal to their caller, and only shrinks. `cmd/ergo`'s tests made `/tmp/ergo-cmd-test-cache-*` in an `init` and never removed it: 7,404 directories, 68 GB, on 2026-11-13 (GS18).

Spec references move with a renumbering: `go run ./scripts/specrefs DOC SECTION` lists every reference to the section's numbered items (`interop.md, Lowering 9`), reading a reference wrapped across comment lines or a Markdown paragraph whole, and `-move 9=13,13=9` rewrites the numbers.

## Merge gate

`scripts/gate.sh` builds `scripts/gate`, a small Go runner that owns the check graph ([design and measurements](research/gate-throughput.md)), and executes it in place of the script. Every check is a step with declared dependencies. Independent steps run concurrently. Each step's output is printed whole, in declaration order. A failing step fails the gate and blocks only the steps that depend on it. A plain `./scripts/gate.sh` runs the fast tier (below). `--full` runs the full tier, `--no-cache` runs the full tier without whole-gate records or step receipts (Go's test cache still applies to the hermetic step, below), `--merge` runs the merge tier (below), `--list` prints every step of the run's tier and its command, and `-record-durations [package ...]` re-measures the tests of the named Go packages, or of every test package when it names none (with `-fast`, the CPU of their fast-tier steps into `scripts/gate/fast-cpu.json`; with `-cpu`, the CPU of each test of the sharded packages into `scripts/gate/test-cpu.json`, below).

- **Tiers.** A lane runs the fast tier before it hands back a unit. The full tier, the merge tier and the macOS check (`darwin-check.sh`) run on every batch head before main moves; only they protect main (NORTH_STAR.md, gate-fast decision D1, 2026-11-06).
  - *Fast* (the default). The in-process checks and tests and the examples step (test-speed decision Q1, 2026-11-08). Every step the gate declares has a class (`stepClass` in `scripts/gate/tier.go`): the fast tier keeps the `classFast` steps of the full tier (the bytecode, Wayfinder, Foldkit and Effect-mapping checks, `gofmt`, `go vet`, `build bin/ergo`, the examples step and `ergo fmt --check`) and adds one `-short` step per test package, as below. A step with no class fails the declaration. - **Recorded durations.** `scripts/gate/durations.json` holds the serial seconds of each top-level test of each test package, from `go test -count=1 -json`. Re-record it after a change that adds or removes test packages, or that moves the cost of tests: `./scripts/gate.sh -record-durations` runs every test package of the module, one at a time, uncached and under the gate's memory and CPU budget, and rewrites the file; `./scripts/gate.sh -record-durations ./<dir> ...` rewrites only the named packages' rows. After each full-tier sweep the gate checks the record against the run (`sweepCostStale`): a sweep that ran more than 3 times its recorded sweep, or ran 10 minutes with no record, gets a note naming the record command. The note is not a failure, since load lengthens a run; the failure a stale record causes is the deadline it sets. Instead the record corrects itself: once every step has ended and the gate's records are written, the gate rewrites each stale row from its run (the sweep becomes what it ran, its slowest run grows in proportion; `rewriteStaleSweeps`) and says to commit it. Before that a write would change the checkout under the sweeps still running. The first row, `internal/sketchfront`, was recorded at 74 load: slowest run 36 s, sweep 81 s.
- **Observed test times** (gate-speed GS33b). Each fast-tier test step runs `go test -short -json`, and each full-tier package test step (a shard, and `go test (other packages)`) runs `go test -json`. The gate keeps each top-level test's wall time in its cache (`test-seconds/`, the last 3 per test) and prints the text plain `go test` would print: the package's lines, a failed or unfinished test's lines, nothing of a passed or skipped test. A test with no time in either runs in the fast tier once and is observed, and a test seen at `sizeCutoff` (2 s) or longer runs only in the full tier from the next run on. The hermetic step replays Go's test cache and observes nothing. Before this, the file had no row for 37 of `internal/sketchfront`'s 58 tests, and `TestStdSnapshotAgrees` (147 s) ran in every fast run.

It took 23m52s for `internal/sketch/lower` at a CPU budget of 2 (1936 CPU-s). A package with rows there deals its full-tier shards and weighs them by CPU (`shardCosts`). The fast tier keeps dealing by wall time: dealt by CPU (GS16), `cmd/ergo` and `internal/sketch/lower` split into 4 and 3 fast shards after a std edit and spent about 80 and 100 CPU-s where one step each spent 52 and 47, since every shard pays the process's own start-up and in-process caches again, and the fast tier is CPU-bound at its budget of 4; the size rule keeps reading wall time, so the fast tier's selection does not move. - **Hang deadlines.** No step relies on go test's default 10-minute timeout as a budget. Every go test command of every step passes `-timeout`, ten times the step's recorded cost (`Step.Weight`), at least 30 minutes (`hangDeadline`, `testTimeoutFor` in `scripts/gate/testcpu.go`; `TestGoTestStepsHaveHangDeadlines`), so load slows a step and never fails it. The closure sweep bounds each run of a package the same way, by its recorded cost; a run that holds a test with no recorded time (a new test, before the batch's re-record) has no bound but the sweep step's own `-timeout` (CS1: the new `TestDirectMatchesGoBuild` outran the 30 minute floor). A focused check run by hand gets go test's 10 minutes unless it passes `-timeout`: `internal/sketchfront` costs about 170 CPU-s with a cold `GOCACHE` (its test binary links the checker and the lowering, and its build tests compile the runtime once), about 650 s at one CPU under load, so set `GOFLAGS=-timeout=30m` (go test reads it, other go commands ignore it) or pass `-timeout`.
- **Std's embed is a leaf (gate-speed GS25).** When a package's embedded files change, Go recompiles every package that imports it. If the recompiled package's output is unchanged, the recompiling stops there.

- **Test-impact selection (gate-speed GS4).** In the fast tier, the steps of `internal/sketch/check`, `internal/sketch/lower` and `cmd/ergo` (`selectPackages`) run only the fast tests that an edit can reach. The full tier still runs every test.
  - *The record.* `./scripts/gate.sh -record-durations -coverage [./<dir> ...]` builds the package's test binary with `-cover` over every module package it compiles. It then runs each fast test alone, with `-short` and the step's variables, its own `TMPDIR` and `GOTMPDIR` (gate-speed GS10: a shared `GOTMPDIR`, whose listing every go build changes, was read by 46 cmd/ergo and 12 lower tests and selected them after any edit), plus a test log that internal/testinputs completes by observing child processes. A cmd/ergo test runs the CLI the record built with the same coverage (`ERGO_TEST_CLI`, gate-speed GS11), through a wrapper that writes its counters beside the test's, so its blocks count and it does not build the CLI from source, a build that read every source file and selected 34 of the 55 tests after any compiler edit. For each test it keeps the blocks the test ran, every file, directory and lookup its process tree read (with their state), and the variables it read. It also keeps the digests of the compiled inputs and the base sources. All of this goes in `coverage/` under the gate cache. It took 10.7 minutes for the three packages (726 CPU-s) at 2 CPUs. Re-record on each new main.
  - *The selection* (`selectTests` in `scripts/gate/selection.go`). A known test that passed at the record is skipped when the edit touches none of the blocks it ran, nothing it read, and no variable it read. The skipped test joins the names the package's shards `-skip`, so a test the record does not know still runs. The gate prints `gate: <step>: selected k of n fast tests …`.

Also a test file, an embedded file, `go.mod`, or a file added to or removed from a compiled directory. The exception is an edited embedded file of `internal/sketch/std` (gate-speed GS9, `observedEmbeds`): the record sets `ERGO_EMBED_OBSERVE` to the checkout root, and std then opens each `.ergo` file it reads at its checkout path, in the test and in the `ergo` processes the test starts, so the test log names its readers and only they run. Changes that cannot change a verdict select nothing: `GOCACHE`, `GOMAXPROCS`, `GOGC`, `GOMEMLIMIT`, `TMPDIR`, and `GOFLAGS`' `-p`.

Otherwise the step would link its test binary only to run nothing: `internal/bindc` and `internal/sketch/syntax` took 14 CPU-s that way on a std edit. Skipping that link is sound because go vet type-checks the package and its tests, and the edit reaches no test.

- **Longest chain first (gate-speed GS6).** A freed slot goes to the waiting step of highest priority (`stepPriorities` in `scripts/gate/priority.go`). A step's priority is its own expected seconds plus the longest chain of the steps that need it, so `build bin/ergo` goes before the examples step that waits on it.
  - Its own seconds are the longest of its last 5 times on this host. The gate keeps those times in `step-times.json` in its cache directory, recording each step that passed, either run or replayed at its recorded cost.
  - With no record, it uses `Step.Weight`, and failing that `unrecordedWeight`.
  - The examples step declares 434 s in the full tier and 134 s in the fast tier. That is its cost when every program builds again; with no weight it started at 101 s of the batch-18 fast tier.
  - The file orders steps only. No key holds it, and a missing or unreadable file falls back to the declared weights, which is what the merge tier's empty sandbox cache gets.
- **Memory budget.** Every step runs under a hard memory cap that covers the step and every process it starts: `ERGO_GATE_STEP_MEMORY` (default `8G`) per step, `ERGO_GATE_MEMORY` (default half of physical memory, in whole gigabytes) for all the steps of one gate together, and the bound of the gates' slice for all the gates of the host together. `ERGO_GATE_HOST_MEMORY` (default three quarters of physical memory) lowers only this gate's own budgets to it; it never changes the slice's bound. Go processes in a step get `GOMEMLIMIT` at 3/4 of the step cap unless the caller set `GOMEMLIMIT`. `--record-durations` runs its packages under the same budget.
  - *systemd scope (Linux with a working `systemd-run --user`).* The gate runs itself in one transient scope in the user slice `ergo-gates.slice`. The scope has `MemoryMax` = gate budget + 512M for the gate process itself, and `MemorySwapMax=0`; the swap setting holds for every cgroup below the scope. The gate moves itself to a `gate` leaf, and every step runs below a sibling `steps` cgroup with `memory.max` = gate budget. So when steps reach the step or gate budget, the kernel's out-of-memory killer chooses among the steps' processes and never the gate, even when a stopped step's memory is not yet freed. (The kernel chooses a victim by size and `oom_score_adj` alone; `memory.min` and `memory.low` do not change the choice, and an unprivileged gate cannot lower its own `oom_score_adj`.) The gate reads both bounds back before every step and refuses to start a step without them. If a named scope cannot set them up, the gate fails instead of switching to the RSS watch. The slice's `MemoryMax` belongs to the host: a gate sets it only when the slice has none, and then only to the default, three quarters of physical memory (a runtime setting, which every gate writes alike). A gate never lowers or raises a set bound, so one gate's `ERGO_GATE_HOST_MEMORY` cannot stop another gate. To change the bound for every gate, set it on the slice: `systemctl --user set-property --runtime ergo-gates.slice MemoryMax=<size>`. When the bound is below this gate's budget, the budget line says so (`…, 24G across gates in ergo-gates.slice, below this gate's 31G`). Each step starts in its own cgroup below `steps` with `memory.max` = step budget and `memory.oom.group=1`, so an out-of-memory kill stops the whole step. When the gate or host budget is reached, the kernel stops the largest process under it, and it can stop two steps when the first one's memory is not yet freed. The gate waits for the kernel's `cgroup.events` `populated 0` state before finishing step cleanup and draining output. The gate reads the step's `memory.events` (and the `memory.events.local` of `steps` and of the slice) to say which budget stopped it. A gate started inside another gate's step opens no scope: the outer step's caps hold, and it watches its own steps' RSS.
  - *RSS watch (darwin, a container, no user bus, or `ERGO_GATE_MEMORY_MECHANISM=rss`).* Each step runs in its own process group, and the gate samples resident memory every 250 ms. It stops a group over the step budget, and the largest group when the sum passes the gate budget. A fast step can pass its budget between two samples: peaks of 639.9M to 724.5M under a 512M budget were measured (up to 41% over). This mechanism has no bound across gates, and a process that leaves its step's process group leaves the watch.
  - The gate prints the mechanism once (`gate: memory budget: systemd scope 8G per step, 31G per gate, 47G across gates in ergo-gates.slice`). A step over its budget fails with `memory budget exceeded (<budget>)` (`gate memory budget exceeded`, `host memory budget exceeded` for the larger caps) and its output, and is never recorded as passed. The other steps keep running. Each step line reports its peak memory. Do not cap the gate with `ulimit -v`: Go reserves far more address space than it uses.
- **CPU budget.** A gate uses at most its CPU budget, `ERGO_GATE_CPUS` (default half of the usable CPUs, at least 2; never more than the usable CPUs). The usable CPUs are the CPUs of the gate's affinity mask (`taskset`), lowered to the tightest `cpu.max` of its cgroup and every cgroup above it, rounded up; not the host's CPU count. A value that is not a positive whole number fails the gate before it starts, with one line (`gate: ERGO_GATE_CPUS: "x" is not a positive whole number of CPUs such as 4 or 8`). The budget bounds how many steps run at once (a freed slot goes first to a step that writes the checkout or that such a step needs, because every closure sweep waits for the writers; then to the heaviest waiting step, by its expected seconds from `durations.json`: a test step weighs its tests' recorded time, a closure sweep four times its package's (a host package's sweep, which does not run its tests, the default), and a step with no recorded time, such as `go vet` or a package that has no rows yet, weighs a stated default of 30 s (`unrecordedWeight`), not the heaviest; `TestStepsWeighTheirRecordedTime` fails while a test package has no rows; `slotPool` in `scripts/gate/slots.go`, `Step.Weight`), the shards of a package (below), the host packages' `-parallel` (at most 8), the gate's own `GOMAXPROCS`, and the `GOMAXPROCS` of every step's Go processes: the caller's `GOMAXPROCS` when it is a whole number within the budget, else the budget. It also bounds the go command's `-p` (`stepGOFLAGS`): the gate appends `-p=<n>` to every step's `GOFLAGS`, after the caller's flags, where `n` is the caller's last `-p` when it is a whole number within the budget, else the budget. cmd/go applies `GOFLAGS` in order and the last value wins, so a caller's `GOFLAGS=-p=16` cannot raise it; every go command a step starts inherits it. A test binary's `-parallel` defaults to `GOMAXPROCS`, so it follows the budget. Each step's receipt key holds the budget, so a step's pass under one budget is not replayed, or promoted into a whole-gate record, under another. The gate passes `GOMAXPROCS` explicitly because Go's runtime reads only the `cpu.max` of the cgroup its process is in, and none in the merge tier's sandbox, which has no `/sys`: there a Go process without it took all 16 CPUs of this host (measured 2026-11-05).
  - *systemd scope.* The kernel also enforces the budget. The scope has `CPUQuota=<budget × 100>%`, and the gate checks that the scope's `cpu.max` reads back as the budget; else it fails before any step, as it does for the memory bounds (`gate: cpu budget: systemd scope <unit> does not enforce the CPU budget: …`). Each step's cgroup has `cpu.max` at the budget too, so a Go child that drops `GOMAXPROCS` still sees the budget (Go's runtime never sets fewer than 2). The merge tier's sandboxed steps run in the same step cgroups. The gate prints the budget once (`gate: cpu budget: 8 CPUs, systemd scope CPUQuota=800%, cpu.max 800000 100000 per step`).
  - *Elsewhere* (RSS watch, darwin), the budget bounds the steps at once and `GOMAXPROCS` only (`gate: cpu budget: 8 CPUs, steps at once and GOMAXPROCS (no cgroup)`).
- **Step lifetime and temp files.** After a step leader exits, the gate stops the remaining members of its process group or systemd cgroup before finishing output. The RSS watch waits until no process of the group can hold the output pipe: a zombie leader whose other threads still run (`Zl` in Linux `ps`) still holds it, and a zombie without threads does not. Its leftover diagnostic names live processes only. The systemd path waits for `cgroup.events` to report `populated 0`. It drains buffered output without waiting for an outside writer; a process that still holds a pipe makes the step fail with a diagnostic (`step output held open by a process outside the step's process group or cgroup`). One holder is not an escape: a sibling fork of the gate. Go forks in parallel, and a child forked while a step's writer is open holds a copy of it until its exec closes it. So at the first read that would block after the step ended, the gate first waits, at most 5 s, for every fork in flight (`forkSettleBound`), then reads on, at most 1 s, to the end of the pipe (`execTailBound`, `scripts/gate/budget.go`); a writer still held after both bounds fails the step as before (`TestRunBudgetedWaitsForASiblingForkInFlight`, `TestRunBudgetedWaitsForASiblingForkExecTail`, `TestRunBudgetedReportsAHolderPastItsBounds`; batch-9 B1). Each step gets a stable per-checkout, per-step `TMPDIR`, protected by an exclusive file lock across gates. The gate restores directory permissions and empties the directory before launch and after the step stops.
- **Disk.** A step does not start when its `TMPDIR` or the gate cache (which holds the merge tier's sandbox) has less free space than `ERGO_GATE_DISK_FLOOR` (a size such as `2G`, the default; `0` turns the check off). It fails at once with `gate: <step>: not started: disk floor: <n> MiB free under <path>, below the floor of <m> MiB`, and free space it cannot read fails it too (`TestStepBelowDiskFloorIsNotStarted`). Before this, a merge tier that filled the disk failed its closure sweeps partway with ENOSPC. Those sweeps were what filled it: internal/closure's std store (a GOCACHE of the compiled standard library, 781 MB) lived under each step's own `TMPDIR`, so each sweep step filled one of its own. Measured in a live merge tier's sandbox: ten of them took 7.7 GB of its 12 GB. The gate now gives every sweep step one store directory, `ERGO_CLOSURE_STD_DIR` = `$TMPDIR/ergo-gate/closure-std` of the gate (inside the sandbox's scratch temporary directory in the merge tier), so a run fills it once and the other sweeps link from it (`TestSweepsShareOneStdStore`; `TestStdStoreHoldsOnlyStdCompiles` counts no build for a sweep with another `TMPDIR`).
- **Scope setup comes first.** In its systemd scope the gate opens its limiter before it starts any process: it moves itself to the `gate` leaf and enables the controllers for the scope's children, and only then runs git and `go list ./...` to find the checkout and declare the steps. The kernel refuses the controllers (`EBUSY`) while any process stays in the scope's own cgroup, and a command that returned can leave a descendant: `go list` starts Go's telemetry sidecar, which can outlive it. A process started after the setup is born in the gate's leaf, where it does no harm (`TestScopeSetupPrecedesDiscovery`). Before it enters the scope, the gate starts only the scope probe and, on the replay path, its fingerprints; these stay in the caller's cgroup.
- **Stop.** `SIGINT`, `SIGTERM` and `SIGHUP` stop the gate, in both tiers, unless it was started ignoring the signal (`nohup` ignores `SIGHUP`, a background job of a non-interactive shell ignores `SIGINT`): then the signal stays ignored. On the first one the gate starts no new step and no new command, and kills every running step whole: its cgroup (`cgroup.kill`) in the systemd scope, its process group under the RSS watch. The merge tier's sandboxed processes are among them: nsenter starts them in the step's cgroup and process group. Every other process the gate starts (`git`, a tool query of a fingerprint, `go list`, `systemctl`) runs in a process group of its own, and the gate kills that group too (`runCommand`, `scripts/gate/stop.go`). So does each `ps` of the RSS watch's sampler. The `ps` that a step's finish runs, to confirm that the step's process group has stopped, is tracked as a command of the step (`runInStep`): a stop neither refuses nor kills it, and waits until it has ended. So every process the gate starts is tracked, and none is in flight when the gate exits (`TestRSSWatchTracksItsPS`, `TestStopWaitsForACommandInAStep`; batch-9 B2). The gate waits until each of those steps is empty and each command has ended, and then closes the merge tier's sandbox, which removes its run directory. In the scope it also kills every process left in its own leaf, such as a descendant that left its group or a telemetry sidecar, until it reads the leaf back empty. Then it exits with 128 plus the signal's number (130 for `SIGINT`, 143 for `SIGTERM`), and its last line says only what the stop proved: `gate: stopped by SIGTERM; every process it started has ended` when the leaf read back empty; under the RSS watch, which has no leaf to read, `gate: stopped by SIGTERM; every step and command it started has ended, with its process group`; and `gate: stopped by SIGTERM; not every process it started has ended: <reason>` when a cleanup failed. A second stop signal during a stop exits at once, as a second Ctrl-C does in Bazel, with `gate: stopped by SIGINT, then SIGTERM before the stop ended; processes it started may remain` (`TestStopperServeExitsOnASecondSignal`); this is the way out of a stop that cannot finish. No process the gate started outlives it, so none keeps a descriptor that the gate inherited from its caller, such as the lock of `flock gate.lock ./scripts/gate.sh` (`TestGateStopsItsStepsOnSignal`; and, for a `SIGTERM` to the gate's whole process group in the merge tier's sandboxed phase, `TestMergeGateStopsOnGroupSIGTERM`, which also checks that the sandbox's run directory is gone). Before this change, a `SIGTERM` to a gate in its scope left its steps running with ppid 1 and still holding the caller's lock (measured 2026-11-05 and 2026-11-06). Under the RSS watch, the gate does not stop a descendant that has left its step's or command's process group, because it has no cgroup to find it; its last line then claims no more than the groups. `scripts/gate.sh` executes the gate in its own process (`exec`), so a signal to the script's process is a signal to the gate (`TestGateScriptExecsTheGate`). Before, it started the gate with `go run`, which does not pass `SIGTERM` on. The binary is `<gate cache>/bin/<checksum of the checkout path>/gate`, one per checkout, and `go build` relinks it only when the gate's sources changed. A stop that begins while the gate probes or replays, before it re-executes itself in its scope, stops the gate there: the re-execution checks for a stop and executes under the stopper's lock, so no stop can begin between the check and the exec (`TestStopperRefusesTheScopeExecDuringAStop`). A signal that the Go runtime takes in the microseconds of `execve` itself is lost with the old process image; blocking the stop signals across `execve` would keep it, but the new runtime would give that blocked mask to every step it starts.
- **Test Go store.** The cmd/ergo test steps get `ERGO_CMD_TEST_GO_STORE`, a store of the direct build path's plans, actions and blobs in `test-go-store/go-<fingerprint>` under the gate cache. The store is keyed by the go command's fingerprint and outlives the run, so a gate reuses the program compiles of the gate before it. Its entries are content-keyed, so the step key holds only that a step gets a store. A `--no-cache` run gets a fresh store, removed when it ends, so that the reference run builds from cold. The merge tier's sandbox gets none. After each run the gate trims the stores to 1 GiB, least recently used first, and prints what is left (`gate: test go store: …`; `scripts/gate/gostore.go`, `TestGoStoreTrimHoldsTheBound`).
- **Step output.** A step's stdout and stderr go to an unlinked spool file in `output/` under the gate cache (below; `$TMPDIR/ergo-gate` when there is no cache directory), not to the gate's memory. The gate prints the spool in declaration order through a 32K buffer, so what it holds in memory for a step does not grow with what the step prints, and a step's output cannot fill the gate's 512M reserve in its scope. A file on tmpfs or ramfs keeps its pages in memory charged to the process that writes it, so on Linux the gate writes step output only to a destination it admits, judged on the opened file and not on its path (a link to tmpfs does not pass): a pipe, a terminal, a socket, a device, or a regular file on a disk file system. The admitted disk file systems are ext2/ext3/ext4, xfs, btrfs, f2fs and zfs. Every other file system is refused, overlayfs (its upper directory can be tmpfs), FUSE and NFS included. Each refusal names the file system it found and how to fix it:
  - an output spool refused: the gate exits 2 before any step runs (`gate: output spool in <dir> is on file system <name> ...`); set `ERGO_GATE_CACHE` to a directory on disk whose `output/` is on disk too;
  - the gate's standard output a refused file: the gate exits 2 before any step runs (`gate: standard output is on file system <name> ...`); redirect standard output to a disk file or a pipe;
  - a cache output file refused: the step passes and prints its output whole, but its pass is not recorded (`gate: <step>: pass not recorded: cache output file in <dir> is on file system <name> ...`), so the next run executes it again; set `ERGO_GATE_CACHE` to a directory on disk.

  Off Linux the gate admits every destination: the RSS watch bounds only the steps' resident memory there. A spool write that fails, such as on a full disk, fails the step, and the gate still reads the step's output pipe to its end. Output the gate cannot print whole fails the step (`gate: <step>: print output: <error>`).
- **Which layer may reuse which result.** Three layers can skip a check: Go's test cache inside a `go test` step, a step receipt (`Inputs`), and the whole-gate record (below). A layer may skip a check only when its key holds every input the check reads. A whole-key miss does not empty the inner layers, so each inner layer must be sound alone.
  - *Go's test cache.* cmd/go rechecks a cached result only against the files the test process opened inside the package's own module, and a step can start a program that starts a `go test` in a way no reader of the step's argv sees (`go run -exec`, `-toolexec`, `-vettool`, a shell expansion; gate-testcache-gap rounds 1 to 3). So the gate's go tests are uncached by default and cached only by declared exception: every step runs with `-count=1` added after the caller's `GOFLAGS` (`stepEnvironment` in `scripts/gate/main.go`), which every `go test` the step starts inherits at any depth and which `go build`, `go vet`, `go run` and `go list` ignore, and only the hermetic step (`Step.Hermetic`, the packages below `scripts/gate/` that `TestCachedGatePackagesAreHermetic` checks) runs without it and replays from Go's cache. `TestTestCommandsHaveCacheCoverage` proves this on the environment the gate builds for each step, not on argv shapes, and `TestProgramsStartUncachedGoTests` runs each of round 3's forms as a real step twice and requires a rerun. Threat model: the guard protects against an accidental gap, a new step or test whose `go test` could replay a stale pass; a step that sets `GOFLAGS` or a `-count` other than 1 on purpose is out of scope, and a literal tripwire fails the test on either word in a step's argv, its `Env` or a reviewed script, so the change shows in review. This default is hygiene for the inner tier, not a merge verdict: a tool that gives its child its own environment (a fresh `Cmd.Env` without `GOFLAGS`, its own `HOME`, `XDG_CACHE_HOME` or `GOENV` naming a `GOCACHE` on the host) can still replay a stale pass from a cache on the host (gate-testcache-gap rounds 4 and 5), and the inner tier and its whole-gate record can carry that pass. Only `--merge` gives a merge verdict: its uncached run is in a sandbox with no cache that outlives the run (Merge tier, below). As hygiene, a step starts only a program on an allowlist, by its exact name (`go`, `env`, `timeout`, `sh`, `./bin/ergo`), sets only `ERGO_REPO_ROOT` or `CGO_ENABLED`, and runs a shell only as `sh -c SCRIPT` with SCRIPT byte for byte an entry of `reviewedScripts` (`scripts/gate/reviewed.go`); `TestReviewedScripts` refuses an entry that no step runs. The cost: a real run reruns every observed main-module test that Go's cache used to replay; a whole-gate replay runs no step and is unchanged. Measured 2026-11-05 on this 16-CPU host, interleaved, with a 1-minute load of 14 to 33 and so no speed verdict: a `--no-cache` run took 337 s after against 364 and 378 s before (the `go test (other packages)` step 1,025 s of CPU against 964 s on the warm run before), and a no-op replay 0.66 to 0.93 s after against 0.74 to 1.16 s before (gate-testcache-gap cost-r4.log). The provenance analyzer's controls (`tools/provenance`, its own module) read the checker's syntax sources in their own process and through `analysistest`, so they run with `-count=1`: before, a field removed from a syntax source replayed their pass while a fresh run failed (measured 2026-11-04, gate-testcache-gap). The sketch9 kernel tests run with `-count=1` for the same reason. Running the controls every time the step runs adds about 2.3 s to that step (planner minima at a 1-minute load of 15 to 26); a whole-gate replay runs no step.
  - *Step receipts.* A step with no receipt runs on every whole-gate miss. A step whose result depends on an input that no digest of declared paths, tools and variables holds gets no receipt. The Effect mapping check (`effect conformance mapping`) asks Git whether each evidence file is tracked, and the index is not a declared input: untracking an evidence file kept its receipt and replayed a pass (measured 2026-11-04). The step has no receipt now. It takes about 0.15 s, less than the 0.4 s receipt lookup it replaces (measured at a 1-minute load of 22 to 29).
  - *Whole-gate records.* The key holds the index and every path, so a whole replay covers both reads above.
  - `TestGateCacheParityModel` checks the three layers together on a fixture checkout, with real Go test caching and the real mapping validator: a nested module whose controls read a main-module source, a main-module test that reads it only through a child process under observation, and the mapping step over a tracked or untracked evidence file. It runs gates, merge-tier runs, source and index edits, restores and cache sweeps, and after each invocation it compares the gate with a reference model: replay or not, exit code, each step's verdict, and which inner cache answered. With the gate's own steps, no step passes while its fresh run fails. Two negative controls put back the removed reuse (the controls without `-count=1` and in the hermetic exception, the old mapping receipt); each must show a stale pass from a real cache hit, and the merge tier must withdraw a stale whole record so that the next gate does not replay it. The model assumes inputs that do not change during a run: an edit made and reverted during a run (ABA) is still found only by the merge tier.
- **Go tests** in the inner tier rely on Go's own test cache where the step lets it (above); the merge tier's uncached run starts with an empty one. `cmd/ergo`, `internal/sketch/check` and `internal/sketch/lower` (`slowPackages`) are each split into processes using the measured durations in `scripts/gate/durations.json`, or the recorded CPU in `scripts/gate/test-cpu.json` where a package has rows: one shard for each 12 s of measured work (`shardTargetSeconds`), at most the CPU budget, so the shard count follows the budget. The checker and the lowering ran their tests in one process, one at a time (294 s and 509 s serial at a budget of 4, measured 2026-11-06, gate-fast plan); at a budget of 8 each is now 8 shards (`TestCheckAndLowerShardByTheCPUBudget`). Each shard is a step with its own `TMPDIR`, and no test of the two packages writes a fixed path outside its temporary directories (reviewed 2026-11-06), so shards share no file. Every shard but the last selects tests by exact name; the last shard skips exactly the names the others selected. So the union of shards covers every test, including tests added since the durations were last recorded. A stale durations file costs wall time, never coverage.
- **The gate's own tests: host and hermetic.** Go's test cache records the files, environment variables and module source a test reads. It does not record the programs a test runs or the shared libraries they load, so no list of program names can make a cached result safe. The gate's own tests are therefore in two kinds of package:
  - *Host packages* (`hostTestPackages` in `scripts/gate/steps.go`) hold tests whose results depend on the host: programs (git, `sh`, `ps`, `systemd-run`, the go command), cgroups, the user's service manager, and the file systems of the temporary directories. `scripts/gate` is one: the gate runs git and `ps` on every run, and its output-storage property runs gates in real systemd scopes. The gate runs each host package with `-count=1` in its own step (`go test ./scripts/gate (host, every run)`), only in the full and merge tiers (`classHeavy`), so Go's test cache never replays a host test. A lane that edits `scripts/gate` runs the package as a focused check. In the full tier each test that starts the merge tier's sandbox and no gate in a systemd scope (`sandboxHostTests`) runs in a step of its own beside the package's step, which skips it: these tests run one at a time and build in a cold sandbox cache, so in one step they added up to most of the package's time (300 s of 509 s at batch 9 on a quiet host), and under the batch-9 gate's load the one step passed its 15-minute test timeout. The step replays only inside a whole-gate replay (below). The step passes `-parallel 8`, or the CPU budget when it is below 8 (`hostTestParallel`): every host test that sets no process-wide state (`t.Setenv`, the working directory, package variables, the shared test slice) runs in parallel, at most 8 at once. Go's default is the step's `GOMAXPROCS`, which is at most the CPU budget, so the bound can lower it only when that is above 8. The 8 was measured before the CPU budget, when the storage layouts ran as parallel gates: at 4, 6 and 8 on a 16-CPU host the package took 151 s, 126 s and 114 s (2026-11-04). No parallel host test starts a gate in a systemd scope now. The 24 output-storage layouts run one at a time on 31 MB of step output, and check the gate's resident memory directly, so the property takes about 60 MiB of disk at its peak; with 1.09 GB of output, eight layouts at a time took 14.2 GB (measured, 2026-11-05).
  - *Hermetic packages* are the other packages below `scripts/gate/`. In the full tier they replay from Go's test cache. In the fast tier each has a keyed step of its own, as every test package has, built with `CGO_ENABLED=0`: to find a cached result Go relinks both test binaries, about 20 s on every run (measured 2026-11-06), and a package key replays without starting Go. Each runs no program except its own test binary (through `os.Executable()`, in one helper), and its step (`go test (hermetic gate packages)`) builds it with `CGO_ENABLED=0`, so it loads no shared library. The host test `TestCachedGatePackagesAreHermetic` checks this on every gate: for every gate package that a step lets Go cache, it lists the test binary's packages (`go list -deps -test -export`, in the step's environment) for Linux on amd64 and arm64 and for macOS on arm64, and checks them with `scripts/gate/hermetic`. That check type-checks the module's source in each of those configurations, with the standard library's types from the export data, and decides what a name denotes from the types, never from its spelling: a local value, a parameter or another package named `os` cannot stand in for `os.Executable`. A program it admits is a local variable defined once by a call of the `os` package's `Executable` and never written again or address-taken. A file that none of the three configurations builds, or a package that does not type-check, is refused. It refuses a call that runs another program, a program lookup on PATH, a raw system call that can be `execve`, cgo, plugins, `go:linkname`, a standard-library package that imports `os/exec` (except the fuzzing engine), and a package from outside the module and the standard library.
- **Go test inputs are observed.** Go's test cache keys a result on the files and variables the test process reads through package `os`. It cannot see what a child process reads: git, `sh`, a C compiler, or a `go build` that a test or the code under test starts. So every test package's `TestMain` calls `testinputs.Main(m)` (or `testinputs.MainFunc` when it prepares the test process). Main runs the test binary again as a child. The child installs a seccomp filter with a user-notification listener, writes the listener's number on a socket to the parent, which takes the listener itself with `pidfd_getfd` (Linux 5.6). Sending the listener by `SCM_RIGHTS` would need a `sendmsg` the filter lets through unnotified, since no one serves the listener before it arrives, and a process forked before that gap closed could use it to pass a socket address by the observer; taken this way, the filter has one rule for every process and no exception. `pidfd_getfd` needs the access ptrace would (`PTRACE_MODE_ATTACH_REALCREDS`: the same user, a dumpable child, and Yama's consent, which `ptrace_scope` 0 and 1 give a parent). The parent first takes a descriptor the child holds from its start, its end of the socket, and tells the child whether to install the filter at all, so a host that refuses (`ptrace_scope` 2 or 3) runs the tests unfiltered and refuses the result instead of leaving the child waiting on a listener no one serves. This workbox has no Yama (kernel 6.12, LSMs capability, landlock and selinux, not enforcing), and the take succeeds. Then the child runs the test binary again by exec: the filter survives exec, so every package initializer runs observed, including those Go ran before testinputs' own. The filter suspends every open, stat-like lookup, write that depends on what exists (`mkdir`, `unlink`, `rename`, `link`, `symlink`, `chmod`, `setxattr` and the like), `chdir`, exec, and `connect`, `bind`, `sendto`, `sendmsg` and `sendmmsg` with an address, the child and its descendants make until the parent has read the call's path; the call then continues unchanged. The test process trusts the observer's variables (`ERGO_TESTINPUTS_LISTENER`, `ERGO_TESTINPUTS_FILTERED`) only once it proves the observer exists: the descriptor a variable names must be a socket whose peer is its parent (`SO_PEERCRED`), kept open across the exec, and the exec'd process must run under a seccomp filter. A variable inherited from a shell or another runner fails that proof, and the result is refused as unobserved. When the child exits, the parent appends to Go's test log:
  - `open` for a file read or a program run, with the `#!` interpreters it names, and for a directory listed, which cmd/go keys on every entry's name and metadata;
  - `stat` for every other lookup, failed ones included, so a file added later is an input, for a directory changed to, and for the path of an AF_UNIX socket connected to, bound or sent to (an abstract or unnamed address names no file); a path both read and looked up gets both lines, since `open` does not look at a link itself. After the run, every link inside the root on the way to a recorded path gets a `stat` too: cmd/go rechecks an `open` path by what it leads to, and a retargeted link may lead to a file with the same size and time;
  - `getenv` for every variable in the environment of every program run, plus `ERGO_TOOL_VERSIONS` whenever a program ran.

  A path outside the module root is dropped, because cmd/go never rechecks such paths, unless its lookup reaches the root through a link. The parent resolves it one component at a time, as the kernel does, and records the rest of the path from the point it enters the root, unresolved: a link inside the root that is later retargeted, or a directory there that is missing now and added later, then changes the key. Nothing the observed processes can change is remembered between calls; only what a lookup finds in a directory that another user owns and this user cannot write, on a path of such directories, is (never when the tests run as root, with real, effective, saved or file-system user or group IDs that differ, or with `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, `CAP_FOWNER`, `CAP_SETGID`, `CAP_SETUID` or `CAP_SYS_ADMIN` permitted or effective). A name relative to a working directory or a directory descriptor reached through a link inside the root (`cd dirs/current`; `openat` on, or `fchdir` to, a directory opened as `dirs/current`, with or without `O_DIRECTORY`) is recorded under the link as well as under the directory. fabricate.py tracks working directories per process and copies one to a child at `clone`, `fork` and `vfork`, which strace reports with the child's pid. A seccomp notification comes before the call, so the observer never learns a child's pid at the fork, and by the child's first lookup its parent may have exited and the child been reparented. So each link inside the root that a `chdir`, or the open of a directory (judged by the file the path leads to), crossed is remembered by the directory it leads to, for the whole run, and any process whose working directory, or a descriptor it names a path relative to, is that directory records its relative names under each such link too: a reparented child, a descriptor passed to another process and an `fchdir` (which is not notified) are covered, and a process that reached the directory another way gets an extra entry, which can only cause a rerun. A read open in the root costs one more `stat` for this, and a directory one more open and `readlink`. `/proc/self/cwd/…`, `/proc/<pid>/root/…`, `/proc/self/fd/<n>/…` and `/dev/fd/<n>/…` are read through the caller's links. Other paths under `/proc`, `/dev` and `/sys` are skipped, judged after `..` is resolved, so `/proc/../<root>/x` is recorded. This happens in Main, so `go test` run by hand observes exactly as the gate does. `internal/testinputs/guard` fails any test package without a `TestMain` that calls Main on every platform; `ERGO_TESTINPUTS_GENERATE=1 go test ./internal/testinputs/guard` writes the missing ones. It finds test packages under any build tags by walking the tree as `./...` does (skipping `testdata`, names starting with `.` or `_`, nested modules and links to directories), with ordinary directory reads that Main records, so a new package, tracked or not, in any clone, worktree or Rift, changes a listing and reruns it. `internal/testinputs` itself is exempt: its end-to-end cases run observed fixture binaries, and observation does not nest (a listener installed below another hides the calls it takes from the outer one). Those cases prime Go's cache, edit what only a subprocess read, and require a rerun, each beside a control with a plain `TestMain` that must replay its stale result.
- **Unobserved results are never cached.** When Main cannot observe, it leaves the test log without its final newline and prints `testinputs: result not cacheable, inputs unobserved: <reason>`; cmd/go then refuses to cache the result (`saveOutput` in `cmd/go/internal/test`), so the package reruns every time instead of replaying a result keyed on a partial list. That happens on another operating system or architecture (observation needs Linux 5.7 or later on amd64 or arm64), when seccomp is refused, when the parent may not take a descriptor from the child (`pidfd_getfd` refused: Yama's `ptrace_scope` 2 or 3, an undumpable test binary), when the parent cannot read a suspended call's memory that the kernel can (`process_vm_readv` fails other than with `EFAULT`, as for a process that made itself undumpable), when a process makes a call that would hide later accesses (`chroot`, `pivot_root`, `unshare`, `setns`, `mount`, `umount2`, the new mount API (`open_tree`, `move_mount`, `fsopen`, `fsmount`, `fspick`, `mount_setattr`), a namespace-creating `clone` or `clone3`, `open_by_handle_at`, `fanotify_mark`, `quotactl`, `quotactl_fd`, `bpf` (which watch or open paths without a lookup the observer sees), its own seccomp listener, a call of another ABI, a system call numbered above the last one of Linux 6.12, which the observer cannot classify), for a path or variable name that holds a newline, which the log cannot carry, when an observer variable is set without an observer behind it, and when the log cannot be marked (the test then fails, since cmd/go never caches a failure). `io_uring_setup` fails with `ENOSYS` under observation, because a ring opens files without system calls; a program that uses one must fall back to ordinary calls.
- **What observation does not key.**
  - Files outside the module root: tool installations, `~/.gitconfig`, user caches, system libraries. `ERGO_TOOL_VERSIONS` stands for the installations (below); tests that run git isolate it from user configuration (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`). In a linked worktree or a Rift, `.git` is a file naming metadata outside the root, so the HEAD, index and objects a test's git reads there are not keyed either. In a clone, such as the merge tier's export, `.git` is a directory inside the root. A `git status` there, and the go command's VCS stamp that runs one (`go build` or `go list ./...` of a main package), writes `.git/index.lock` and `.git/index`, which a sweep observes as a change of the checkout during its run. So every git process that Go code in the repository starts passes `--no-optional-locks` first (`TestGitCallsTakeNoOptionalLocks` in `internal/residue`), and every step runs with `GIT_OPTIONAL_LOCKS=0`, which reaches the go command's git too (`TestStepsTakeNoOptionalLocks` in `scripts/gate`). A package that runs git declares `.git` with its members (one entry for the path and each path directly in it: the file `.git` in a worktree, the files and directories one level down in a clone, where git reads no deeper), so it gets one verdict in both layouts (`TestGitMetadataVerdictIsTheLayoutsOwn` in `internal/closure`).
  - A variable that was unset when a result was cached, read by a program the test runs. A program's lookup of a variable is a library call, not a system call, so it leaves no trace, and cmd/go's log cannot say "every variable, present or not". The gate closes this for its own runs: a Go test step receives only the variables `internal/testinputs/testenv` names, whose values join `ERGO_TOOL_VERSIONS`, and the gate log prints the list. `go test` run by hand passes the caller's whole environment, so exporting a variable after a cached run can replay a result the variable would change; run `go test -count=1`, or use the gate. Every variable a started program receives is keyed, so running the tests by hand from a shell with a different environment reruns the packages that start programs.
  - Extended attributes: cmd/go's log has no entry for them, and changing one changes no modification time. `setxattr` and `removexattr` are recorded as lookups of their paths.
  - Two changes of a file inside one clock tick with the same size, and a change made with the old modification time restored (`touch -r`, `tar -x`, `rsync -a`, `cp -a`), for files: cmd/go rechecks a file by size, mode and modification time, not content. A directory listed is rechecked by its entries, so an entry added under a restored directory time is still seen.
  - A relative `#!` interpreter, which the kernel resolves against the working directory, and the dynamic loader an ELF program names (`PT_INTERP`). Every program here names an absolute interpreter and the system loader, both outside the root.
  - Races inside one run: a file the observed tree changes between the parent's lookup and the call it suspended, and a thread that changes the shared working directory, or reuses a descriptor number, while another thread's call waits. A link a `chdir` or a directory's open crossed is matched to working directories and descriptors by the directory it led to when the call was notified, which a link retargeted in between changes.
  - A runner that fakes the observer on purpose. The test process proves only that its parent created the socket it inherited and that some seccomp filter is installed (`Seccomp: 2` in `/proc/self/status`), not that the filter is this observer's: a `go test -exec` wrapper that makes a socket pair, sets `ERGO_TESTINPUTS_FILTERED` and runs the binary under an unrelated filter makes the tests run unobserved while believing they are observed. Any check the test process could make, such as a nonce the parent echoes, is one more message such a wrapper can answer, so the proof is aimed at what happens by accident (a variable inherited from a shell, a runner or a nested test), which it catches, and a deliberate wrapper is out of scope, as one that rewrites the test log is.
  - Processes a test leaves running after it exits: once the observing parent exits, their filtered calls fail with `ENOSYS`. The filter sets `no_new_privs`, so a setuid program does not gain privileges under a test.
- **What observation costs.** An observed call waits for the parent: a stat takes about 15 µs instead of 1.4 µs with synchronous wake-up (Linux 6.6 and later), most of it the kernel's round trip. The go command makes most of the calls: on every run it stats each standard-library source it builds on, and a seccomp filter sees registers, not paths, so it cannot pass those calls through. Measured 2026-10-11 on the 16-CPU workbox, with other lanes running:
  - each package's tests alone, observed against `-count=1`, two rounds: 2,060 s against 1,626 s of CPU time in total (+27%; `cmd/ergo` +24%, the legacy compiler package +28%, `scripts/gate` +43%). Wall time at a 1-minute load of 14–62 was 1,272 s against 822 s; an earlier measurement at load 13–73 gave 1,933 s against 1,551 s of CPU (+25%), with the wall times reversed, so the load swamps wall time;
  - the full gate, with every step and every Go test rerun: 108.2 and 135.5 s against 95.3 and 67.7 s on main (1-minute load 27–92 when each started, 68–91 when it ended; earlier pairs measured 99.1 and 149.1 s against 82.2 and 70.9 s, and 74.9–76.6 s against 50.1–60.8 s);
  - a gate with nothing changed: 4.6–7.0 s at a 1-minute load of 68–94, every Go test `(cached)` except the guard (below). On main, at loads of 62–75, the first no-op after a full run took 5.8 and 14.5 s (rerunning 1 and 7 test packages), and the second 5.5 and 3.2 s.

  A no-op stays a no-op only if no test reads what the gate rewrites. The gate therefore builds `bin/ergo` beside its cache and moves it into `bin/` only when its bytes change (`go build` touches its output even when it relinks nothing), and a test that builds a command inside the repository passes `-buildvcs=false`: VCS stamping runs `git status`, whose walk would make the result depend on every file in the working tree, build outputs included. For the same reason the gate's own tests declare its steps over the packages `durations.json` names instead of running `go list ./...`, which lists every directory in the module, including the ones the gate's own steps write. The guard is the exception: it must see every new package, so it walks the tree and reruns whenever a listing changes, such as when the gate writes `bin/`; it takes about a second.
- **Each test package records only its own inputs.** Go keys a cached test result on every file and directory the test opened or examined, and on each variable it read (its test log). A test that reads the whole tree reruns after every edit. The rule: a test package reads the directories of its dependencies (`go list -deps -test`), its own `testdata`, and a short list of declared paths, each with a reason. `internal/closure` holds that list and checks it. Each declared path has a grant: one file, the listing of one directory, a flat pattern of files (`docs/research/ef-migrate/*.ergo` grants no subdirectory), a path with its members (the path and each path directly in it, any access, used when any of them is read: `.git`, a file in a worktree and a directory in a clone), or a subtree, which only a measured walk deeper than one level earns. The check resolves each recorded path as the kernel does, so a path is classified by the object it reaches and not by its spelling: each symbolic link on the path is an input too, and a path the check cannot resolve (a `..` after an absent component, a loop of links) is outside the closure. `TestEveryPackageRecordsOnlyItsClosure` builds the test binary of every test package of the module, runs it with `-test.testlogfile`, and fails on a recorded path inside the checkout that is outside the package's closure, and on a declared path that no recorded input uses. It runs each test binary in a sandbox built as Bazel's linux-sandbox builds one, in an unprivileged user and mount namespace that every child process inherits. Every mount of the file system is read-only, recursively from `/`. The only writable places are scratch directories that the sweep makes fresh and empty for each run: `TMPDIR` (also `GOTMPDIR`), `XDG_CACHE_HOME` (with `GOCACHE` in it), the directory of the test log, and a fresh tmpfs at `/dev/shm`. Each is a mount of its own outside the checkout, so Linux refuses a hard link or a rename of a checkout file into it (EXDEV). A package can declare a cgroup2 mount that its tests write (`scripts/gate` writes its memory budgets), because cgroup2 holds no file that can be a name of a checkout file. The tests hold no capability, run with `no_new_privs`, and cannot make a user namespace, so they cannot remount anything. Before the first package runs, the sweep checks this from inside the sandbox: the mount table, the capability sets, and that a remount, an unmount and a new user namespace fail. It also refuses a checkout that has another name: a bind mount of it, a mount inside it, or a hard link of one of its files outside it, because a read by that name is not classified. Thus the tests cannot change the checkout or anything above it. A process outside the tests can, if they ask it to: a service of the host that they reach by a socket (the systemd user manager, for example). So the observer (`internal/testinputs`) records each path with its identity at the time of the access: every location that the lookup of the path passed, with the device and inode of the object there and the target of each link. Before it looks up a name, the observer watches (inotify) the directory, if a process of this user outside the tests can change it. It also watches every directory of the checkout and the mount table. The last close of an inotify descriptor destroys its watch group, and the kernel waits there for a host-wide grace period (about 15 ms at load 60, whatever the number of watches; on a busy host it held an observer's close past a one-minute run deadline). So the observer does not make that close. Before it adds a watch, it starts a holder: this binary again, with `ERGO_TESTINPUTS_WATCH_HOLDER=1`, which gets a second descriptor of the same group and waits on a pipe from the observer. The observer's close is then not the last one and returns at once; when the observer closes the pipe, or exits, the holder exits, and the group is destroyed in the holder, which nobody waits for. The holder runs no test, has no stdout or stderr, and carries none of the run's environment. A holder that cannot start leaves the close to the observer (`internal/testinputs/identity_linux.go`; `TestWatchGroupEndsInTheHolder`). The check classifies each path by the objects that its accesses reached, and compares them with what the path names after the run. A path whose object changed after the run is outside the closure, unless a declared path names the object of the access exactly. A path that met a change during the run, and a change in the checkout that no access looked up, are outside the closure, and no declared path covers them. A path that has no identity is outside the closure unless a declared path names it exactly. The observer cannot observe its own package's tests (Linux refuses a second seccomp listener), so the sweep gives `internal/testinputs` no identity. Its log is the test log that Go writes in the test process, which records each path as the test spelled it, and the exact declared paths of that package cover what those paths name in the checkout. The sweep classifies each run's log before it removes the run's scratch directories, so a path through a link that a test left in its scratch resolves through that link, and a read of the checkout that way is outside the closure. This holds only while the link stays as it was at the read. A scratch link that a test of `internal/testinputs` removes or changes after the read (one in `t.TempDir`, which the testing package removes; one pointed elsewhere) no longer shows where it led, and no identity does: the read is then classified by what the link names after the run, or by nothing. Only an observer of that package's tests closes both forms. A path that leaves the checkout after it entered it is outside the closure. A test that writes outside its scratch directories fails with EROFS, and the sweep reports a closure violation that names the package: write to `t.TempDir` instead. If any part of the sandbox cannot be made or checked, the sweep refuses to run and says which part; on a system without Linux namespaces (macOS) it reports unsupported and fails. The tests of the sandbox make a namespace, so they run only with `-count=1`. Each run of a test binary has a reaper: a child subreaper (`PR_SET_CHILD_SUBREAPER`) that starts the run's sandbox. While the run goes on, the reaper reaps each adopted process that ends, as tini does, so a test that waits for an orphan's process group to go sees it go; it never waits for the helper, whose exit status is the run's. When the run ends, or passes its deadline, the reaper kills and waits for every process of the run, also one that left its process group or session (`setsid`) (`TestRunCollectsADescendantThatLeftItsSession`, `TestRunReapsAnOrphanThatEndsDuringTheRun`, `TestReapEndedLeavesTheHelperAndRunningChildren`; batch-9 B3). The deadline is `ERGO_CLOSURE_RUN_DEADLINE`, a Go duration (by default ten times the run's recorded cost, at least 30 minutes, and none of its own for a run with an unrecorded test; never later than a minute before the test binary's own `-test.timeout`; a value that is not a positive duration fails each run, with the variable's name). A run of the sweep holds at most 45 s of recorded test time, so it ends well within it. A run that has not ended by then fails and names its package (`TestRunDeadlineStopsAStuckRun`). The sweep skips only the packages in its skip list (`unsweepable` in `internal/closure/closure_test.go`), each with its reason; an empty reason, or a directory that is not a test package of the module, fails the sweep (`TestSweepTargets`). Today the list holds `scripts/gate`, whose tests start processes in new user namespaces (the merge tier's sandbox), which the sweep's sandbox refuses. A package in the list has no checked closure. Each run builds with an empty `GOCACHE`, so a sweep of every package is slow (about 10 minutes); the gate's full tier runs it one package per step, as *The closure sweep* (above, under Tiers) says. Run it by hand after a change that adds a test input: `ERGO_CLOSURE_SWEEP=all go test -count=1 -run TestEveryPackageRecordsOnlyItsClosure ./internal/closure`. `ERGO_CLOSURE_SWEEP` also takes a comma list of package directories, and `ERGO_CLOSURE_KEEP=<dir>` keeps the logs and each package's inputs outside its closure. The checks that read every tracked file (the residue checks) live in `internal/residue`, whose declared input is the whole tree. A test that builds a command of the module passes `-buildvcs=false`, or builds it once per test process outside the tree, as `internal/sketch/lower` does with `cmd/ergo`. Thus an edit of this page reruns neither the checker's tests nor the lowerer's tests.
  Limit: the closure rule covers what the tests and the processes they start do, except a read in `internal/testinputs` through a scratch link that the test removes or changes after the read (above). It does not cover a change that a process outside the sandbox makes while a test runs: another process of this user, a service of the host, or a service that runs as root. The identity and the watches find some of these changes, but not all of them. Examples that are not found: a hard link of a checkout file made from outside; a link in the scratch directories of the tests changed between the observer's lookup and the kernel's (scratch directories are never compared, so the change need not be undone); a file of `internal/testinputs` swapped and restored, since that package has no identity; data or a descriptor that a service reads for the tests and sends through its socket; and a change in a directory that the observer does not watch. The follow-up unit `sandbox-host-services` closes this class: a constructed root, a network namespace, and no IPC to the host unless a package declares it.
- **Other steps** declare their inputs: repository paths, tool fingerprints (below), environment variables and installed directories. A step that walks a directory itself, rather than Git's view of it, such as the Foldkit snapshot check, declares that directory as installed: every entry on disk, files Git ignores included; a link out of it back into the repository contributes only its target. A file's digest carries its content and the permission bits that can change a result: the three executable bits, which a check can read and which decide what a step can run, and owner-read. Steps run as the checkout's owner, so no group or other read or write bit decides their access, and no check asserts one; checkouts made under different umasks share receipts. A symlink among a step's inputs keys its target text and what it reaches, by the link rule of the whole-gate key (below). A link that reaches a directory, or a place outside every keyed root, cannot be keyed: the step runs without its receipt and prints why (`gate: <step>: not cached: <path> reaches <target> outside every keyed root`). These steps replay a recorded pass while those inputs are unchanged. Receipts live under `ERGO_GATE_CACHE`, else `$XDG_CACHE_HOME/ergo-gate` (by default `~/.cache/ergo-gate`), in `ergo-gate-v4/`, never in the tree, and every worktree shares them. A receipt names the size and SHA-256 digest of the step's output, which is in a `.out` file beside it. A replay prints that file only when both match; otherwise the step runs again. Failures are never recorded. A pass the gate cannot record still passes, and the gate says why (`gate: <step>: pass not recorded: <reason>`).
- **Example programs (`examples (default)`).** After `build bin/ergo`, the step runs `go run ./scripts/examples`: it builds each program under `examples/` tagged `default` with that `bin/ergo`, runs its own tests (`ergo test`), and compares each recorded case's stdout, stderr and exit status byte for byte (`examples/README.md`). It writes nothing into the checkout. It runs every module of `modules/` too (MK0; `examples/README.md`, Modules of `modules/`). Its key holds `examples/` and `modules/` as installed directories (the runner walks them on disk, so a file Git ignores there counts; an absent `modules/` is a distinct input), the runner's sources without its tests and `testdata/`, `go.mod`, the `go` and `sh` fingerprints, and `bin/ergo` as a built file (`Inputs.Built`). A built file is a file a step in `Needs` writes: the gate digests it as it digests a repository path, but only when it keys the dependent step, after its `Needs` passed, and never from a memo, so the key holds the compiler that step built. A missing or unreadable built file fails the step (`gate: hash inputs: …`) and never replays; a FIFO there runs it without its receipt. `bin/ergo` has no VCS stamp and embeds the runtime that `ergo build` emits, so its digest stands for the compiler. The runner builds in an emission cache of its own run (Emission cache bound, above), which is not keyed: it is addressed by content. Cost, measured on 2026-11-04 on this host with one program (`tidewalk-replay`) and a warm Go build cache: the runner alone, after a change under `examples/`, takes 0.3 s (0.7 s with an empty emission cache); a replayed receipt costs the digests of `examples/`, the runner's sources and the 11 MB `bin/ergo`.
  - *Per-program verdicts (gate-speed GS1).* When the step runs, the runner replays each program whose own inputs are unchanged, so it does not build and test every program again. It keeps verdicts in `ERGO_EXAMPLES_CACHE`, which the gate sets to `examples/` under its cache directory; `go run ./scripts/examples -cache DIR` does the same by hand. A program's key holds:
    - every file of its folder (name, mode and bytes);
    - the digests of `bin/ergo` (compiler, std snapshot, emitted runtime) and of the runner's own binary;
    - `go env` of the settings that change a build;
    - the whole environment;
    - the runner's `-timeout`, `-budget`, memory and root.

    The runner records only a pass. A program whose key cannot be computed (for example, an unreadable file) runs, with `examples: <program>: not cached: <reason>`. Programs tagged `ts`, `net`, `cc`, `tty` or `gui` are never cached, because they read the Bun cache, the network or a C toolchain. A replay prints the recorded lines, then `ok <program>: cached (inputs …)`. The run ends with `examples: cache <dir>: N programs replayed, M run`. In the merge tier's sandbox the gate cache is empty, so every program runs. Law: `TestCachedVerdictEqualsRerun` (scripts/examples): after edits of a program's files, its cases, the compiler's bytes, the environment, and an unreadable file, a cached run's verdict equals a fresh run's.
  - *Programs at once (gate-speed GS7).* The runner runs `-jobs N` programs at once (GATE-ex, 2026-11-11), by default the `GOMAXPROCS` the environment sets, which the gate sets to its CPU budget (`ERGO_GATE_CPUS`), else half the usable CPUs, so the step uses the budget and never more; each built program keeps its own kernel memory limit (`ERGO_PROGRAM_MEMORY`); `-record` runs its ports at once too. Each program writes to its own buffer, and its lines are printed once it and every program before it ended, so the output, the case count and the failures are those of a one-at-a-time run. A panic in a program's goroutine stops every group of the run and reaches the runner's caller. Before, the step ran one program at a time at about 0.8 CPU: 93–94 s of wall for 77 CPU-s after a one-line edit inside a function body of the lowering at a 4-CPU budget, the fast tier's critical path; after, 64–70 s for 87–88 CPU-s beside the other steps, and the fast tier went from 104–107 s to 77–84 s (2026-11-13, host load 45–60, measured). Law: `TestProgramsRunAtOnceAndPrintInOrder`.
  - *Fast-tier programs (gate-speed GS3).* The fast tier runs only the programs listed in `scripts/examples/fast-tier.txt`; the full tier runs every `default` program. The list holds exactly the `default` programs that some mutant ledger row names as a killer (`examples:PROG`, `example:PROG/case`, `example:PROG test …`): a program no row names kills no mutant the fast tier needs. `internal/residue`'s `TestFastTierExamplesAreLedgerKillers` checks both directions, so a new killer row must add its program to the list, and a listed program must be named by some row.
- **Whole-gate replay (the inner tier).** Before the gate runs a step, it computes one key over every input of every step (package `scripts/gate/replay`; the collectors are in `scripts/gate/wholegate.go`). The key is SHA-256 over:
  - the version `ergo-gate-v4` and the SHA-256 of the running gate executable;
  - the absolute path of the checkout root, which steps see through `TMPDIR` and `ERGO_REPO_ROOT`;
  - the HEAD commit and every index entry (mode, blob, stage, path), so a change between tracked and untracked is a key change, and so is a commit with the same tree (Go's VCS stamping reads HEAD);
  - every path below the root except `.git`, with its class (tracked, untracked or ignored) and its kind (file, symlink, directory or other). A tracked or untracked file gives its content and its keyed permission bits. An ignored file gives its stat tuple: size, modification and change time in nanoseconds, inode and mode. A FIFO, a socket or a device makes the key unreplayable (`<path> is a FIFO: only regular files, directories and symlinks can be keyed`; see "What a key can read" below): what a step reads from it is not in any stat field (a FIFO keeps its inode and times when a step drains its buffer), as a step receipt refuses it too. The gate does not read the content of ignored files (379 MB below `dist/` in the warm source). Go's test cache keys the ignored files a test reads, so the whole-gate key must hold them too. The one exception is the gate's own output: `bin/` and the ignored paths below it, which `build bin/ergo` writes (`gateOutputs` in `scripts/gate/wholegate.go`). Every step that runs `bin/ergo` needs that build and keys the file after it (`Inputs.Built`), so the binary there at the start is no input; a key that held it changed when the build rewrote a stale one, and the run recorded nothing (`TestWholeGateRecordsOverAStaleBuild`). Since no key holds the binary, a whole-gate replay (in the run, and the replay before the scope) runs `build bin/ergo` after it, a go build the build cache serves, so `bin/ergo` matches the tree after every gate; a failed build fails the gate (`rebuildOutputs`). A directory gives its path: a test that lists its parent sees an empty directory. A symlink gives its target text and what it reaches (the link rule below);
  - each variable a step can receive (Environment, below), set or not, with its value;
  - the gate's settings: every `ERGO_GATE_*` variable, `XDG_CACHE_HOME` and the cache directory;
  - the run's tier: `fast` for a plain gate, `full` for `--full` and `--no-cache` (every step, every test of every package). A record therefore names the tier that made it, and replays only for a run of that tier: the replay before the steps, the run's own record and its package keys key the tier the same way (`collectTier`, `replay.WithTier`). The merge tier's uncached run is `merge` and writes no record, so `--merge` compares only with a `full` record. The fast tier runs fewer tests, so its record never stands for a full run (`TestWholeGateRecordNamesItsTier`). A run prints its tier after the identity line (`gate: tier: full`), and a replay prints it too;
  - the host fingerprint: GOOS and GOARCH; the kernel release and version; the CPU count; the CPU budget, which sets the shards, the steps at once, `GOMAXPROCS` and the host packages' `-parallel`, so a verdict can differ under another budget (a test with a timing bound, a race that shows only at some parallelism); physical memory; the memory mechanism, the budgets and the bound of `ergo-gates.slice`; the cgroup v2 facts (the file system of `/sys/fs/cgroup`, and `cgroup.controllers` and `cgroup.subtree_control` of the user manager's cgroup); the file system type of the checkout, the temporary directory, `GOTMPDIR`, `GOCACHE`, the gate cache and its output spools; the user id; `RLIMIT_NOFILE`; and the tool fingerprint (below) of every declared host program (`hostPrograms`). A declared host program is each program that a step or its shell script starts, and each program that the code and tests of `scripts/gate` start. `TestHostProgramsDeclared` fails when a step or a test starts a program that is not declared. A program that is not on `PATH` is a distinct value. On darwin the gate reads the kernel and memory facts from `sysctl` and the file system types from `statfs`; darwin has no cgroups. A fact that the gate cannot read makes the key unreplayable: it never matches, so the gate neither replays nor records. The gate reads physical memory again at every collection, and only a positive size it read is a fact; an unknown size gives `the physical memory cannot be read`, and a size that changes during a run keeps the run from recording.

  When every step passes, the gate stores the output of each step and then writes a whole-gate record under the key. A later gate at the same key starts no step: it prints the record. The gate replays in its scope once its limiter is open and before it declares its steps (gate-speed GS28): a replay declares none, and on a miss the facts the replay keyed are the run's start key, so they are collected once. Before, it replayed before it opened a scope, and a miss collected the facts twice, the first time at the caller's CPU share: on a std edit at 4 CPUs the gate clock started 6.8 to 8.2 s after the command, 3.1 to 3.5 s of it that first collection; now 3.4 to 3.5 s, the in-scope collection 0.8 s and the fast tier's test selections, which now run at once, 0.8 s (1.7 s one after another). Entering the scope adds 0.1 to 0.25 s to a replay. After the identity line, a replay prints `== <step>: ok, replayed (passed in <s>s at <time>)` and the recorded output for each step, then `gate: replayed <n> steps (key <12 hex>, recorded <time> at head <sha>)`. The durations are the recorded ones. Thus the host step replays only inside a whole-gate replay. Measured on 2026-11-04 on this 16-CPU host: a no-op gate replayed its 15 steps in 0.53 to 0.59 s wall (three runs, 1-minute load 20.5). Before, a no-op gate took about 116 s, almost all of it the host step (load 32 to 50).
  - *Changes during a run.* At the end of a run the gate computes the whole key again. It records only when the end key equals the start key, and when no stat-keyed path changed within 2 s before either computation (as Go's test cache does with `modTimeCutoff`). Otherwise it prints `gate: no whole-gate record: <reason>`. So a step that writes into the checkout stops the record. In a new worktree the first gate writes `bin/ergo`, and the tests of `internal/sketch/lower` ran `ergo run` in the checkout root, which built `dist/main`; the second gate ran those tests again, because their inputs changed. The third gate recorded (measured 2026-11-04). Since batch 12 (T1), `ergo run` builds into a temporary directory and writes no `dist/` (inferred: the second gate then records). A change that is made and then reverted inside one run (ABA) is not found: the merge tier is the guard.
  - *Failures.* The gate never records a failure. A run that does not replay and fails a step withdraws the record at its key (`gate: withdrew whole-gate record <key>`). A concurrent pass at the same key can record again after a withdrawal; the merge tier runs every step again before a change reaches main.
  - *Store.* `<cache>/ergo-gate-v4/objects/<sha[:2]>/<sha>` holds the printed output of a step, named by its SHA-256. The gate writes an object once: it links a temporary file into place, and it keeps an object of the same name that verifies (it replaces one that does not). `<cache>/ergo-gate-v4/whole/<key[:2]>/<key>.json` holds the record: for each step its object, size, outcome (ran, or cached from a step receipt) and duration, and the head, tree, clean flag and time of the run. The gate writes the record last, by one atomic rename. Any process can delete or damage an object or a record at any time (a manual clean, a withdrawal, a future eviction). A replay opens the record and each object. It verifies the size and digest of each object through the descriptor that it reads, and it copies the object into a private file. Then it prints from those private files and never opens an object by name again. A missing or damaged object makes the gate run the steps. Records are per worktree, because the key holds the root path; objects are shared. Nothing evicts records yet: each passing gate with a new key adds about 10 KB.
  - *The link rule.* A symlink in the checkout keys its target text and what it reaches. A target in the checkout is covered by its own entry, and a target in a fingerprinted installation (`GOROOT`, the file of a tool) by the fingerprint. A link that reaches any other place, that dangles outside, that loops, or that passes through such a place makes the key unreplayable. The gate then does not replay or record, and prints `gate: no whole-gate replay: <path> reaches <target> outside every keyed root`.
  - *What a key can read.* One rule (`replay.KindOf`) decides it for every file that any key reads, wherever the walk reaches it: an entry of the checkout, the target of a link (relative or absolute, in the checkout or in a fingerprinted installation) and every path below a directory it reaches, a path below a fingerprinted installation, and a file a step receipt hashes. Only a regular file, a directory and a symlink can be keyed, and a symlink only when what it leads to can be keyed by the same rule. A FIFO, a socket, a device or a file type the walk does not know makes the whole gate unreplayable: the gate does not replay, does not record, and refuses a record that already sits at the key. The reason names the path and the kind, for example `gate: no whole-gate replay: stream reaches /…/go/stream, a FIFO: only regular files, directories and symlinks can be keyed`. A fingerprint that fails, for such a file in the installation or for any other reason, makes the key unreplayable in the same way (`program go cannot be fingerprinted: <path> is a FIFO: …`).
  - *Not keyed.* Go's build cache and module cache: the build cache is addressed by content, with the toolchain in each action id, and `go.sum` verifies the module cache, so Go trusts both. User configuration outside the checkout, such as `~/.gitconfig` (as for Go's test cache; see Tool fingerprints). A test that depends on the time replays until the key changes; the merge tier runs it again.
- **Merge tier (`--merge`).** Run it before a change reaches main. If the key of the checkout has no full-tier record, the gate first runs the full tier (the inner tier), which records on a pass; a fast record does not count; if the inner tier fails, the gate exits 1. Then the gate runs every step uncached. It does not use step receipts or whole-gate records, and it drops the hermetic exception, so every step, the hermetic one included, runs with the uncached default (`-count=1` in `GOFLAGS`, above) and no `go test` it starts replays a result. One exception (GATE2 GT5): a closure sweep step replays the pass of an earlier merge run while its package key is unchanged (`keySweepSteps` in `scripts/gate/sweepkey.go`; the key of *The closure sweep*, above, with the merge tier in it, so neither a full-tier pass nor a fast one stands for it), and records its own pass; a replayed sweep prints `ok, cached`. The sweeps took 23,267 of the 28,064 step CPU-s of the batch-18 merge tier (measured, gate-merge-8.log). `--merge --no-cache`, run on a release head, is the reference: its uncached run replays no sweep, and the merge tier is otherwise the same (before GT5 the gate refused the pair). `TestMergeTierReplaysUnchangedSweeps` counts real runs of fixture steps: a second merge replays the sweep and runs the other step, an edit outside the sweep's closure replays it, and an edit inside reruns it, and `--merge --no-cache` sweeps again at the same key. The run is in a sandbox (below), so it starts with an empty build cache and test cache, a module cache that holds only archives the gate built from module contents `go.sum` verifies, and no Go cache from before the run in any tree it reads (*Input contract*, below). Then the gate prints one line for each step, `merge: <step>: inner <pass|none>, uncached <pass|FAILED|not run>`, and `merge: verdicts equal (<n> steps)` or `merge: FAILED: verdicts differ: <steps>`. A difference exits 1 and withdraws the record at once, before the gate collects the end key, so a change or a collection error at the end cannot keep a discredited record. A tracked or untracked file, HEAD, the index, a variable, a setting or a host fact that changed during the uncached run also exits 1. The inner tier's steps write ignored files into the checkout (`bin/ergo`); the uncached run writes into its export (below), not the caller's checkout. A change of ignored files and directories is named (`merge: the run wrote into the checkout: …`) and does not fail the merge tier. The merge tier writes no whole-gate record. A flaky step shows as a difference. The merge tier is the clean-against-incremental check (Fai's F6): it finds an input that no key holds.
  - *Policy.* Only the merge tier gives a merge verdict. The inner tier (a plain gate, and the merge tier's first run) is hygiene: it can replay a stale pass from a cache on the host that a tool chose itself (Go test cache, above), and its whole-gate record can carry one. The merge tier's verdict is its uncached run, and that run is in a sandbox with no persistent state.
  - *Sandbox.* The uncached run is in a bubblewrap (`bwrap`) sandbox the gate makes without privilege (`scripts/gate/sandbox.go`, `scripts/gate/sandbox_linux.go`). The gate starts a holder process in a new user namespace that maps only its own user and a new pid namespace (`startSandbox`), and bwrap joins them (`--userns`, `--pidns`, `--unshare-pid`, `--die-with-parent`). One function, `sandboxArgv`, builds bwrap's argv from a plan (`sandboxPlan`); nothing else decides a mount. The root is a tmpfs. Before the sandbox starts, the gate exports the head commit on the host into the checkout's new empty directory (`exportCommit`, `scripts/gate/inputs.go`): `git init`, `git fetch` of the head by its hash from the repository, and `git checkout --detach`, with no user or system git configuration. The object store is not bound into the sandbox. So the run checks a fresh export of the commit, never the caller's working tree; a checkout with changes gets no verdict (`the checkout has changes; ...`). Every step of the run enters the sandbox through `nsenter` (`sandboxWrap`, applied in `execute` in `scripts/gate/main.go`), so it still runs as the gate's child, under the gate's memory budget, with its output in a spool on the host. Closing the holder ends the pid namespace, and the kernel stops every process left in it.
  - *Writable paths.* Each path a step may write by name is bound read-write from its own new empty directory (`sandboxScratch`): `/tmp`, `/var/tmp`, `HOME`, `XDG_CACHE_HOME`, `GOCACHE`, `TMPDIR`, `GOTMPDIR`, the gate cache, the checkout and the module cache (`go env GOMODCACHE`). Those directories are under the run's own directory, `<gate cache>/sandbox/<random name>`, which the gate creates (it fails if the name exists) and removes when the run ends, so a cache a step fills (Go's test cache wherever a tool puts it, under HOME, XDG_CACHE_HOME or GOCACHE) lives only as long as the run and two runs never share one. They are on disk, not tmpfs, measured: on tmpfs the gate's own tests refused their output spools (Step output, above), a directory-order test of `internal/sketch/build` failed, and every byte a step wrote, a cold build cache of gigabytes included, would count against the step's memory budget. No host path outside the run's directory is writable.
  - *Read-only paths*, the minimal set, each found necessary by running `--merge` without it (2026-11-05; `sandboxReadOnly`): `/usr`, the programs the steps run (`sh`, git, the C compiler, `ps`) and their libraries (without it: `bwrap: execvp /bin/sh: No such file or directory`), with the host's `/bin`, `/lib`, `/lib64` and `/sbin` links into it recreated; and `GOROOT`, the toolchain `go.mod` selects (without it: `go: downloading go1.27.0 ...`, which fails). Here `GOROOT` is in the host's module cache; only `GOROOT` is bound, never the cache around it. The steps in the sandbox get `GOROOT/bin` first on `PATH`, `GOTOOLCHAIN=local`, `GOPROXY=off` and the run's own `GOMODCACHE` (`sandboxEnvironment`). `/etc` is not bound: `--merge` passed without it, so the host's git, resolver and user configuration are not inputs of the verdict. bwrap adds `/proc` and a minimal `/dev`. `checkSandboxPlan` refuses a plan whose read-only set exposes `HOME`, the host's module cache or a parent of either, `/tmp`, `/var/tmp`, the caller's `GOCACHE`, `XDG_CACHE_HOME`, `TMPDIR` or `GOTMPDIR`, `$HOME/.cache`, `$HOME/Library/Caches`, the directory of the runs, or the checkout. `TestSandboxArgvProperty` checks these rules over generated plans; `TestSandboxPlanOfThisHost` checks the plan of this host and starts it.
  - *Input contract.* The guarantee: no byte that a process of this user could write before the run is visible in the run, except the commit and module file contents verified against the commit's go.sum. The run reads three inputs from before it. (1) The commit, exported as above. (2) The modules, built by construction, as a Nix fixed-output derivation is: for each line of each `go.sum` tracked at the head, the gate reads the host's `<GOMODCACHE>/cache/download/<module>/@v/<version>.zip` or `.mod`, checks that the line's `h1:` hash, which covers file names and contents only, matches, and writes into the run's empty module cache only those verified contents (`seedModules`). A `.mod` file is written as read, since `h1` covers all of its bytes. A `.zip` is written as a new archive built from the verified members alone (`moduleZip`): members sorted by name, stored without compression, each with the date 1980-01-01, no flags, attributes, extra fields or comment, and no archive comment and nothing after the central directory. So the bytes the run gets are a function of what `h1` covers, and no byte of the host's container reaches it: not a ZIP comment, a header field, an extra field or data around the archive. No other host file is read: not `.info`, `.ziphash`, `.lock` or `list`. Go needs none of them offline to build from a module cache that `go.sum` pins (the provenance analyzer step builds `tools/provenance`, which requires golang.org/x/tools, x/mod and x/sync, from the constructed archives alone), and it writes its own `.ziphash` into the run's cache. `TestModuleZipByConstructionProperty` generates module trees and, for each, host archives with equal `h1` hashes that vary member order, method, times, modes, extra fields, member and archive comments, and data before and after the archive, each beside host `.info`, `.ziphash`, `.lock` and `list` files: every variant seeds the same bytes, which hash to the `go.sum` line, have the fixed shape and hold no host byte, and nothing else is written. `TestSandboxModuleZipIsConstructed` is round 7's verifier probe as a regression: a host zip whose comment holds a marker seeds, and inside the sandbox the run's zip exists without the marker. A file the host does not have is not copied, and the step that needs it fails (`GOPROXY=off`); a file whose hash differs fails closed (`the module inputs: <file> does not match go.sum`); a `go.mod` with a `require` and no `go.sum` beside it fails closed (`requires modules but has no go.sum`); a `go.work` anywhere in the commit fails closed (`the merge tier runs with GOWORK=off and admits no workspace`). Go then extracts each module from the constructed zip, and checks it against `go.sum` again, as `go mod download` does. In the sandbox every step runs with `GOWORK=off`, `GOPROXY=off`, `GOTOOLCHAIN=local` and `-mod=readonly` last in `GOFLAGS`, after the caller's flags and `-count=1`, so no flag in `GOFLAGS` lets a step change a `go.mod` or `go.sum` (`TestSandboxEnvironmentPinsModules`). (3) The declared read-only trees, `/usr` and `GOROOT`. Each is admitted by its resolved identity (`admitInputs`, `scripts/gate/inputs.go`): the declared path with every symbolic link in it and its parents followed, component by component, as the kernel follows them (`resolvePath`, checked against `filepath.EvalSymlinks` by `TestResolvePathMatchesKernel`). The forbidden paths, HOME, the checkout and the runs' directory are compared with both the declared and the resolved path, each by its own spelling and resolved. The check walks the resolved tree, and bwrap binds the resolved tree at the declared path (`--ro-bind <resolved> <declared>`), so the tree checked is the tree bound whatever its spelling. `sandboxArgv` reads only that admitted set. At the start of every run, `checkInputs` (`scripts/gate/inputs_linux.go`) reads each resolved tree entry by entry and finds every path this user could have written: one the user owns with its owner write bit, one of a group of the user with the group write bit, one any user may write, and one `access(2)` says is writable (ACLs). It also finds a Go build or test cache (a `trim.txt`, a `testexpire.txt`, cmd/go's `README`, or a 64-hex-digit `-a` or `-d` entry in a two-hex-digit directory), and a directory this user cannot read. The walk does not follow a symbolic link. Each link's target is resolved as the sandbox resolves it: through the trees as bound, the masks and the sandbox's top-level links. A target inside a tree is checked there; a target in a scratch path is the run's own; a target in `/proc` or `/dev` is the kernel's; a target that holds one of these shows only them. Any other target, absolute or relative, is masked with an empty read-only directory, so the link shows nothing, whatever a later change binds there. A finding in `/usr` is masked: a directory is bound as an empty read-only tmpfs, a file as `/dev/null`. A finding that is the root of a tree, that is in, at or above `GOROOT`, or that is at or above a program the steps run (each `hostPrograms` name, resolved) is not masked: the merge tier fails closed with `gate: --merge needs its sandbox and gives no verdict without it: the input contract: <path> (<reason>) ...`. On this host (2026-11-05) the check masks 11 paths, every one writable by this user: `/usr/bin/{bsondump,mongodump,mongoexport,mongofiles,mongoimport,mongorestore,mongostat,mongotop}`, `/usr/local/bin/{docker-credential-porter,porter}` and `/usr/share/doc/mongodb-database-tools`; it finds nothing in `GOROOT`. It also masks 177 targets of links in `/usr` that leave both trees: 176 under `/etc` and `/var/lib/ghostscript/CMap` (`/usr/share/X11/rgb.txt` to `/etc/X11/rgb.txt`, for example). The other outward links in `/usr` reach `/dev/null`, `/bin` and `/sbin` (the sandbox's links into `/usr`), or HOME, a scratch path. Inside a user namespace (the gate's own tests during the merge tier's run) an unmapped group reads as the overflow group, which is also one of the process's groups, so the check masks more there: measured, `/usr/local/share/fonts` (root:staff, mode 2775) as well. `TestInputContractProperty` checks the check and the mask plan against a reference over generated trees; `TestInputAdmissionResolvesLinks` does so with each tree declared through links (the tree, a parent, a chain, a relative link) and links inside to and out of the trees; `TestSandboxAdmitsSymlinkRoots` and `TestSandboxArgvBindsAdmittedRoots` start the sandbox over a tree declared as a link; `TestSandboxMasksContaminatedInputs` makes such a tree, starts the sandbox and reads the masked paths inside; `TestSeedModulesVerifiesGoSum` and `TestSeedModulesRefusesUnverifiedRequirements` check the seeding; `TestMergeTierInputContractRegression` is round 6's finding as a regression: a tool keeps a Go build cache in `$GOMODCACHE/cache/go-build` and restores it into a fresh `HOME` for its child; the cache is primed on the host until it replays, the bad input is committed, and the second merge tier must fail on the test's own failure.
  - *Fail closed.* Where the sandbox cannot run, `--merge` exits 2 with one line, `gate: --merge needs its sandbox and gives no verdict without it: <reason>`, before it runs anything: off Linux (`scripts/gate/sandbox_other.go`), without `bwrap`, `nsenter` or `cat` on `PATH`, without user namespaces, with a mount bwrap cannot make, with a dirty checkout, with an input the input contract refuses, with a module that does not match `go.sum`, or with a plan `checkSandboxPlan` refuses (`TestMergeTierFailsClosed`, and `TestSandboxArgvProperty` for the plans). There is no unsandboxed merge verdict and no switch for one. The plain gate does not need the sandbox.
  - *Threat model.* The sandbox protects the merge verdict against state that outlives a run: a stale pass in a cache a step or a tool it starts chooses, in a writable path (each starts empty) or in a declared read-only tree (the input contract masks it or fails closed), and the caller's uncommitted files. `TestMergeTierSandboxRegression` runs the merge tier twice with the checked input changed in between, once for each way a child picks its cache (the inherited environment; a fresh `Cmd.Env` with and without `GOCACHE`; a tool-chosen `HOME`, `XDG_CACHE_HOME`, or `GOENV` with its own `GOCACHE` under a host path; and round 5's verifier probes verbatim), and the second run must fail on the new input. `TestEnclosedRunWrapsEveryStep` requires every step of the run to enter the sandbox, and `TestMergeTierSandboxConcurrent` runs two merge tiers at once over one cache-sensitive check and each gives its own verdict. Residuals: a step can still change an input during the run and change it back (ABA within one run); a module file's contents come from the host and are admitted on the strength of `go.sum`'s `h1` hash (SHA-256 over the names and contents), so they are what the commit pins unless SHA-256 is broken, and what `h1` does not cover (order, modes, times, the container) the gate sets itself; the network is not cut, but with no `/etc` there is no resolver configuration, so a name lookup fails, and `GOPROXY=off` stops the go command's downloads, so only a step that fetches on purpose (by address, or with its own `GOPROXY`) reaches the network; a file in `/usr` that root owns and a privileged process wrote is admitted, because no process of this user could write it; a path this user owns without a write bit (all of `GOROOT` here, which Go extracts read-only) is admitted, so a process of this user that adds the bit, writes and removes the bit again before the run is not found (no step of the run can write it: the tree is bound read-only); the host's `GOENV` file (under `HOME`) is not visible, so a setting kept only there (`GOPROXY`, `GOPRIVATE`) does not apply in the uncached run, while one passed as a step variable does; the sandbox has no network namespace, so a step can still reach a server on the host's loopback or an abstract Unix socket, which could hold state; and a gate that is killed leaves its run's directory under `<gate cache>/sandbox/`, which no later run reuses (each name is new) and the gate prints when it cannot remove it (`gate: the merge sandbox's run directory ... was not removed`).
  - *Cost.* Measured 2026-11-05 on this 16-CPU host, interleaved, each side with its own caches, against f830a312 (the uncached run on the host); the 1-minute load was 13 to 45 throughout, so there is no speed verdict (gate-testcache-gap cost-r6.log). With the inner tier replayed, the uncached run took 333.7 s (load 22 at start, 13 at end) and 335.1 s after, against 277.4 s (load 16 to 22) and 265.4 s (load 13 to 31) before; the whole `--merge` took 347.9 s after against 266.9 s before. The steps start 23 to 28 s into the run (the export, and an empty build cache) against 2 to 4 s. With an empty build cache the steps compile everything again: the host step used 1,080 to 1,100 s of CPU against 241 to 246 s, and `go test (other packages)` 1,275 to 1,286 s against 965 to 995 s, with a peak of 6.4 to 7.1G against 2.3 to 2.4G, close to the 8G step budget. The input contract (measured 2026-11-05, against cd112257, which bound the host's module cache and object store; load 15 to 80, so again no speed verdict; gate-testcache-gap cost-r7.log and check-cost-r7.log): `checkInputs` over `/usr` and `GOROOT` took 0.69 to 0.78 s (five runs, load 17), the export 1.42 to 1.49 s and the module seeding (8 files) 0.11 to 0.22 s (three runs each). The uncached run took 374.0 s (load 16 to 46) and 306.4 s (load 18 to 37) after, against 330.1 s, 305.9 s and 302.8 s before (load 15 to 64); `go test (other packages)` peaked at 6.6 to 6.7G after against 6.7 to 7.3G before.
- **Environment.** Each step gets a stable `TMPDIR` under the caller's temp directory, unique to its checkout and step. After the step's process group or cgroup is stopped and its output is drained, the gate removes that directory; a cleanup error fails the step. The stable path lets Go's test cache reuse tests that read `TMPDIR`, while files created by a killed process do not survive the step. Every step, and every tool query of a fingerprint, receives only the variables `internal/testinputs/testenv` names, as Bazel's strict action environment and Nix's pure builds pass only declared variables: `PATH`, `HOME`, `TMPDIR`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`, the go command's settings, the Go runtime's variables, `GIT_OPTIONAL_LOCKS` (always 0, whatever the caller sets), `ERGO_GO` (`system` unless the caller sets it, so no step downloads Go; `TestStepsBuildWithTheSystemGo`) and `ERGO_TOOL_VERSIONS`. A step's own settings come over them (`CGO_ENABLED=0` for the hermetic step). So the whole-gate key, which holds each of these variables set or not, covers all that a step can read from its environment. A step that declares an input variable outside the list fails: no step can receive it. The gate log prints the list once (`gate: steps receive only …`). Go test steps receive `ERGO_TOOL_VERSIONS`, a digest of the git and `sh` fingerprints and the values of every one of those variables, set or not. The gate derives it; it never passes the caller's `ERGO_TOOL_VERSIONS` to a step or a tool query. So every variable a step receives is a key input or derived from key inputs (`TestReceivedVariablesAreKeyed`). Observation records a read of it for every test that runs a program, so a Go test result cached under other tools or settings is not reused, and no other variable can reach a cached test. The `go` tool fingerprint of a cached step carries the same Go runtime variables: `GODEBUG=inittrace=1`, for example, changes what a Go program prints without changing its bytes. The runner sets umask 022 and `GIT_OPTIONAL_LOCKS=0`, and `GOGC=400` unless the caller sets `GOGC`.
- **Tool fingerprints.** A tool's fingerprint keys what the tool prints about itself (`--version`; for `go`, `go env` with the toolchain settings) and every byte the gate can locate that running the tool executes or loads, each under its absolute path:
  - `go`: the file PATH resolves to and the whole `GOROOT` that `go env` reports. That file may be a launcher that selects another toolchain (`GOTOOLCHAIN`); the reported `GOROOT` is the selected toolchain's, so its `bin/go`, compiler, linker and standard library are keyed.
  - `git`: the binary and its exec path (`git --exec-path`), whose helpers git runs.
  - Any other file that is not a script: the file.
  - A script (`#!`): nothing. A script can exec any file, and the gate cannot locate what it runs, so its fingerprint never matches a recorded pass, and every step that keys that tool runs. (Until 2026-10-26 a script inside an npm package, such as the `tsc` launcher, keyed its package closure; that rule went with the Node toolchain.)

  The bytes are keyed because another build that prints the same version must not replay a pass. The path is keyed too, never in place of the bytes, because the same build under another prefix may load its helpers from another place. Every installation is hashed again on every run: 0.6–1.0 s for all five tools of the time (go, node, bun, tsc and git) together and 1.6–2.6 s one tool at a time, at a 1-minute load of about 39 on this host's 16 CPUs (measured 2026-10-11, before the Node toolchain was removed; the three tools now keyed take at most that). The gate starts every fingerprint its steps name as soon as it starts, so this overlaps loading the files and the first steps. No digest is remembered between runs, so no file timestamp, which a coarse clock can leave unchanged across a same-size rewrite, decides whether bytes are hashed. On darwin the kernel kills a signed binary that was rewritten in place and run, and keeps killing that file after its bytes are restored, until a new file replaces it (measured on darwin/arm64, 2026-10-30): such a tool answers nothing, so its fingerprint differs from the one recorded with the same bytes, and every step that keys it runs. Not keyed:
  - the system shared libraries the dynamic loader maps (libc and the like), which belong to the operating system rather than the tool;
  - git subcommands found on PATH outside the exec path, which git looks up only when a command is not built in;
  - a wrapper named in `GOFLAGS` by `-exec` (which `go run` runs the program under) or `-toolexec` (which wraps every compile and link): the caller's `GOFLAGS` string is keyed, the wrapper's bytes are not, and the caller's `GOFLAGS` is empty here (the gate adds `-count=1` to it for its steps, which names no wrapper);
  - git configuration (`~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`, `/etc/gitconfig`), which can name programs git runs (`core.hooksPath`, `core.fsmonitor`, filters, `!` aliases) and change what tests see (`init.defaultBranch`): it is user state outside every tool installation, and isolating the tests' git from it (`GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM`) belongs to the tests that run git.

  An installation the gate cannot read, or a tool that does not answer the gate's question within 10 s, never matches a recorded pass. The gate never waits on a tool longer than that deadline plus 1 s: at the deadline the tool is killed, and a process it started that still holds its output open is cut off 1 s later. That process is not killed and may outlive the question. Questions run in the gate's own process group, so terminal signals (Ctrl-C, a hangup, `nohup`) reach them exactly as they reach the gate.
- **Log identity.** The second line is `gate: head <sha> tree <tree> clean=<bool>`, so a log names the commit it checked. `clean=false` means staged, unstaged or untracked (non-ignored) changes, submodules included even when a submodule's `ignore` setting hides them from `git status`; the gate still runs, and the line says the log does not certify that commit alone. Each step line ends with when the step started, so a log shows its critical path.
- **Process smokes** that drive the CLI run as Go tests in `cmd/ergo` (`*_smoke_test.go` and `*_process_test.go`). Each one works in a private workspace whose files are copied in the test process; observation makes what the CLI reads there inputs of Go's test cache too.
- **Test addresses.** A test learns a server's address from the server: the server binds port 0 and reports the address it bound (an `onListen` callback, or the program's `listening http://…` line), as `net/http/httptest` does. A test that must name an address before the server starts, or that binds it again after the server released it to prove the release, must keep the kernel from assigning the port to any other socket in between. `internal/testport` reserves the port for the whole test (off Linux, `testport.Reserve` skips the test). No test closes a probe listener and hands its port on: another test can take the port in between (#112).
- **Sketch test rules** (AGENTS.md, Tests; `internal/residue`). Each has an allow list in `internal/residue/testdata` whose rows name the unit that removes them, and a row that admits nothing fails.
  - `TestTestsCompareNoWallClock`: a test in `internal/sketch` compares no measured duration with any nonzero constant; elsewhere the floor is 10 s (`wallclock-allow.txt`).
  - `TestSplitsPinNoDomain`: a split in `internal/sketch` sets no `Count`/`Digest` (`count`/`digest`) pin, in its literal or by an assignment (`split-pin-allow.txt`).
  - `TestSketchBuildsSayWhy`: a declaration in an `internal/sketch` test file that calls `buildAll` or `ergoCLI`, or runs the `go` command, has a "builds Go because" line in its own doc comment (`builds-go-allow.txt`).
- **Compiler data rule** (compile-speed CS11; `internal/residue/compiler_maps_test.go`). `TestCompilerHasNoPointerKeyedMaps`: no `Map` in the self-hosted `compiler/` module is keyed by a node, a type or a symbol. A key is a builtin or std type, or a type `compiler/` defines over string; never a borrow, a record, union, operation type or machine `compiler/` declares, or a defined integer it declares (a dense id). A per-id result is a dense side table. The rule passes while `compiler/` does not exist; `TestCompilerMapKeyRule` runs it on a small module.

## Package split

`ergo build`, `ergo run` and `ergo test` lower a program to one Go package per Ergo package (`pkg/<path>`), one per std package it reaches (`std/<path>`), and one shared package (`shared`) for what packages that do not import each other both use (`internal/sketch/lower/pkgsplit.go`, `lower.LowerSplit`). The go command then compiles independent packages at the same time, and after an edit it compiles only the edited package and its importers. The split is a pass over the one-package lowering:

- Each top-level declaration starts in the package of its Ergo source file; a std declaration starts in its std package, which the lowering's naming table names. A generated declaration starts with the program declarations it names. A declaration that a lower package uses moves down to a package that lower package sees; a declaration that two sibling packages use moves to the shared package.
- In a test build the harness is main and the root Ergo package is its own Go package below it (`ergoroot`; test-speed FT6): the tests, the law runs, the runner and its helpers, and the generators, literals and assertion renderers start in main, and the root's Go init, which registers the source tables, starts in `ergoroot`. A body edit of the program then changes the text of its own Go package and not main's; with the dev profile's export data, which holds no bodies, the direct path compiles that package and reuses the harness's archive. An edit that moves a later declaration to another line changes the export data's positions, and compiles the harness too; so does a test edit, since the root's source tables hold the tests' calls.
- A std package holds only std declarations: a declaration of the program, or a generated one, that a std package uses goes to the shared package. A std package sees the std packages it imports and the prelude; a package of the program sees every std package.
- Law InitsKeepTheirOrder: `func main` and every `func init` stay in the root, in the reference's order. Go runs a package's inits after its imports' inits, so an init moved below the root would run earlier than in the reference.
- Only a name used from another Go package gets an exported spelling (`X` + name). Other names keep their spelling, so the runtime's type names and `%+v` output stay the same.
- A program of one Ergo package still splits out the std packages it uses.
- `ERGO_LOWER=single` selects the reference: the one-package module. The emission cache keys the two modes apart.
- The IR path splits too (`lower.LowerIRSplit`, `pkgsplit_ir.go`). A function with an IR body counts the names its body spells as its references, and each Go package gets an IR file of its own bodies, `ergoir.json` in its folder; the root always has one. The direct path and go build pass each package's compile its own file (`-ergoir`), and the direct path keys each compile on its file's content, so an edit of one package's IR bodies compiles that package again. The patched compile resolves an IR body's names in its own package only, so a name that the split places in another package is declared again in the body's package under the name the IR spells: a type as an alias, a function as a function that calls the other package's (Go inlines it). The split reports these in `IRForeign`. `TestIRFilePerPackage` checks the files on examples, and `TestDirectBuildStartsNoGoCommand` builds an IR program of two packages with the patched compile.
- An importer's compile on the direct path is keyed on the digest of each import's export data (`__.PKGDEF`), not on the import's archive. A body edit that leaves a package's export data the same compiles that package and links; its importers are reused. Go puts the body of a function its inliner may copy into the export data, so an edit of such a body compiles the importers too, as it must: their objects hold a copy of the old body.

- Declaration shards (test-speed FT9, `internal/sketch/lower/pkgshard.go`, `lower.LowerShards` and `lower.LowerIRShards`): in every test build of a program after its first, each package of the program whose declarations hold at least 64 KiB is cut further into Go packages below it, `shard/<root|pkg dir>/s<hash>`, so Go's cache per package is a cache per shard and a body edit compiles one shard. A shard is a run of strongly connected components of the package's declaration groups, in an order with every callee first, so shards import only shards before them (law ShardsAreAcyclic). A shard ends after a component whose first name hashes to 0 mod 4 once its cost is 24 KiB (content-defined chunking); the cost is the bytes of its declarations and of every generic declaration outside it that it instantiates, transitively, since Go compiles an instantiation again in each package that makes it. and is named by the hash of its first name, so an insert moves only the cuts near it (law ShardsLocalUnderInsert). The last run stays in the package. The root keeps `main`, every init, every embedded asset (wherever its `//go:embed` stands among the declaration's comments) and every group that reaches one, since nothing imports the root. Names that cross a shard get the split's exported spelling, and each shard has its own IR file. The first test build of a program (no mark of it in the cache's `warm` folder) does not shard: shards make a cold compile dearer, each paying its imports and instantiations again; it writes the mark, which holds that split build's emission key, so every later test build of the program with other inputs, the edit loop, shards, and an unchanged one keeps the split and reuses its module: the module of unchanged inputs never depends on how many builds came before (NG-Q8; `TestShardsAfterTheFirstBuild`). `ERGO_LOWER=split` selects the split without shards, `ERGO_LOWER=shards` shards in every build; `ergo build` and `ergo run` do not shard by default. `TestBodyEditChangesOneShard` holds a seeded body edit of the `examples/deps` test programs to one changed Go package; `TestShardsTypecheck` and `TestShardsLocalUnderInsert` hold the two laws in process. The receipt is in [compile-speed.md](receipts/compile-speed.md#declaration-shards).
- Shared instances (MONO-HOOKS-MIN, which replaced MONO-SHARED on 2026-11-19): Go compiles a generic instance in every package that names it, so each shard that names `Graph[string]` compiled `Graph[string]`'s methods and every generic body they reach again. A call of a known instance goes to MONO1's monomorphic copy instead (`internal/sketch/lower/mono.go`), in a run build and in a test build alike, on the text path and the IR path: the copy is a plain function, which Go compiles once, in the package that declares it, and an importer that inlines it reads its body as any other function's. Go's compiler is not changed for it: MONO-SHARED's instance package (`inst`), its IR `shared` lists and the patched compile's `noder/ergoshared.go` with its 8 hooks in Go's own files are gone. What Go still compiles per package is a generic type's own Go methods, for each instance a package names. `genericLowering=stencil` is the reference; `TestGenericLoweringsAgree` and `TestIRInstancesMatchSource` hold the copies to it; the receipt is in [compile-speed.md](receipts/compile-speed.md#shared-instances).

`TestSplitLoweringAgrees` (seeded; `ERGO_SPLIT_SEED` replays one seed) checks that the split, the shards and the reference print the same output on generated multi-package programs. `TestBodyEditCompilesOnePackage` and `TestColdCompilesInParallel` count the go command's compile actions. The receipts are in [compile-speed.md](receipts/compile-speed.md#package-split).

## Embedded std snapshot

The `ergo` binary carries the checked prelude and std as a snapshot (`internal/sketchfront/stdsnap/std.snap`, `snapshot.ExportStd`, internal/sketch/check/snapshot). Its first check of a process installs the snapshot, so it parses no std file and checks no std declaration, even with every cache empty. It decodes a std package's segment on the package's first import.

- An export is deterministic: the same std and checker give the same bytes, in any process (Law ExportIsDeterministic, `internal/sketch/check/snapshot/order.go`). `TestStdSnapshotIsCurrent` compares the embedded bytes with this head's export and fails when they differ, so the gate refuses a stale snapshot before a release is built from it, and an edit that changes nothing checked needs no new snapshot. Rewrite the snapshot and `stdsnap_gen.go` (the digest of the std sources) with `go test ./internal/sketchfront -run TestStdSnapshotIsCurrent -update-std-snapshot`.
- At run time the compiler compares the snapshot's std-sources digest with the std sources the binary embeds. When they differ, it refuses the snapshot and falls back to the disk cache (CHK1b) or to source.
- `ERGO_STD_SNAPSHOT=off` selects the reference: std is checked from source, or read from the disk cache. `TestStdSnapshotAgrees` compares the reference with both the embedded snapshot and a snapshot this process exports, over the examples, seeded programs and the checker's corpus.
- How the bytes stay the same: the checker's finishInfo visits its node-keyed maps in source order (the one pass whose map order reached the type table's ids in std); the snapshot carries no memo of the type table (they are keyed by object identity, and a decoded checker rebuilds them on use); and the generated codecs write a map's entries in rank order (an id already given, a node's tree-order id, else the type and fields). `TestExportIsDeterministic` checks two checks from source and an export with tied keys reversed.

## ergo budget

`ergo budget [--config FILE] [--width N] [--class crit|lane] [--lane NAME] -- COMMAND [ARGS...]` (`cmd/ergo/budget.go`, `internal/budget`, unit WS4a) runs COMMAND once the host's budget has `--width` cores free for it, and gives the cores back when COMMAND ends. Every `ergo budget` on the host shares one budget, so ten workspaces cannot each take every core. Its design is the model `models/gatebudget`, checked by `ergo test ./models/gatebudget`.

- **The budget file.** The host's owner writes it, because the host may be shared. It is named by `--config` or `$ERGO_BUDGET`, with one `key value` per line:
  - `cores N`, the budget, required;
  - `share N`, the lane class's share of the budget;
  - `gate-load N`, the interim load gate;
  - `state DIR`, the folder of the budget's state, by default `FILE.state`;
  - `log FILE`, which gets a `queue`, `take` and `end` line per command.
- **Cores, not runs.** A take names its width, and the widths held never sum past `cores`. A wide take (a heavy run) waits in the same queue as a narrow one.
- **Order.** One queue, served in order with no backfill: a narrow newcomer never passes a wide older waiter.
  - The next waiter is the oldest lane waiter while the lane class holds less than its share, else the oldest crit waiter, else the oldest lane waiter.
  - A release hands the cores on at once. Waiters sleep on the holders' locks, so a release and a crash wake them.
- **Crashes.** Each waiter and holder owns a file under the state folder, flocked for its lifetime, so the kernel frees a dead runner's cores. The lock is never inherited by COMMAND.
- **Children.** COMMAND runs with `GOMAXPROCS` set to the width and the grant lent in `$ERGO_BUDGET_GRANT`. An `ergo budget` inside it, of at most that width, runs in the grant and takes nothing, so a holder never waits on its own child.
  - COMMAND runs in its own process group, which is killed when COMMAND ends.
  - On Linux, COMMAND also dies with `ergo budget`.
- **The interim load gate.** With `gate-load N`, the lane class takes nothing while the 1-minute load is over N, and the load is read again every 15 seconds. Crit is never gated. The memory-admission unit (WS4c) replaces the gate.
- **Exit.** COMMAND's exit code (128 plus the signal for a signal); 2 for an invalid invocation; 1 when the budget cannot be read.

## ergo dev

`ergo dev [DIR] [--idle DURATION]` (`cmd/ergo/dev.go`, issue #203) is one daemon for each workspace (DIR, by default the working directory) and Ergo release. It answers a warm `ergo check` with no process start. Its lifecycle is the model `models/dev`, checked by `ergo test models/dev`. The model holds three invariants: at most one daemon per workspace and release; a request is answered by a daemon of the client's release, or in process; no request is lost at idle exit or at a crash.

- **Identity.** The daemon's socket and lock are `dev/<digest>.sock` and `.lock` under the cache root. The digest is of the release (the producer qualifier) and the workspace's absolute path, so two releases serve one workspace with two daemons.
- **One daemon.** A daemon takes the lock with a non-blocking `flock` before it listens. A second daemon of the workspace and release prints `already running` and exits 0. The kernel gives the lock back when a daemon dies, so a crash leaves no lock; it may leave the socket file, which the next lock holder removes.
- **Ready line.** On stdout: `ergo dev: serving DIR at SOCKET release RELEASE`.
- **Requests.** A request is one JSON object on the socket: `release`, `dir` (the client's working directory), `env` (the client's environment) and `args` (`["check", PATH, options...]`). The answer is one JSON object: `served`, `stdout`, `reason` and `work` (the stage counters the daemon spent on it).
  - The daemon answers only from memory, the warm answer of the store ([build.md](spec/build.md), Warm answer), and starts no process. It checks the inputs the manifest names, as the CLI's warm path does, but between requests it keeps each input file's hash, each folder's listing digest and the decoded manifest (`sketchfront.StatSums`). A kept read stands while the file's stat (size, modification and change time, device, inode) is the one it was read with, and only if the file's last change was more than a second before that read. A write in the same timestamp tick may leave the stat as it was (Git's "racily clean" entry), so a file changed that recently is read again. So a request stats every input but reads and hashes only the files whose stat changed.
  - It serves a request only when the request is from its own release and its environment is the daemon's own. The comparison leaves out `PWD`, `OLDPWD`, `SHLVL`, `_` and `ERGO_STAGE_REPORT`, and a variable given twice keeps its last value.
  - Everything else is answered `served: false`, and the client answers it in process. A cold check, a build and a check whose inputs changed are answered this way.
- **The CLI as client.** `ergo check DIR` asks the daemon of its release that serves the package's folder or its nearest ancestor. It answers in process when no socket is there, the connection fails, the connection ends with no answer, or the daemon does not serve the request. Since a request is a pure function of its inputs, asking twice is safe. `ERGO_DEV=off` turns the client off.
- **Exit.** After `--idle` (default 10m) with no request, or on SIGINT or SIGTERM, the daemon removes its socket file and closes its listener. It then answers the requests already accepted and exits, which gives back the lock. A client that connects late finds no listener and answers in process.
- **Not served yet.** The daemon answers no cold check: it does not hold the checked program in memory. Its work for a request is a stat of each input, in proportion to the program, plus a read of each file that changed; a file watch would remove the stats. Builds, `ergo test` and the LSP and MCP are not served either.

`TestDevAnswersAWarmCheck` runs the daemon, the CLI as its client, a second daemon and an idle exit; `TestDevClientAnswersInProcessWhenTheConnectionEnds` checks the client's fallback, and `TestStatSumsReadOnlyWhatChanged` the rule of the kept reads. `go run ./scripts/buildcost dev` counts the daemon's work for each request (the receipt's "ergo dev (CS9)" section).

## Stage counters

`ERGO_STAGE_REPORT=FILE` makes any `ergo` command write, as it exits, a JSON object of the work it did (`internal/stage`, `sketchfront.StageReport`): `files_read` and `bytes_read` (source inputs read from disk), `files_parsed` and `bytes_parsed` (std's files included in the file count), `packages_checked` and `decls_checked`, `std_files_parsed`, `std_packages_checked` and `std_packages_decoded` (the checker's std work, from source or from the checked std snapshot), `modules_lowered`, `go_bytes_lowered` and `modules_reused` (the emission cache), `bytes_hashed`, `go_compiles` and `go_compiles_reused`, `links` and `links_reused` (the direct path's actions), `go_commands`, `processes` (every process the command started, Go tools and the programs it runs included), `bytes_written` and `outputs_placed` (executables placed at an output path), `std_exports` (the standard archives the go command gave the direct path's plan; 0 when a [pin archive](spec/build.md#pin-archives) set held them), `obligations_affected` (the tests and law runs `ergo test --affected` found affected or new against its BASE; the git reads of BASE are not processes the command counts), `shared_fallbacks` (the `ergo test DIR/...` runs whose module test binary did not build, so each package was tested alone), and `binaries_ir` and `binaries_text` (the executables a build placed, by their module's lowering: with the IR bodies, as every `ergo` command builds, or the Go source text alone; the examples runner fails any `ergo test` that places a `binaries_text` one), and `obligations_evaluated` and `eval_steps` (the tests and law runs check-time evaluation decided, by `ergo check` or by `ergo test`'s first tier, and the evaluator steps it spent, test-speed FT0 and FT1), `obligations_native` (those a test binary ran), `shared_test_modules` (the shared test modules `ergo test DIR/...` linked, TEST-one; 0 when it linked each package's own: the examples runner fails a program whose test leg linked a module its key did not hash), and `obligations_stored` and `packages_routed` (the verdicts it printed from the verdict store with no run, and the packages a route note sent to the test binary with no evaluation, [testing.md](testing.md#two-tiers-the-evaluator-and-the-test-binary)). The counters count work, never time, so they are the same on any host. `TestStageReportCountsAgree` holds them to a count made from the files and to the direct path's `Report`; `TestFrontEndWorkGrowsLinearly` holds the front end's work linear in the program.

`go run ./scripts/buildcost` runs the compile-speed scenarios (first build, warm, comment, body and signature edits, `check` and `test` twice) on programs of the seeded generator `internal/testinputs/genprogram` and on named examples, and prints the counters of each with the user-mode instructions of its process tree where Linux allows `perf_event_open`; `buildcost empty` counts the thin client and the empty-package compile, and `buildcost gen DIR N SEED` writes a generated program. Wall times are context. The baseline is [the compile-speed receipt](receipts/compile-speed.md). `go run ./scripts/buildcost test` runs the test cost receipt (test-speed FT0): per example package, `ergo check` twice, `ergo test` first, rerun twice, after a comment edit and after a one-line body edit, then `ergo test ./...` per example module, each line with the instructions and the stage counters, the obligation counters included (`obligations_evaluated`, `eval_steps`, `obligations_native`, `obligations_stored`), and a summary of the test-speed plan's §5 rows.

`go run ./scripts/buildcost tests [-kinds property,diagnostics,built] [-rounds 5] [-kills] [-o FILE]` asks whether a Go test family is cheaper as Ergo (wf10 TPROBE). For each kind it counts four forms of one family on the same subject: the Go test as the gate runs it, a hand Go control (a plain `main`), `ergo test` and `ergo check` of an Ergo form laid over a scratch copy of the tree, cold (new caches, Go's std and Ergo's pinned sets on disk), warm and after a named one-line edit, beside two floors (the control's binary run alone, and a hash of the inputs read against one stored verdict). The families, their commands and edits live in `scripts/buildcost/testdata/tprobe/families.json`. `-kills` first judges each mutant of the family's ledger with every form and writes the kill matrix there; an Ergo form that misses a kill has no speed result. A kind is a `win`, and ports, when an Ergo form is faster in any one of cold, warm and edit (owner, 2026-11-18: "Any gain ports"); the verdict names the form, the scenarios it wins and every slower one with its ratio. `tie`, `loss` and `no result` stay Go. The meter never writes the checkout but for the kill matrix, and removes the caches it made. The receipt is [the self-host receipt's TPROBE section](receipts/self-host.md#tprobe).

### Process start

Every `ergo` process, a warm answer included, pays its packages' inits before `main`. A package of the module keeps package-level values that cost nothing to build (constants, and slices and structs Go lays out at build time). A table a command needs, such as a map or a parsed or read source, is built on its first use (`sync.OnceValue`), never at start. `TestStartBuildsNoTables` bounds the bytes the module's inits allocate, from `GODEBUG=inittrace=1`. `go run ./scripts/buildcost start` counts the thin client, the warm `check` and `build`, and the start of a probe per package; `buildcost count CMD ARG...` counts any command (docs/receipts/compile-speed.md, "Process start"). `buildcost reuse` checks generated programs and examples in process, edits them, and counts the packages the incremental check's decision would check again after each edit (docs/spec/build.md, "Interface fingerprint"; docs/receipts/compile-speed.md, "Incremental check (CS5a)").
